# モニターを挿しただけでソフトウェアが入る — LG・Windows Update・ドライバー信頼体系の穴

> モニターがユーザーの同意なしに Windows Update でソフトウェアをインストールできるということは、個別ベンダーの逸脱か、ドライバー署名・アップデート信頼体系に空いた構造的な穴か。

## 導入

2026 年 7 月 18 日 (KST)、Hacker News のトップに上がったのは videocardz.com の一本の記事だった。タイトルは "LG monitors silently install software through Windows Update without user consent" — LG モニターがユーザーの同意なしに Windows Update を通じてソフトウェアをこっそりインストールする、というものだった。1078 点、コメント 546 件。単一ベンダーの一度のミスを扱った記事がこれほどの反応を得ることは珍しい。反応の大きさは、この事件が単なる LG のミスとして読まれなかったという信号である。

事実関係は単純だ。ユーザーが LG モニターを Windows PC にケーブルで接続すると、何の確認ウィンドウも出ないまま `LG Monitor App Installer` という Microsoft Store アプリがインストールされる。Microsoft Store 上のパッケージ識別子は `9PM9N6F47JB8-LGElectronics.LGMonitorApp` で、発行者は LG Electronics 本人だ。インストールされたアプリは起動のたびに McAfee の 30 日間無料体験ポップアップを表示する。ユーザーはソフトウェアをダウンロードするとクリックしたことも、ライセンスに同意したこともない。モニターという物理的な周辺機器を一つ接続しただけである。

この事件が大きな反響を呼んだのは、これが LG だけの問題ではないと多数のユーザーが即座に見抜いたからだ。同じメカニズムの上で、Alienware、ASUS、Samsung の類似した自動インストールが同じスレッドで報告された。すなわち問題の重心は 「LG が悪事を働いた」 ではなく、「モニターメーカーがユーザーの同意なしに任意のソフトウェアを PC に押し込める通路が Windows の中にすでに存在する」 という事実そのものにある。リード質問はここから出る。これは個別ベンダーの逸脱なのか、それともドライバー署名とアップデート信頼体系が最初から抱えていた構造的な穴なのか。本稿は、何がどうインストールされるのか、その通路がなぜ存在するのか、そしてその通路を塞げるのかを順に見る。

## 現象 — ケーブル一本に付いてくるもの

まず何がインストールされるかを正確に押さえる。インストールされるのはドライバーそのものではなく、`LG Monitor App Installer` という名のランチャーだ。このランチャーは接続されたモニターモデルに応じて追加ソフトウェアをダウンロードする中央ハブの役割を果たす。Microsoft Store の説明によれば、このハブが提供するのは OnScreen Control、LG Switch、Dual Controller、UltraGear Control Center といった LG モニターユーティリティである。これら自体は、モニターの輝度・画面分割・KVM 切替などを扱う正常な機能性ソフトウェアだ。問題は機能の有害性ではなく、インストールの無断性にある。

無断性を最も鮮明に露呈したのが McAfee 広告だった。igorslab.de と Tom's Hardware の報道によれば、あるユーザーが LG UltraGear 27GP83B 一台と LG 27GN800 二台を接続した後、Windows の信頼性履歴 (Reliability History) を確認する過程でこのインストールに初めて気づいた。発見の引き金は起動直後に出た McAfee のポップアップだった。30 日間無料体験を有料サブスクリプションへ転換するよう誘導するそのポップアップは、連続した 32 回の起動のうち 31 回で現れた。モニターユーティリティがアンチウイルスベンダーの広告掲示板になったのである。

さらに重いのは、このアプリが宣言した権限だ。privacyguides.org の整理によれば、`LG Monitor App Installer` は Microsoft Store 上で 「すべてのシステムリソースへのアクセス (access to all system resources)」 と 「インターネット接続へのアクセス (access your internet connection)」 を宣言する。すなわちこのアプリは UWP サンドボックスの制限を受ける通常のストアアプリではなく、システム全体にアクセスできる信頼レベルで実行される。同メディアはその含意をこう要約した。「理論的には、インターネットアクセスがあれば、このアプリは広告を別のものに差し替えたり、システムからデータを流出させたりすることもできる」 。今表示されているのが McAfee 広告だという事実は今日のペイロードにすぎず、その場所に何が入るかはベンダーとそのパートナーの選択次第だということだ。

ユーザーの制御権がいかに弱いかもこの事件の核心だ。HN ユーザー `Kelteseth` はこう書いた。「確認できる。昨日、私の Windows 11 マシンで同じことが起きた。アンインストールは Microsoft Store のライブラリ項目からしかできなかった」 。コントロールパネルの通常のプログラムアンインストール一覧にも、アプリ設定の明確な場所にもうまく露出しないというのだ。しかも削除しても終わりではない。HN ユーザー `thewebguyd` の証言はより直接的だ。「私は LG モニターを持っているが、ある時あの馬鹿げた LG アプリが現れたのに気づいた。アンインストールしたら、Windows Update の更新項目としてまた飛び出してきた。Microsoft がこの動作を能動的に可能にしている」 。削除 → 再インストールの循環は、Windows が自動ダウンロードしたドライバー・アプリをドライバーストア (Driver Store) にキャッシュしておき、デバイスが再認識されると再適用するために発生する。

ここで事件の性格が浮かび上がる。これはマルウェアの侵入ではない。署名された正規ソフトウェアが、正規の通路を通じて、ユーザーの明示的な同意なしに実行されたのである。HN ユーザー `devttyeu` の要約がその逆説を正確に突く。「あなたの OS が第三者ベンダーのマルウェア (技術的にはメーカーソフトウェア) をバックグラウンドで、ユーザー操作ゼロでインストールする」 。括弧内の訂正 — 「技術的にはメーカーソフトウェア」 — がこの事件のグレーゾーンを正確に印づける。コードは合法で署名は有効だが、ユーザーの同意だけがない。

## 深層 — Windows Update はなぜこれを許すのか

この通路はバグではなく設計だ。そして最初は善意で設計された。HN ユーザー `joe_mamba` はその歴史をこう回顧する。「これは Windows 7 以降あった機能で、うまく機能していた。インストール後にインターネットを漁り回る必要なく、必要なドライバーを全部引っ張ってきてくれたから」 。`orbital-decay` の指摘はその通路がいつから濫用されたかを突く。「プリンター、マウス、タブレット、ディスプレイタブレットのメーカーたちは、少なくとも Windows Vista や 7 以降、この通路を自社のガラクタアプリを押し込むのに使ってきた」 。すなわち 「デバイスを挿せばドライバーが勝手に入る」 という利便性と、「デバイスを挿せば望まないソフトウェアが勝手に入る」 という濫用は、同じ一つのメカニズムの両面である。

そのメカニズムの現在の形を理解するには Windows の DCH ドライバーモデルを見なければならない。DCH (Declarative, Componentized, Hardware Support Apps) は Microsoft が推してきた現代的なドライバーパッケージ規格で、三つの原則から成る。第一に Declarative — ドライバーはコインストーラー (co-installer) や `RegisterDll` のような命令型拡張なしに、宣言的な INF ディレクティブのみでインストールされねばならない。第二に Componentized — 基本ドライバーと OEM・エディション別の任意のカスタマイズが分離されねばならない。第三が核心で、Hardware Support App (HSA) — ドライバーに付随するすべての UI 構成要素はドライバーパッケージの外へ分離され、HSA という別個のアプリとしてパッケージされねばならない。

まさにこの HSA が濫用の通路だ。Microsoft のドキュメントによれば、HSA は UWP あるいは Desktop Bridge アプリとして MSIX パッケージされ、必ず Microsoft Store を通じて配布・更新されねばならない。そしてメーカーはこの HSA を 「デバイスが接続されると自動インストール」 されるよう構成できる。自動インストールの流れはこうだ。デバイスを接続すると Windows がそのハードウェア識別子を WMIS (Windows Metadata and Internet Services) から取得したデバイスメタデータと照合し、メタデータをパースして関連づけられたアプリを識別した後、そのアプリのダウンロードを引き起こす。LG のケースで起きたことがまさにこれだ。カーネルに実際にロードされるディスプレイドライバーは Windows 標準ドライバーで十分なのに、デバイスメタデータが指すストアアプリ — `LG Monitor App Installer` — が自動で付いてきたのである。

ここで二つの信頼判断が一つに潰される。署名信頼体系が保証するのは 「このコードは検証された発行者 (LG Electronics) から来ており、配布途中で改竄されていない」 という出所の真正性だ。ところが自動インストールメカニズムは、この出所保証を 「ゆえにこのコードはユーザーが望み、安全だ」 という意図の正当性へとこっそり拡張する。署名は出所を証明するだけで善意を証明しない。HN ユーザー `MatejKafka` はこの点をこう整理した。「ドライバーは依然として認証を通過し署名を受けねばならない。Microsoft にはそれを拒否する権限がある」 。形式的には正しい。しかし認証と署名が検査するのはコードの技術的適合性と発行者の身元であって、「このアプリが起動のたびに McAfee 広告を表示するか」 という行為の正当性ではない。ゲートは存在するが、そのゲートが測る尺度が別物なのだ。

問題を原理のレベルで突いたのは HN ユーザー `coldtea` だった。「ドライバーはいかなる種類であれ広告を表示する前面プログラムであってはならない。サンドボックスに閉じ込められ、厳格な API に従うべきだ」 。この指摘が的確なのは、DCH モデルがそもそもドライバーから UI を切り離してサンドボックス化した HSA へ分離しようとする規格だった点にある。ところがその HSA が 「すべてのシステムリソースへのアクセス」 権限を宣言し広告を表示した瞬間、サンドボックスで危険を隔離しようとした設計意図は裏返る。隔離のために作った箱が、隔離されていない権限を入れる箱に使われたのだ。

この構造は新しいものではない。OEM が特権的な通路を用いてユーザーが要求していないソフトウェアを植えるパターンには、よく知られた先例がある。最も悪名高いのは 2015 年の Lenovo の Superfish 事件だ。Lenovo は消費者向けノートに Superfish Visual Discovery という広告挿入ソフトウェアをプリインストールしたが、このソフトウェアがウェブページに広告を注入するために自己署名ルート証明書をシステム信頼ストアに植えた。その証明書の秘密鍵がすべての機器で同一だったため、誰であれその鍵を抽出すれば任意の HTTPS 接続を中間者 (MITM) で傍受できた。利便性のために植えたソフトウェアが TLS 信頼体系全体を崩したのである。米国 FTC は 2017 年に Lenovo と和解に至った。

Superfish だけではない。HP は 2017 年頃、HP Touchpoint Analytics のようなテレメトリーサービスをユーザーの同意なしにアップデートを通じて植えて論争になり、Lenovo はこれより前に LSE (Lenovo Service Engine) を通じ BIOS/UEFI の WPBT メカニズムで OS 再インストール後もソフトウェアを自動復旧させるようにして批判を浴びた。通路は毎回異なる — プリインストール、ファームウェア、テレメトリー更新、そして今回の Windows Update HSA。しかし構造は一つに収束する。消費者機器への信頼 — ハードウェアを買えばそのメーカーが自分のシステムへ特権的アクセスを持つという事実 — を、メーカーがユーザーの利益ではなく自社の収益化へ転用するのだ。LG のケースはこの系譜の最新項目であり、通路がいまや 「モニターケーブル接続」 という最も受動的な行為にまで降りてきた点で、むしろより重い。

## 展望 — この穴を塞げるか

実務的な対応から見る。個別ユーザーがこの自動インストールを切る方法は存在する。設定ではシステム > バージョン情報 > システムの詳細設定 > ハードウェアタブ > デバイスのインストール設定で 「デバイス用のメーカーアプリを自動的にダウンロードしますか?」 を 「いいえ」 に変える。より確実にはグループポリシーエディター (`gpedit.msc`) で、コンピューターの構成 > 管理用テンプレート > システム > デバイスのインストールの 「インターネットからのデバイスメタデータの取得を禁止する」 と 「メタデータに関連づけられたアプリケーションの自動ダウンロードを禁止する」 を有効にする。HN ユーザー `delta_p_delta_x` がスレッドで共有したのも、まさにこの経路だ。

しかしこの対応には三つの構造的限界がある。第一に、これらの設定の既定値が 「はい」 だという点だ。すなわち何もしていない圧倒的多数のユーザーは自動インストールに晒されている。オプトアウト (opt-out) を要求する設計は、問題を知る少数だけを守り、知らない多数を放置する。第二に、`gpedit.msc` は Windows Home エディションに存在しない。すなわちこの最も確実な遮断手段は、最も脆弱な消費者層 — Pro を買っていない一般ユーザー — にはそもそも与えられない。第三に、ドライバーストアキャッシュの問題により、すでに流入した項目はデバイス再認識時に蘇りうる。HN ユーザー `Someone1234` はそれゆえこう釘を刺した。「Microsoft がここに介入すべきだ。これは自社製品を使う人に正常に期待されるべき動作ではない」 。ユーザー側の緩和策が存在するという事実が、設計責任をユーザーへ転嫁する根拠にはなりえないという指摘だ。

Microsoft の立場から見れば、これはインセンティブ構造の問題だ。自動ドライバー・アプリインストール通路は OEM が要求する機能である。プリンター・マウス・GPU・モニターのメーカーすべてが 「自社デバイスを挿せば自社ソフトウェアが即座に準備されていること」 を望み、その即時性が Windows のハードウェア互換性という中核価値を支える。HSA 自動インストールを全面廃止すれば正常なデバイスの利便性も一緒に死ぬ。逆に放置すればその通路は広告とテレメトリーの配管として使われ続ける。Microsoft は使いやすさと濫用防止のあいだのトレードオフのど真ん中に立っており、これまでの既定値の選択 — 自動インストール 「はい」 — は OEM 側に傾いていた。

技術的変化の兆しはある。Microsoft のドキュメントによれば、今回の事件の配管であるデバイスメタデータ (device metadata) 方式はすでに deprecated 状態であり、今後の Windows リリースで削除され 「ドライバーパッケージコンテナーメタデータ (Driver Package Container Metadata)」 へ置き換えられる予定だ。しかしこれが濫用を終わらせるかは不確実である。代替メカニズムもまた 「デバイス識別子に紐づいたアプリを自動インストール」 するという根本設計を共有するなら、配管の名が変わるだけで濫用の表面積はそのまま残る。核心となる変数は、自動インストールの既定値を 「いいえ」 へ反転させるか、そしてストア認証段階で 「起動のたびに第三者広告を表示する HSA」 のような行為を拒否事由とするかだ。前者は OEM の反発を、後者は審査コストの増大を招く。どちらも Microsoft がこれまで負おうとしなかったコストである。

OEM 側のトレードオフも明白だ。この通路で得るのはソフトウェア配布の摩擦の除去と、McAfee のような提携先からの付加収益である。失うのは信頼だ。1078 点の HN スレッドと複数メディアの同時報道が示すように、こうした濫用はいまや即座に可視化され、ブランドコストとして跳ね返る。Superfish 以降、Lenovo が 「ブロートウェアのないクリーンなイメージ」 をマーケティングポイントに据えねばならなかったことが、そのコストの実物だ。規制面でも FTC の Superfish 和解という先例があり、同意なきインストールが繰り返されれば、消費者保護・欺瞞的慣行 (deceptive practices) のフレームで規制リスクが高まる。短期の提携収益と長期の信頼・規制リスクのあいだの交換で、LG はいま後者の請求書を受け取っている。

結局、三当事者の誘因が食い違った場所にこの穴がある。Microsoft はハードウェア互換性のために自動通路を開けておきたく、OEM はその通路で収益化したく、ユーザーは望まないソフトウェアを拒否したい。前の二者は通路の存在を望み、最後の一つだけが通路の閉鎖を望む。力の配分がこのように 2 対 1 である限り、既定値は通路を開ける側に設定され続ける。この穴を塞ぐ唯一の確実な道は、自動インストールをオプトイン (opt-in) へ反転させ、「ユーザーが明示的に許可していないソフトウェアはインストールされない」 という原則を既定値に据えることだ。しかしその決定は技術ではなく、力の再配分の問題である。

## 結論

リード質問に戻る。これは個別ベンダーの逸脱か、構造的な穴か。正直な答えは両方であり、その二つは分離されない。LG がモニターユーティリティランチャーに McAfee 広告を載せ起動のたびに表示したのは、明らかにベンダーの逸脱だ。しかしその逸脱が可能だったのは、「署名された発行者のアプリをデバイス接続だけで自動インストールする」 という通路を Windows が既定値で開けておいたからである。逸脱は個別的だが、逸脱を実行する配管は構造的に予め敷かれていた。

この事件の本当の教訓は署名信頼体系の限界にある。コード署名とストア認証は 「誰が作ったか」 と 「改竄されていないか」 を証明するには有効だが、「このコードがユーザーの利益のために動作するか」 は証明しない。出所の真正性と意図の正当性は別の軸であり、今の信頼体系は前者を検証した後、後者まで自動的に承認してしまう。LG、Alienware、ASUS、Samsung が同じ通路で発見されたという事実は、これが一社の道徳性の問題ではなく、その承認の自動性が生んだ構造的誘因の問題であることを語る。

消費者機器への信頼とは結局こういうことだ。ユーザーがモニター一台を買ってケーブルを挿すとき、彼は画面が点くことを期待するのであって、自分の PC に全権アクセスのソフトウェアが植えられることを期待していない。その期待と実際のあいだの隙間を埋めていたのはメーカーの自制であり、LG のケースはその自制がいかに薄い防御線だったかを示した。自制に依存する信頼は、いつであれ収益化の誘惑の前で崩れる。穴を本当に塞ぐには既定値を変えねばならず、既定値を変えることは Microsoft・OEM・ユーザーのあいだの力の配分を変える営みだ。その再配分が起きるまで、次のベンダーの次のポップアップは予定された事件である。
