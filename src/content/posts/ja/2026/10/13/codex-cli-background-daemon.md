# コマンドから常駐サービスへ — Codex CLIのデフォルトデーモンが問うもの

> CLIがウィンドウを閉じた後も残り、自らを更新するのであれば、それは利便性のための設計なのか、ユーザーが同意した覚えのない常駐サービスなのか。

## 導入

2026年10月12日（米国時間）、Hacker Newsのトップページに「Codex CLIはデフォルトで、永続的かつ自己更新するバックグラウンドデーモンをインストールする」というタイトルの投稿が上がり、609ポイントを集めた。リンク先は記事ではなく、OpenAIの`openai/codex`リポジトリに立てられたGitHub issue #48195である。issue自体は9月25日に登録されたもので、半月以上静かに積み上がっていた不満が、Hacker Newsを経由して一気に噴き出した格好だ。

issue作成者のYihua-Liu-1997の要求はシンプルである。CLIでは`daemon_auto_start`をオプトイン（デフォルトfalse）にするか、少なくとも有効化する前に一度は確認してほしい、というものだ。根拠として挙げられた観察は四つある。対話型の`codex`セッションを開くだけで、すべてのウィンドウを閉じた後も生き続けるデーモンが起動する。約374MBのプラットフォームパッケージ一式がホームディレクトリ配下にコピーされ、デーモンはそのコピーから実行される。切り離されたアップデーターが起動5分後、以降は毎時アップデートを確認し、新しいリリースをダウンロードしてバックエンドを再起動する。そしてデーモンは、最初に自分を起動したセッションの環境変数を握り続ける。

本稿はこの件を一件のバグ報告としては読まない。開発ツールが「ユーザーが実行するコマンド」から「ユーザーのマシンに常駐するサービス」へと性格を変えるとき、何が一緒に変わるのか。そしてその転換をデフォルト値として押し通すとき、どのようなコストが誰に移るのかを検討する。

## 現象の分析：0.157.0で実際に起きたこと

まず事実関係をissue本文に沿って整理しておく。作成者の環境は、Linux（WSL2）上で`npm install -g @openai/codex`によりインストールしたCLI 0.157.0である。このバージョンから、対話セッションを開くと`codex app-server --managed-daemon`プロセスが別セッションでTTYなしに起動する。このプロセスはCodexのウィンドウをすべて閉じた後もPID 1に親が付け替えられて残り、`codex app-server daemon stop`を実行するか再起動するまで動き続ける。

二つ目の観察はより微妙だ。デーモンは、npmがインストールしたばかりのものとバイト単位で同一のパッケージ（`codex`、`codex-code-mode-host`、同梱の`bwrap`・`zsh`・`rg`）を`~/.codex/packages/app-server-daemon/releases/<version>/`配下に丸ごとコピーし、そのコピーから実行される。作成者の言葉を借りれば、この時点からバックエンドのバージョンは、パッケージマネージャーでインストールしたCLIのバージョンと切り離される。ユーザーはnpmで特定のバージョンを入れたと信じているが、実際にターンを処理しているのは別のパスに置かれた別世代のバイナリかもしれない。

三つ目はアップデーターである。`codex app-server daemon pid-update-loop`という切り離されたプロセスが、起動5分後、以降は毎時アップデートを確認し、新リリースをダウンロードしてバックエンドを再起動する。関連issue #40969（8月26日登録、本稿執筆時点でオープン）は、この再起動が実行中のターンに60秒のドレイン時間しか与えず、その後SIGKILLを送ると報告している。ビルドやテストを数分かけて回すエージェント作業であれば、アップデート一回で作業が断ち切られるということだ。

四つ目は環境の固定である。作成者は呼び出しごとに`HTTPS_PROXY`を差し替えるラッパー経由でCodexを起動しているが、デーモンは最初に自分を起動したセッションのプロキシ変数を使い続け、以降のセッションがどんな設定で起動されても外向きの接続はその最初のプロキシを経由する。作業ディレクトリがセッションではなくデーモン基準になるという#42457、#37537も同じ根から来ているように見える、と作成者は記している。10月13日には、macOSで0.162.1を使う別のユーザーが「デーモンサーバーがセッション間で環境変数を漏らす」というタイトルで#53547を新たに起票した。

さらに、無効化の過程で見つかったバグが加わる。`codex app-server daemon stop`はアプリサーバーを止めるが、アップデーターのプロセスは残したままで、作成者は70秒後もまだ生きているアップデーターを手動でkillしなければならなかった。issueに記されたワークアラウンドは次のとおりだ。

```sh
codex features disable daemon_auto_start
codex app-server daemon stop
pkill -f 'app-server daemon pid-update-loop'   # not stopped by `daemon stop`
rm -rf ~/.codex/packages/app-server-daemon
```

では、OpenAIはこの変更をどう告知したのか。0.157.0のリリースノート（9月25日公開）の新機能一覧には、「対象となる対話セッションでバックグラウンドサーバーの自動起動を有効化し、サーバー設定に互換性がない場合の復旧選択肢を追加した」という趣旨の一文がある。永続プロセス、パッケージのコピー、毎時のアップデーターという言葉はその一文には出てこない。issueスレッドのあるコメント（foma-agent）は、公式の設定リファレンスページに`daemon_auto_start`の項目が一つもないと指摘している。これは当該コメントの主張であり、筆者が設定リファレンスページを直接確認したわけではない。

Hacker Newsスレッドの反応は大きく三つに分かれた。一つ目は回避策の共有である。あるユーザー（whimblepop）は、文書化された設定はないがフィーチャーフラグで無効化できるとして、`~/.codex/config.toml`の`[features]`の下に`daemon_auto_start = false`を書く方法を案内した（直接の引用ではなく、コメントの要旨の要約）。別のユーザー（grimgrin）はそれに加え、シェル関数で常に`--no-daemon`を付ける二重の防御を紹介している（直接の引用ではなく、コメントの要旨の要約）。二つ目はディスク使用量だ。あるユーザー（icantevenhold）は、古いバージョンが溜まって自分のシステムで合計12GB程度を占めていたと書いた（直接の引用ではなく、コメントの要旨の要約）。三つ目は比較である。Claude Codeも同じ運用モデルだとして、ホームディレクトリ配下の旧バージョンのバイナリ群と、フォアグラウンドのウィンドウなしに動くバックグラウンドタスクを確認したというコメント（timdorr）があった（直接の引用ではなく、コメントの要旨の要約）。

## 深層分析：何が「コマンド」と「サービス」を分けるのか

この件の核心は自動アップデートそのものではない。Hacker Newsの最初のコメント（dingaling911）は、この分野は動きが速いので自動アップデートは標準であり、ブラウザもそうしているのだからハーネスがやらない理由はない、と反論した（直接の引用ではなく、コメントの要旨の要約）。この反論は半分は正しい。ブラウザの自動アップデートは、セキュリティパッチを素早く行き渡らせる実績ある方式である。しかしブラウザとCodex CLIとでは、ユーザーが結んだ契約の種類が違う。

UNIXの伝統において、CLIの契約は明快だ。ユーザーがコマンドを実行するとプロセスが立ち上がり、仕事をし、終われば消える。そのプロセスは呼び出し元シェルの環境変数と作業ディレクトリを継承し、実行されるバイナリはユーザーが（あるいはユーザーが委ねたパッケージマネージャーが）インストールしたまさにそのファイルである。あるHacker Newsユーザー（kristjansson）は、デーモンモードが「Codex CLIは呼び出したシェルの環境変数を継承する」といった前提を壊すと指摘した（直接の引用ではなく、コメントの要旨の要約）。プロキシの固定や作業ディレクトリの問題は、この契約違反が表面に現れた症状である。

一方、ブラウザやデスクトップアプリは最初から「常駐するアプリケーション」としてインストールされ、ユーザーはそれが自己更新することをおおむね承知のうえで受け入れている。issue作成者もまさにこの区別を提案している。共有され自己更新するデーモンはリモートコントロールやデスクトップアプリでは合理的なのでそこでは有効にしてよいが、CLIのデフォルトは「ウィンドウと共に生きて共に死に、自分がインストールしたバイナリを実行し、バックグラウンドで自己更新しないこと」であるべきだ、という主張である。Hacker Newsでも、デスクトップクライアントなら想定内だが、npmでインストールしたCLIがこうするのは驚くのも無理はない、というコメント（infinite_spin）が同じ線を引いた（直接の引用ではなく、コメントの要旨の要約）。

二つ目の論点はサプライチェーンである。パッケージマネージャー経由のインストールには、それ自体に統制点がある。npmならlockfileとバージョン固定、Homebrewやディストリビューションのパッケージならメンテナーのレビューと署名がある。あるHacker Newsユーザー（thebeardisred）は、まさにこういう場面でディストリビューションモデルの価値がわかるとして、パッケージングしテストし妥当なデフォルトを決めてくれる人々がこうした事態を防いでくれると書いた（直接の引用ではなく、コメントの要旨の要約）。ところが、デーモンがインストール済みパッケージをホームディレクトリへコピーし、そのコピーを毎時自ら差し替え始めると、パッケージマネージャーはもはや実際に実行されるコードの正本ではなくなる。企業環境で特定バージョンを承認・配布したとしても、その承認が有効なのは最初の一時間だけである。

issueスレッドのあるコメント（aetherxeg-source）は、この問題を「インストールされたCLIのアイデンティティ ≠ デーモン実行のアイデンティティ」という境界として要約した。そして、クライアントが接続するたびに、CLIバージョン、デーモンバイナリのダイジェスト、デーモンの世代、アップデーターの状態、継承された環境の世代を含む「実行レシート」を提示しようと提案している。大げさな提案に聞こえるかもしれないが、問い自体は正確だ。いまこのターンを処理しているのは正確にどのコードなのか。現在の構造では、ユーザーはこの問いに答える手段を持たない。

この問いがコーディングエージェントにおいて特に重い理由がある。コーディングエージェントはシェルコマンドを実行し、リポジトリを読み書きし、しばしば認証情報が置かれた環境で動く。あるHacker Newsユーザー（dllu）は、自動アップデートの途中で権限が壊れ、`.git`が読み取り専用になって目標の作業が止まった経験を報告している（直接の引用ではなく、コメントの要旨の要約）。本ブログは7月12日に、Grok CLIがxAIに何を送っているかをパケットレベルで分析した記事を扱った。あのときの問いが「このエージェントは何を外へ送るのか」だったとすれば、今回の問いは「このエージェントは自分のマシンの中に何を残し、それは誰の意志で変わるのか」である。二つの問いは同じ信頼境界の内と外だ。

もちろん反対側の事情もある。Hacker Newsで法律向けIDEを作っているというユーザー（piker）は、バグのあるアプリケーションが現場に長く残ることもまたユーザーに敵対的だとし、自分たちはデーモン方式も検討したが、最終的には起動のたびにアップデートを強制確認する方式を選んだと書いた（直接の引用ではなく、コメントの要旨の要約）。この対比には示唆がある。同じ「早く更新させたい」という動機でも、実行時にユーザーの目の前で確認する方式なら、ユーザーはその瞬間を見ることができ、拒否することもできる。バックグラウンドデーモンは、その瞬間をユーザーの視界の外へ移す。違いは更新頻度ではなく、可視性と拒否可能性にある。

## 展望と示唆：行儀のよいCLIの条件

この件からは「行儀のよい開発ツール」の条件をいくつか引き出せる。第一に、常駐はオプトインであるべきだ。ウィンドウを閉じた後も残るプロセスは、ユーザーが明示的に求めたときにだけ生まれるべきである。Codexにはすでに`codex app-server daemon start`という明示的な入口があるので、issue作成者の提案どおりその経路でのみデーモンを起動するのは、技術的に難しくないように見える。

第二に、パッケージマネージャーでインストールされた場合は、そのインストールを正本として尊重すべきだ。issueは、npm、brew、pacmanなどでインストールされたならコピーも自己更新もせず、インストール済みのバイナリを実行せよと求めており、外部管理のデーモン実行ファイルをサポートしてほしいという#41188（Nix、Homebrew、npmによるインストールを例に挙げている）も同じ方向である。自己更新機能が意味を持つのは、独自のインストールスクリプトで入れたユーザーに対してだけだ。Hacker Newsでは、XDG仕様に従わないこと自体が、そのアプリがシステムを乱暴に扱うことのシグナルだという指摘（quotemstr）も出た（直接の引用ではなく、コメントの要旨の要約）。

第三に、無効化の方法は文書化され、完結していなければならない。現在のワークアラウンドは、文書化されていないフィーチャーフラグ、アップデーターを残すstopコマンド、手動の`pkill`とディレクトリ削除の組み合わせである。無効化に四つの手順が必要で、そのうち一つがバグの回避なのであれば、その機能は事実上無効化できないものに近い。

第四に、自動起動されたデーモンは、最後のクライアントが離れたときに一緒に終了すべきだ。これはissue作成者が、デフォルトを維持するとしても最低限これはしてほしいと求めた項目の一つであり、「ウィンドウと共に生きる」というCLIの契約を部分的にでも取り戻す方法である。

組織の立場から見ると、示唆はより実務的になる。コーディングエージェントは、いまや開発者個人の道具である以前に、エンドポイント上で動くソフトウェア資産である。Hacker Newsとissueスレッドには、コンテナや別VM、専用機の中でしかエージェントを動かさないというコメントがいくつもあった。これを過剰反応と見ることもできるが、バージョンを固定し、変更履歴を確認してから上げるという運用原則は、ほかのどの依存関係にも適用してきたものだ。エージェントだけが例外である理由はない。一方で、Hacker Newsの何人かのユーザーは、OpenAIがサードパーティ製ハーネスの利用を認めている点を挙げ、ファーストパーティのハーネスが悪くても逃げ道はあると指摘した。この競争圧力がデフォルトを元に戻す原動力になるかは見守るしかない。本稿執筆時点でissueはオープンのままで、スレッド上でOpenAI側の公式回答は確認できなかった。

## 結論

Codex CLIのデーモン問題は、自動アップデートが良いか悪いかの問題ではない。ブラウザは自動アップデートを行い、ほとんどのユーザーはそれをありがたく思っている。問題は、ユーザーが「コマンド」としてインストールしたツールが、ユーザーに尋ねることなく「サービス」へと性格を変えたことにある。その転換とともに、実行されるコードの正本はパッケージマネージャーからホームディレクトリ内のコピーへ移り、アップデートのタイミングはユーザーの視界の外へ出て、環境変数の継承という古い契約は壊れた。リリースノートは、そのすべてを一文で片付けた。

エージェントにできることが増えるほど、エージェントがユーザーのマシン上で何として存在しているのかについての透明性は重要になる。常駐はオプトインで、パッケージマネージャーによるインストールは正本として、無効化の方法は文書化され完結した形で。これは新しい要求ではなく、CLIという形式が数十年守ってきた契約を書き直したものに近い。動きの速い分野であればあるほど、ユーザーがインストールしたものこそが実行されるものだという単純な保証が、信頼の土台になる。
