# 自前のLLMプロキシなしで、エージェントが何をしているかをどう知るのか

> LLMトラフィックの可視性は経路を所有して初めて得られるものなのか、それともハーネスが出力するテレメトリで足りるのか?

## 導入

2026年10月18日、Jared Siegelが自身のブログに3分ほどで読める短い記事を投稿した。タイトルを穏当に訳せば「自前のLLMプロキシを動かしていないなら、いったい何が起きているかをどうやって知るのか」となる。原題には卑語が含まれており、文体もそれに見合って荒い。Hacker Newsには卑語を外したタイトルで投稿され、300ポイントを獲得し、トップレベルのコメントだけで42件が付いた。

記事の主張は単純である。我々の多くは、どこかのベンダーの有料サブスクリプションにつながったフロントエンド、つまりTUIであれGUIであれ音声通話であれ、何らかの窓口を通してモデルと対話している。自分のデータが入り、相手のデータが返ってくる。著者はそれを買うこと自体には今のところ不満はないと言う。問題は、ベンダーが「仕事が行われている証拠」として見せる使用量画面だ。著者はそれを注意をそらすための仕掛けと呼び、エンジニア向けの時系列トークン使用量統計ではなく、それでは何の判断も下せないと書く。

この記事が興味深いのは、結論よりもコメント欄のほうである。「プロキシを使え」という記事の下に、プロキシは単一障害点だという反論、OpenTelemetryで十分だという反論、そのOpenTelemetryはハーネスが見せたいものしか見せないという再反論、そしてそもそもサブスクリプションではプロキシを使う経済的な理由が弱いという指摘が順に積み重なった。本稿ではその議論を整理し、エージェントトラフィックのオブザーバビリティをどこで確保すべきかを検討する。

## 現象の分析:プロキシが見せるもの

まず原文が示した根拠をそのまま紹介する。著者は「OTelのエクスポートオプションがあるだろう」という反論をあらかじめ想定し、それも理由の一つにすぎないとして、その場で思いつくものとしてさらに5つを挙げる。

- 複数のプロバイダと複数のモデルを、自分が管理する単一のエンドポイントで扱える。
- どのキーが、どのクライアントで、いつ、どのモデルを呼び、ステータスが何だったかのログが残る。
- 仮想APIキーを使い、唯一のメインキーを業務、エージェント、ハーネスのあちこちにばらまかずに済む。
- 自分が管理するインフラである。
- すべてを設定し直すことなく、モデルとプロバイダを非常に素早く切り替えられる。

著者は特定のプロキシ製品を推薦しない。自分が管理する場所で自分で動かすこと、そして選んだ後は実際の必要に合わせて改造できることだけを強調する。彼は自分のプロキシを、より良い洞察のため、そしてカスタムMCPサーバーのエンドポイントのような追加機能のために改造したと明かしている。最も具体的な事例は一つだ。コーディングセッション中にキャッシュミスが見えたら、その原因を手作業で20秒以内に特定できるという。まだ自動化はしていないが、使っているプロキシにAPIがあるので自動化も可能だと付け加える。

この「キャッシュミス」の事例がなぜ重要なのかは、コメント欄で明らかになる。@viccisは、結局はキャッシュTTLにやられると書いた。Claudeのサブスクリプションでもサブエージェントは5分のTTLを持ち、それを知るまでは、サブエージェントが10分ほどかかるテストを待っている間に5時間の利用枠が大きく削られていたという。会社のAPI利用でも5分のTTLはまったく足りず、モニタリングしなければ会社の予算を燃やすことになるとした（直接の引用ではなく、コメントの要旨の要約）。この証言自体は検証できないが、「なぜキャッシュが切れたのか」という問いには、ベンダーダッシュボードの日別棒グラフでは答えられず、リクエスト単位の記録があって初めて答えられることは明らかである。

プロキシが何をしてくれるのかについての最も短い説明もコメント欄にある。@andaiは、LLMはJSON APIの上で動いているのだから、そのJSONを読めば何が起きているかがわかると書いた。他人のハーネスを使っているとモデルが実際に何を見ているのかがわからず苛立たしかったし、LLMではコンテキストがほぼすべてであることを考えればそれは問題だという。最も簡単な方法は、`OPENAI_API_URL` のような設定をlocalhostに変え、リクエストをそのまま転送しつつファイルにダンプする20行ほどのPythonスクリプトを立てることだとした。そして、そもそもそれが必要であるべきではないと付け加えた（直接の引用ではなく、コメントの要旨の要約）。

つまりプロキシが明らかにするものは、大きく4つに整理できる。第一に、実際に送信されたプロンプト全体、すなわちハーネスがユーザーの見えないところで付け加えたシステムプロンプトやツール定義まで含んだコンテキストである。@Havocは、Claude Codeが登場した頃にプロキシをいじってみたが実行可能な洞察は得られず、得たものといえばClaude Codeとその肥大化したシステムプロンプトを捨てたことくらいだと書いた（直接の引用ではなく、コメントの要旨の要約）。逆説的だが、その「捨てる」という判断こそがプロキシのもたらした判断である。第二に、リクエスト単位のトークンとキャッシュの状態だ。第三に、キーとクライアント単位の帰属、つまり誰が何を使ったかである。@redmalangは、コストをプロジェクト単位に帰属させるのに使っており、それが実際にかなり役立っていると答えた。第四に、シークレット管理だ。@hopppはLiteLLMのプロキシをサーバーに構築している最中だとして、仮想キーを発行できるのでプロバイダのAPIキーがサンドボックスに近づかないこと、すべてが見えること、ガードレールを掛けられることを挙げた。それなしではサンドボックス内のエージェント群をオーケストレーションできないという（直接の引用ではなく、コメントの要旨の要約）。

コメント欄には具体的なツール名も数多く挙がった。LiteLLM、GoModel、Bifrost、OpenRouter、TailscaleのAperture、mitmproxyが言及され、自作プロキシを紹介するコメントもいくつもあった。ただし、そのかなりの部分が開発者本人による宣伝だった点は覚えておく価値がある。LiteLLMのメンテナーを名乗る@ij23が複数のスレッドに返信し、GoModelを紹介した@verdvermは自らを熱心なファンと称した。原文の著者が自分が何を使っているかを明かさなかったことを@jFriedensreichが妙だと指摘したのも、同じ文脈で読める。

## 深層の分析:プロキシが背負うもの、そしてOpenTelemetryという代替

最も体系的な反論は@CharlieDigitalから出た。要旨はこうである。この用途にプロキシは不要であり、むしろ使うべきではない。プロキシは生産性の経路のど真ん中に置かれた単一障害点になるからだ。CodexとClaude CodeはOTelのトレースを出力し、OpenCodeやPiのような他のハーネスはプラグイン機構にフックしてOTelを自分で出力すればよい。コレクターを立てるか既存のコレクター基盤を使えば、ツール呼び出し、プロンプト全体、トークン使用量とコストがすべて入ってくる。そして決定的なのは、OTelの送信と収集はベストエフォートなので、トレースの一部を失っても生産性の損失はないという点だ。一方、障害を起こしたり過負荷になったりしたプロキシは、解決するまでチーム全体を足止めする（直接の引用ではなく、コメントの要旨の要約）。

この反論の事実部分は確認できる。Claude Codeの公式モニタリングドキュメントは、OpenTelemetryでメトリクスを時系列として、イベントをログプロトコルで、オプションで分散トレースを出力すると説明している。最小構成は環境変数をいくつか設定するだけだ。

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
```

ただしドキュメントを丁寧に読むと、「プロンプト全体が入ってくる」という話には条件が付く。ユーザープロンプト本文の記録（`OTEL_LOG_USER_PROMPTS`）とツール引数の記録（`OTEL_LOG_TOOL_DETAILS`）は、デフォルトで無効である。リクエストとレスポンスのMessages API JSONを丸ごとイベントとして出力する `OTEL_LOG_RAW_API_BODIES` もデフォルトで無効で、ドキュメントはその本文に会話履歴全体が含まれると明記している。このイベントはリクエストの試行ごとに1件出るので、リトライもそれぞれ記録される。トークンについては、`cache_read_tokens` と `cache_creation_tokens` が入力トークンとは別に報告される。言い換えれば、原文の著者がプロキシで行っているキャッシュミスの追跡は、少なくともClaude Codeに関してはOTelでも原理的に可能である。

ところが、この代替には構造的な限界がある。@ProjectBarksは、OTelに対する正当な批判は、ハーネスが見せようとするものしか見られないことではないかと問うた。彼はAI企業が出したコーディングツールが収集すべきでないデータを収集していた事例をリンクで挙げ、すべてのハーネスをサンドボックスで動かし、ネットワーク全体を記録すべきだと主張した（直接の引用ではなく、コメントの要旨の要約）。彼が挙げた個々の事例は本稿では検証していない。しかし論理そのものは事例とは無関係に成り立つ。自己申告型のテレメトリは観測対象が観測データを生成する構造であり、その信頼は観測対象次第である。@InsidiousWombatの一行コメントも同じ点を突いている。OTelは自分が何をしているかを見せるだけで、相手が自分のクエリで何をしているかは見せない、というものだ。

かといって、プロキシがこの問題を完全に解決するわけでもない。@jeenaは、ハーネスがオープンソースでない限りプロキシは役に立たず、別のサブドメインへこっそり通信するのは簡単だと指摘した（直接の引用ではなく、コメントの要旨の要約）。LLMプロキシが見るのはモデルAPIへのトラフィックだけである。ハーネスがテレメトリやその他のデータを別経路で送っていれば、それはプロキシの外側だ。したがって「信頼しないハーネス」を前提にすると、答えはプロキシではなく、@ProjectBarksの言うVM単位のネットワークロギングの側に行き着く。観測のレイヤーが3つに分かれるわけだ。ハーネスが自己申告するOTel、モデルAPIの経路を横取りするプロキシ、そしてホストのすべての送信を見るネットワーク層である。

予防と事後分析の違いもある。@pavelmelnichukは、OTelはプロキシが解決するものの4分の1にすぎないとして、エージェントが見当違いの深みにはまり、気づく前に100ドルを燃やしたらどうするのかと問うた。OTelは事故後の可視性を与えるが、プロキシはハードリミットを掛けて事故そのものを防ぐという。彼もまた、自分が作っているオープンソースのプロキシを紹介する文脈での発言だった。この論点は正確である。観測するだけの経路は、定義上何も止められない。予算上限、キーの失効、モデルの遮断といった統制は、リクエスト経路の上にあって初めて可能になる。そして単一障害点の問題については、@lokarが短く答えた。単一障害点にならないプロキシ構成も作れる、と。

最後にプロキシ自体のセキュリティがある。プロキシは定義上、すべてのプロバイダキーを握るボトルネックだ。@jubilantiはプロキシを使うべきだという点には同意しつつも、LiteLLMをはじめとするこの種のツールはバグだらけでバイブコーディングで作られたように感じられ、更新の速さを見ると脆弱性がないはずがないと書いた（直接の引用ではなく、コメントの要旨の要約）。他のユーザーはBifrostのほうが良いとしたが、ある人はそれが部分的にシェアウェアだと付け加えた。キーをばらまかないために設けた集約点が、選び方を誤ればキーをまとめて失う集約点になる。原文の「自分が管理するインフラ」という利点は、そのインフラを管理する能力と時間があるときにだけ利点である。

## 展望と示唆:サブスクリプションとAPI、そして何をどこに置くか

この議論で最も多くのコメントを集めたスレッドは、技術ではなく経済の話だった。@NeutralWantedは、Claude Maxの20倍プラン（月200ドル）を使い、毎週ほぼ週間上限まで使い切っているが、APIキーで試したところ2〜3日で200ドルに達したと書いた。だからAPIキーを使う人々がそのコストをどう正当化しているのかわからないという（直接の引用ではなく、コメントの要旨の要約）。@paid_dot_expertは月100ドルのサブスクリプションを使いつつ、1日のコストが300.82ドル、208.72ドルと集計された日々の表を貼った（何を基準にしたコストなのかはコメントに明記されていない）。@dcss_gardenerは、サブスクリプションは大きく補助されており、安いトークンは顧客獲得の手段だと見た。

これがオブザーバビリティとつながる理由は明確である。プロキシはAPIキーの経路で最も自然に機能する。@jakozaurは、API価格を払うならプロキシは良いが、サブスクリプションなら `~/.claude/projects/` のようなディレクトリのJSONLファイルを集めるほうが簡単で、サブエージェントの構造までプロキシより整理されていると書いた。ただし最大の価値は組織全体のエージェントセッションを集めたときに生まれ、そのときは認証情報を除去し、セキュリティに対処する必要があるとした（直接の引用ではなく、コメントの要旨の要約）。@skeritはサブスクリプションでもmitmproxyを経由してClaude Codeを動かし、すべての入出力を記録していると述べ、@kqrはサブスクリプションで他のハーネスを使うのは利用規約違反ではないのかと問うた。サブスクリプションとプロキシの関係は、技術的には可能だが規約上はグレーゾーンだという認識がコメント全体に漂っている。また何人かのユーザーは、150人を超える組織はエンタープライズ契約でAPI課金に移ることになると主張したが、この数字は本稿では確認できていない。

これらを踏まえて実務上の提言をまとめると次のようになる。これはコメントとドキュメントを根拠にした筆者の分析である。

第一に、個人がサブスクリプションで使う場合は、プロキシよりもローカルのセッションログ収集が先だ。すでにディスク上にあるJSONLを読むのが最もコストが低く、経路に何も挟まない。@vascoのように、これはすべてキャッシュヒットを手作業で眺めるための見栄であり、大きなプランを買えば済むという見方もあり、個人の規模では一理ある。

第二に、チームがAPIキーでエージェントを動かした瞬間に計算が変わる。キーの帰属、予算上限、仮想キーの発行は、リクエスト経路の上でしかできない。この場合プロキシは観測ツールではなく統制ツールであり、そうであれば単一障害点にならないよう冗長化し、キーを握るコンポーネントとしてセキュリティ更新に追随する運用負担を受け入れなければならない。

第三に、OTelとプロキシは二者択一ではない。ハーネスのOTelはツール呼び出しやサブエージェントといったハーネス内部の構造を見せ、プロキシは実際に境界を越えたバイトを見せる。二つの記録を突き合わせられれば、「ハーネスが報告したもの」と「実際に送ったもの」の差そのものがシグナルになる。プロンプト本文を記録した瞬間にそのログが機微情報の保管庫になることも併せて覚えておくべきだ。@lionkorは、EUではチャットに個人情報が含まれ得るとし、「ディスレクシアがあるのですみません」のような一文でさえ個人情報だと警告した。Claude Codeがプロンプトの記録をデフォルトで無効にしているのも、同じ理由によるものと読める。

第四に、ハーネスを信頼しないのであれば、観測のレイヤーをもう一段下げる必要がある。モデルAPIのプロキシは、別のサブドメインへの送信を見ることができない。

## 結論

原文は「自分で動かせ、そうすればわかる」の一文に要約できる。著者は、家では楽しく学びになるからそうしており、職場ではそうしなければ仕事をきちんとしていないことになるからそうしていると書いた。大規模言語モデルがどう動くのかを面接のホワイトボードに描けるほど理解することはないかもしれないが、推論をサービングしている間に計装しておくことはできる、というのである。

コメント欄が付け加えたのは、その一文の条件である。何を知りたいかによって観測点が変わる。自分のエージェントが何をしたかはハーネスのテレメトリで、実際に何が送信されたかはプロキシで、ハーネスがそれ以外に何をしているかはネットワーク層でしかわからない。そして統制したいのであれば、観測ではなく経路を所有しなければならない。

@hdraはスレッドの途中でこう問うた。人々はこれらのツールで、どんな判断を下すためにどんなデータを得ようとしているのか（直接の引用ではなく、コメントの要旨の要約）。プロキシを立てる前にまず答えるべきなのはこの問いである。あなたのチームは、先月エージェントが使ったトークンのうちキャッシュミスで失われた分を把握しているだろうか。把握していないなら、それを知るために必要なものは何で、それをどこに置くべきなのか。
