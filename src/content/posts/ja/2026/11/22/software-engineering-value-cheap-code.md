# コードが安くなった後のソフトウェアエンジニアリング — コミット240%とリリース30%のあいだ

> コードを書くコストがほぼゼロに近づいたのなら、ソフトウェアエンジニアリングの価値もゼロへ収束するのか。それとも価値は「書くこと」から「検証し、合意すること」へ居場所を移しただけなのか。

## 導入

2026年11月22日、Qiita に「コードを書くコストが下がった今、ソフトウェアエンジニアリングの価値はどこにあるのか」という記事が投稿された。筆者の figueiredoluiz 氏は日常的に AI を使って開発している実務者であり、記事の出発点は感想ではなく一つの数字である。NBER のワーキングペーパー（Demirer・Musolff・Yang、2026年9月改訂版）によれば、自律型コーディングエージェントの利用に伴うコミット数の増加は240%と推定される一方、リリース数の増加は30%にとどまった。

この差は、いま開発組織で起きていることを最も圧縮した形で示している。実装は確かに速くなった。しかしユーザーに届くソフトウェアの量は、それに比例して増えてはいない。この記事が興味深いのは、「AI がエンジニアを置き換える」と「AI は過大評価されている」という二つの陣営のスローガンのどちらにも与せず、複数の研究の測定対象を一つずつ揃えながら、ボトルネックがどこへ移動したのかを追跡している点である。本稿はその追跡をなぞりつつ、日本のエンジニアコミュニティから出たこの問題提起が、開発組織一般に対してどのような含意を持つのかを分析する。Qiita のいいね数は64と爆発的ではないが、脚注に8本の一次資料を並べた構成は、国内の AI 開発論の中でもかなり誠実な部類に入る。

## 何の生産性が上がったのか

まずデータを整理しよう。元記事が引用する研究は、一見すると互いに矛盾している。

第一に、Cui らが Management Science に発表した研究は、Microsoft、Accenture、Fortune 100 企業の開発者4,867人を対象とした3件のランダム化比較実験を分析した。AI コーディング支援を利用できる開発者は、完了タスク数が平均26.08%増加し、経験の浅い開発者ほど効果が大きかった。

第二に、METR が2025年に公開した実験は正反対の結果を出した。経験豊富なオープンソース開発者16人が慣れたリポジトリで246件のタスクに取り組んだところ、AI ツールを使った場合の作業時間は約19%長くなった。さらに興味深いのは、参加者が実験前には時間短縮を予想し、実験後も速くなったと感じていたことである。体感と計測が逆方向を指していたのだ。

元記事の筆者は、この二つを勝ち負けで比較しない。対象者、タスク、環境、指標が違い、評価対象のツールも現在の自律型エージェントとは世代が異なる。だからこそ「誰が、何を、どの指標で測ったのか」をまず揃えようと提案する。ごく当たり前の主張だが、AI 導入効果をめぐる社内議論の大半がまさにこの点でかみ合っていないことを考えれば、この当たり前は軽くない。

第三が核心となる NBER の研究である。50万人以上の GitHub 開発者と AI 利用データを用い、ツールの世代別に開発活動の変化を分析した。コミット数の累積的な増加効果は、補完型ツール（コード補完系）30%、対話型エージェント180%、自律型エージェント240%の順に大きくなる。ところが自律型エージェントの効果を後工程まで追うと、プロジェクト数は80%増えたのに対し、リリース数の増加は30%にすぎない。さらに四つのソフトウェアマーケットプレイスでは、新規アプリが増えたにもかかわらず、利用量の合計の増加は確認されなかった。

整理すると、ファネルはこうなる。コミット240% → プロジェクト80% → リリース30% → 実際の利用の増加は未確認。段階を下るほど効果は急激に縮む。著者らはこれを weak-link（最も弱い環）という考え方で説明する。最終的な成果が複数の工程に依存するなら、そのうち一つだけを高速化しても全体が比例して速くなるとは限らない。製造業の制約理論（TOC）と同じ構造であり、アムダールの法則にも似ている。並列化できない部分が全体速度の上限を決めるのである。

ただし元記事は、240%と30%の差をすべてレビューの遅延に帰するのは早計だと注意を促す。生成コストが下がれば、複数の案を試し、採用しない実装を破棄することも容易になる。捨てられたコミットも判断材料になり得る。この留保は重要である。コミットに対するリリースの比率が下がったという事実は「浪費」かもしれないし「安くなった探索」かもしれず、データだけでは両者を区別できない。

## ボトルネックはレビューと検証へ移った

生成が速くなるほど、評価する側の負荷は大きくなる。元記事はこれを三つの証拠で示す。

一つ目は、2026年11月に公開された Newman・Bird・Butler・Murphy-Hill の研究である。24人へのインタビューと2,590人へのアンケートを通じて、AI 支援がコードレビューに与える影響を調べた。参加者からは、PR の大型化や件数の増加に加え、作成者が変更を理解せず質問に答えられないケースが報告された。論文はこれを author stewardship（作成者として変更を理解し、責任を持つ姿勢）の欠如として扱う。レビュー担当者が作成者の代わりに意図や設計を調べ直すなら、実装で節約した時間はそのままレビューで消費される。コストが消えたのではなく、別の人の机へ移っただけである。アンケートでは、AI レビューツールの利用と、増えた PR への対応のしやすさとの間に相関が確認されなかった点も押さえておきたい。「AI が書いた PR は AI がレビューすればよい」という直感は、少なくともこのデータでは支持されていない。

二つ目は METR による SWE-bench の分析である。SWE-bench Verified のテストを通過した AI 生成パッチ296件を、3つのリポジトリのメンテナー4人に評価してもらったところ、自動評価はメンテナーが受け入れ可能と判断する割合を、調整後で平均約24ポイント高く見積もっていた。テストを通過したパッチのおよそ半数は受け入れ基準を満たしていなかったという推定である。元記事は、エージェントにレビュー指摘を受けて修正する機会がなかったことを理由に、これを AI の能力の限界とは断定しない。それでも一つの結論ははっきりしている。テストの合格と、プロジェクトが変更を受け入れることは別の判断である。テストはあらかじめ定義した条件を確認するだけで、その条件が十分かどうかまでは保証しない。

三つ目はオープンソースプロジェクト Mem0 の事例である。2026年8月11日に起票された Issue（#6893）には、オープンな PR が462件、新規 PR が週に約100件なのに対しマージは週30件程度、という状況が記されている。流入が処理能力の3倍を超えるキューは、いずれ際限なく長くなる。Mem0 は外部 PR の受け入れ方を変えた。原則としてメンテナーが accepted ラベルを付けた Issue に紐づく PR だけがレビュー対象となり、条件を満たさない PR は自動的にクローズされる（ドキュメントのみの変更などは例外）。AI によるコード生成は認めるが、投稿者は自分の変更とコードベースへの影響を AI の助けなしに説明できなければならない。

元記事がこの事例から引き出す洞察こそ、この記事の白眉である。変わったのは審査の厳しさではなく順序だ。**実装の妥当性を調べる前に、それが解くべき問題かどうかをまず合意する。** 生成コストが下がった時代には、レビュー担当者の時間を何に使うかも設計の対象になるということだ。

ここでトレードオフが鮮明になる。レビューを人の手に残せば、処理量は生成量に追いつかない。レビューを無条件に自動化すれば、「テストは通ったがマージできない」半分がそのまま流れ込む。両極端がいずれも失敗するなら、残る選択肢はレビューそのものを設計し直すことである。

## レビュー担当者を増やすより、レビューを設計し直す

その再設計の大規模な事例として、元記事は Meta の RADAR（Risk Aware Diff Auto Review）を挙げる。論文によれば、Meta では差分1件あたりの実質コード行数が前年比105.9%、開発者1人あたりの差分件数が51%増加し、著者らはこの増加の80%以上にエージェント型 AI が関係していると報告している。同時に、24時間以内にレビューが完了する割合は低下していた。

RADAR は変更の出所と種類を判定し、適用条件、静的検査、機械学習によるリスクスコア、LLM レビュー、決定的な検証処理を組み合わせる。一定の条件を満たす低リスクの変更は自動的に統合し、それ以外は別のレビュー経路に回す。53万5,000件以上の差分を評価して33万1,000件以上を統合し、レビュー所要時間の中央値は35%短縮された。RADAR で処理した変更は、リバート率と本番障害率がほかの変更より低かった。

元記事はここでも解釈を抑制している。最初から低リスクの変更を選別しているため、この結果だけで自動レビューが人間のレビューより安全だとは結論づけられない。選択バイアスが結果に組み込まれているという指摘である。参考にすべきは数値ではなく構造、つまり変更の種類に応じて検証の流れを分けたという点だ。

これを小さなチームに移すとどうなるか。元記事の例は実用的である。ドキュメント修正はリンク・形式のチェック中心に、通常のアプリケーション変更はテスト・静的解析と影響範囲に応じたレビューに、認証・権限・金額計算・破壊的な DB 変更にはより強い検証と責任者の判断を。これは RADAR が証明した普遍的なルールではなく、失敗したときの影響に応じて検証を配分する一例にすぎない、と元記事は付け加える。

展望を三つのシナリオに分けてみよう。

- **楽観シナリオ:** Mem0 型の「事前合意」と RADAR 型の「リスク比例の検証」が標準的な慣行になる。リリースの増加率が徐々にコミットの増加率に追いつき、エンジニアの時間は要件定義とリスク判断へ再配置される。
- **悲観シナリオ:** 組織がコミット数や PR 数といった上流の指標で AI 導入の成果を評価する。レビューキューは伸び続け、理解されていないコードが「テスト通過」を根拠に積み上がる。障害が起きても、誰もそのコードを説明できない。
- **現実的シナリオ:** 両者が混在する。大規模な組織は自動化されたリスク分類を備え、小さなチームやオープンソースは受け入れ方針を絞って流入を制御する。その間で「生成は安く、検証は高い」というコスト構造が固定化する。

実務者への示唆は明確である。着手前に受け入れ条件や守るべき制約を明確にしておくことが、事後の評価を助ける。条件の整理に AI を使っても構わないが、「何を満たせば受け入れるのか」という判断まで曖昧にすると、テストやレビューの結果も解釈しにくくなる。日本の現場で言えば、受け入れ基準を曖昧にしたまま「とりあえず PR を出す」文化が残っている組織ほど、このコスト構造の悪い面を強く受けることになるだろう。

## 結論

リード質問に戻ろう。コードが安くなれば、エンジニアリングの価値もゼロへ収束するのか。元記事が集めた証拠は、そうではないと語る。ただし「既存のプロセスを守れ」という意味でもない。効果の薄いレビューや形式的な承認は減らしてよい。Mem0 のように判断を上流へ移し、RADAR のようにリスクに合わせて検証を自動化すること自体がエンジニアリングの仕事である。元記事の言葉を借りれば、AI は実装を加速させる手段であり、エンジニアリングはその加速を信頼できる成果につなげるための営みである。

残る問いは、元記事の最後の節が投げかけている。自動化された判断が間違っていたとき、私たちは何を根拠にそれを見抜けるのか。Anthropic が2026年1月、主に経験の浅い開発者52人を対象に、新しい Python ライブラリ（Trio）の学習に AI 支援が与える影響を調べたところ、理解度テストの平均点は AI 利用グループが50%、非利用グループが67%だった。チャット型の支援で、短期的な学習の結果であるため長期的なスキル低下の証明ではなく、質問の仕方によって差が出たことも併せて報告されている。それでも方向は居心地が悪い。実装だけでなくテストやレビューまでエージェントに任せるほど、検証の基準を理解し、その結論を検討し直す力がより多く求められる。ところがその力は、任せるという行為そのものによって使われなくなっていく。

読者に残したい問いは二つである。あなたのチームは AI 導入の効果をコミットで測っているのか、リリースと実際の利用で測っているのか。そして、エージェントに任せた後でチームが使わなくなった知識や判断力は何であり、それをどう保つのか。240%と30%のあいだの差は、この二つの問いに対する各組織の答えが積み重なってできた数字である。
