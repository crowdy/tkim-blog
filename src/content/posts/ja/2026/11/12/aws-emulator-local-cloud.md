# AWS自らが作ったローカルAWS — エージェントが書いたエミュレーターはどこまで信頼できるか

> 人間が一行もレビューしていないエミュレーターが返す「成功」は、テストの証拠なのか。それとも、もう一つの検証対象なのか。

## 導入

2026年11月11日、AWSはWhat's NewでAWS Emulatorを発表した。ローカルのコンピューターやCIパイプラインでAWSアプリケーションをビルド・テストするためのツールで、告知は「with no deployments or AWS account required」と書く。既存のSDKやCLIの呼び出しをそのままエミュレーターに向ければ、デプロイもアカウントもなしにテストできるということだ。ソースはGitHubの`aws/aws-emulator`でCC0 1.0のパブリックドメイン献呈として公開され、エミュレーター自体に追加料金はかからない。翌日、このリポジトリはHacker Newsで992ポイント、コメント266件を集めた。

話題になったのは、機能よりも作り方だった。同日にAmazonの公式ブログに掲載されたSr. Principal EngineerのMatthew Goldbergの記事は、こう始まる。「Thousands of autonomous AI agents wrote every line of code in AWS Emulator.」そして一文を添える。「Our team hasn't written or reviewed any of the code.」世界最大のクラウド事業者が自社APIのローカル複製を出すにあたって、そのコードを人間は書いてもいないし読んでもいないと公言したのである。

同じ日、日本のQiitaには、このエミュレーター上で実際のCDKとTerraformのスタックを動かしてみた実測記事が投稿された。本稿はこの二つのソースを重ねて読む。AWSが語る忠実度（fidelity）と、実務者が測った挙動のギャップこそが、このツールをどこまで信頼してよいかを教えてくれるからだ。

## 現象の分析 — 何が公開され、どう作られたのか

READMEによれば、AWS Emulatorは「a local emulator of the AWS APIs」である。Rustで書かれており、LinuxではRPMかDebianパッケージをインストールして`aws-emulator`を実行し、WindowsとmacOSではDockerコンテナで動かす。ソースからビルドすると、自己署名証明書で`127.0.0.1:9297`にHTTPSを開く。Rustのテストにdev-dependencyとして組み込み、プロセス内で動かす組み込みモードもある。READMEは用途をビルド、テスト、CIに限定し、「Don't use it for production workloads or to test security」と釘を刺す。テレメトリーはデフォルトで有効で、フラグ、環境変数、設定ファイルで無効化できる。リポジトリは「This repository does not take PRs」と明記している。2026年11月16日の確認時点でリポジトリのスターは8.5千、オープンなイシューは445件、コミットは32,502件だった。

告知が掲げる約束は二つある。第一に、サポートする操作については、有効な呼び出しに対してAWSと同じ結果を返す。サポートしない操作には501を返す。第二に、インスタンスごとにポート、キー、メモリ上の状態が独立しているため、並列のエージェントやテストスイート、CIジョブが互いに干渉しない。状態はメモリ上にしかなく、止めれば消える。

制作の経緯はGoldbergの記事に書かれている。始まりは週末の実験だった。彼はKiroに三段階のプロンプトを与えた。AWS CLIでテストを書き、実際のAWSで通るまで直し、そのテストを通すメモリ内実装を作れ、というものである。Kiroは約15分でAmazon SQSの最初のバージョンを作り、週末のうちに残りを作った。もちろん穴だらけだった。彼は、エージェントがCコンパイラを作ったAnthropicの研究から着想を得たと述べている。仕様と参照実装がきちんと定義されていれば、エージェントは仕様に従うものを作れる、という論理だ。AWSにはSmithy APIモデルという仕様があり、実際のAWSという参照実装がある。

製品化にははるかに長い時間がかかった。エージェントは三つのチームに分かれる。テスト作成チームはSmithyモデルからシナリオを導き出して実際のAWSで検証し、その結果をAWSを呼ばずに再生できる形で保存する。イシュー検出チームはそのテストをエミュレーターに対して再生し、失敗をイシューとして登録し、原因が同じと思われる失敗をまとめる。修正チームはイシューを一つずつ引き受け、ビルド、レビュー、セキュリティ、忠実度を確認するマージゲートに修正を提出する。初期の骨組みは438個のAWS APIモデルのリクエストを処理し、忠実度テストは「tens of thousands」に達し、「hundreds of agents」が同時に働いて「thousands of issues fixed every day」だという。ただし、完全に実装されたサービスがいくつあるかは明かしていない。Goldbergはこう書く。「Without this merge gate, we wouldn't trust what our agents are building.」解決済みのイシューは`issues/things-that-now-work`、未解決のイシューは`issues/things-that-do-not-work`フォルダにファイルとして残る。

## 深層分析 — 忠実度スコアと実際の挙動のあいだ

Qiitaに実測記事を投稿したNana_777氏は、2026年11月12日、Windows 11とDockerの環境でエミュレーターv1.0.322を対象に、CDKスタックを10段階に分けてデプロイした。S3バケット、オンデマンドのDynamoDB、SQS+SNSのサブスクリプション、EventBridgeルール、Step Functions、`Code.fromAsset`でデプロイしたLambdaは、いずれもデプロイと動作に成功した。API GatewayとLambda、DynamoDBをつなぐPOST/GETの経路も、IAM権限付与の漏れで2回失敗した後に動作した。筆者は、Lambdaの権限不足が`AccessDeniedException`として検出されたことをむしろ有用だと評価している。

失敗も具体的である。インラインコードのLambda（`Code.fromInline`）はデプロイはできるが、呼び出すと`exports is not defined`で失敗した。CloudWatch AlarmはCloudFormation上では`CREATE_COMPLETE`なのに、`describe-alarms`に現れなかった。`LambdaRestApi`がデフォルトで作るプロキシ権限は、`statementId`が100文字の制限を超えて失敗した。Lambda Function URLの権限作成は`InvokedViaFunctionUrl`で失敗し、ロールバックされた。Terraform 1.16.2（AWS provider 6.73.0）では、S3とDynamoDBについて`init`、`apply`（13秒）、`destroy`（6秒）まで成功した。ところが`apply`直後の`plan`でDynamoDBの`on_demand_throughput`に`-1 -> null`の差分が出て、2回目の`apply`は`UpdateTable`の`ValidationException`で失敗した。27個のAPIを叩いてみると、4個（Athena ListWorkGroups、Translate、Comprehend、QuickSight）が501を返した。筆者は、残りの23個がエラーなく応答したからといってAWSと同じである証拠にはならない、と線を引いている。

この記事の価値は、その次の段階にある。筆者はリリースに添付された`scores.json.gz`をダウンロードし、サービスごとの合格率を自分で数え直した。公式のスコア表ではなく筆者の集計である、という但し書きが付く。skippedを除く42,857件のうち24,243件が合格、全体で56.6%だった。SQS 90%、S3 79%、DynamoDB 77%、IAM 71%、Lambda 46%、CloudFormation 16%である。興味深いのは、CloudFormationが16%なのに筆者の単純なスタックはすべてデプロイできたことだ。筆者は、CloudFormationのテストの多くがサービス横断やロールバック・更新を伴う複雑な構成を対象にしているためだろうと推測しつつ、内訳までは確認していないと述べている。結論はこうである。スコアが低いからといって自分の構成が動かないとは限らず、使うAPIの範囲で個別に試すのが確実だ。

筆者は公式リポジトリの`issues/`フォルダ（未解決6,544件、解決済み12,708件）も全文検索し、自分が見つけた差異6件と突き合わせた。`on_demand_throughput`の`-1`、`statementId`の100文字超過、CloudFormation経由のAlarmが見えない件は、すでに未解決イシューとして記録されていた。インラインのLambda、Function URL、同一スタック内での`prod`ステージ名の重複は該当するイシューが見つからず、未報告の可能性があるとしている。

この突き合わせが示すのは、エージェント式開発の強みと弱みが同じ場所にあるという事実である。強みは透明性だ。エージェントが見つけた差異が一件ずつファイルとして残っているため、外部の利用者が自分の観測を既存の記録と機械的に照合できる。弱みは「成功」の意味である。CloudFormationが`CREATE_COMPLETE`を報告するのに、リソースが実際には使えないAlarmの事例は、ステータスコードを信じるテストが空虚に通過しうることを意味する。筆者の勧告もまさにここにある。スタックが成功したことだけで判断せず、作成されたリソースをdescribeや実際の呼び出しで別途確かめよ、というものだ。

セキュリティの境界もはっきりさせておく必要がある。公式のセキュリティページは、IAMポリシー、権限境界、バケットポリシーのようなリソースベースのポリシー、KMSキーポリシー、アカウント間・リージョン間のアクセスを、このエミュレーターでテストしないよう求めている。HNで引用された同ページによれば、エミュレーターは自身のキーで署名されたリクエストを決して拒否せず、KMSキーポリシーやS3バケットポリシーを確認しない。権限エラーが検出されたというQiita筆者の観測と合わせて読むと、権限エラーが「検出されることもある」ことと、権限の検証に「使える」ことはまったく別の話である。

HNの反応は二つに分かれた。一方は市場構造に目を向けた。直接の引用ではなく要旨をまとめると、エージェントがなければAWS社内でこれほど多くのサービスをエミュレートしようと考える者はいなかっただろうし、これでfakecloudやLocalStackのようなツールの堀はなくなった、という反応である。同じ手法は競合がAWSのサービスを複製することも容易にし、クラウドが完全にコモディティ化したことを露わにする、という指摘もあった。Cloudflareのminiflareは人間が手作りしたものであり、「エージェントが作り、実サービスに対して検証する」という手法こそが本当に新しい点だ、という評価も出た。もう一方は信頼を問題にした。これが継続して保守される製品なのか一回限りの実験なのか不明だとしてTestcontainersのモジュールがあるFlociを使うというコメント、コードはここ1か月でほぼすべてClaudeで生成されたように見えるという主張、数か月様子を見てから判断するという反応が続いた（いずれも直接の引用ではなく、コメントの要旨の要約）。

## 展望と示唆 — どこに使い、どこに使わないか

実務上の結論は、Qiita筆者のまとめ表が最もよく要約している。向いている用途は、IaCの構文エラー、リソース間の参照、基本的な作成・削除、CIでのスモークテスト、SDKを使うアプリの結合テストである。向かない用途は、IAMやリソースポリシーの検証だ。ほかにもいくつか落とし穴がある。`AWS_ENDPOINT_URL`が空のシェルで実行すると、コマンドは実際のAWSに向かう。CDKが出力するURLは実際のAWSのホスト名なので、ブラウザでそのまま開いてはいけない。Lambdaの中から他のサービスを呼ぶなら、エンドポイント、認証情報、`NODE_EXTRA_CA_CERTS`を明示的に設定する必要がある。ポートマッピングを省略形で書くとエミュレーターがネットワーク全体に公開されるので、`127.0.0.1:9297:9297`のように明示すべきだ。エミュレーターは1日に複数回リリースされるため、リリース番号、検証日、使うサービスの忠実度スコアを記録しておけ、という勧告もある。

特に最初の落とし穴は強調に値する。エミュレーターに向いていたテストが、環境変数が一つ抜けた瞬間に、実アカウントの認証情報で実際のAWSに触れる。ローカルテストの安全性は、エミュレーターではなく、その環境変数が必ず設定されているという前提にかかっている。CIに組み込むなら、エンドポイントが空のときに失敗させる事前チェックが不可欠である。

今後の展開は三つに分けて考えられる。楽観的なシナリオでは、忠実度テストとマージゲートという仕組みが回り続けて合格率が着実に上がり、AWS EmulatorがローカルでのAWSテストの事実上の標準になる。サードパーティのエミュレーター市場は大きく縮む。悲観的なシナリオでは、「成功と報告するが実際には異なる」差異がテストを空虚に通過させる事例が積み重なり、人間がレビューしていないコードベースではその原因を追うことが難しくなる。現実的なシナリオはその中間である。単純なサービス（SQS、S3、DynamoDB）は早く実用的になり、CloudFormationのようにサービスを横断する領域は長く個別の確認が必要で、セキュリティの検証は引き続き実際のAWSの役割として残る。

## 結論

リード質問に戻ろう。人間がレビューしていないエミュレーターの「成功」は証拠なのか。現時点での答えは「限定された範囲の証拠」である。このエミュレーターの信頼は、コードレビューではなく、実際のAWSに対して検証された数万のテストとマージゲートから来ている。その信頼は、テストがカバーする範囲までしか成り立たない。サービスごとの合格率が16%から90%まで開いていること、そしてCloudFormationが成功を報告してもリソースが使えない場合があることは、その範囲の境界を示している。

だから、このツールを使うチームがやるべきことは明確だ。エミュレーターの成功応答をそのままテスト結果として扱わず、リソースを再取得するか実際に呼び出して確かめる段階をテストに組み込むこと。そして、エンドポイントの環境変数が空なら失敗するようにしておくことである。Qiitaの筆者が公式記録にない差異を3件見つけたやり方、つまり自分の観測を公開イシュー一覧と突き合わせるやり方は、こうしたツールに向き合う良い手本である。

あなたのCIは、いま「成功」という応答を受け取ったとき、追加で何を確かめているだろうか。エージェントが作るツールが増えるほど、この問いの重みは増していく。
