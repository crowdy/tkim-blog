# Outlook.comのDMARC拒否騒動 — 「誤り」で終わった4日間が残したシグナル

> Microsoftはロールバックし、小規模な送信者に新たな義務はないと述べた。では今回の騒動は過ぎ去った事故なのか。それとも、メール認証の「事実上の義務化」がすでに進行しているという予告編なのか。

## 導入

2026年11月5日、メールセキュリティ・リレー事業者のMailRouteは、自社の送信ログに奇妙なバウンスを見つけた。Microsoftのコンシューマー向けメールサービス（Outlook.com、Hotmail、Live、MSN）が、DMARCレコードのないドメインからのメールの一部を拒否し始めたのである。バウンスメッセージは次の通りだった。

```
550 5.7.1 Message rejected: Message lacks SPF/DKIM/DMARC Auth Records (AS9031519)
```

MailRouteは翌11月6日に「Outlook.comがDMARCのないドメインのメールを拒否している」という記事を公開し、Hacker Newsで552ポイント、コメント374件を集めた（objectID 50416158）。その時点でMicrosoftは何も発表していなかった。

結末はあっけない。MailRouteが11月10日に追記したアップデートによれば、Microsoftはこの現象をスパム対策ルールの更新によるものとし、そのルールがこのメールを「誤ってブロックしており、ロールバックした」と説明した。Microsoftが示した終了時刻は11月9日11:02 UTCである。MailRouteは、小規模な送信者にも新たなDMARC義務が生じたとする当初の解釈は誤りだったと訂正した。

しかし、この4日間をただの障害として片付けるのは難しい。実際にメールは拒否され、Outlook.comは拒否したメッセージを再送しない。その間に、病院の患者、住宅所有者、応募者、保護者、会員へ届くはずだったメールが消えた。そしてHNの議論は、この事故をきっかけに、はるかに古い不満を噴出させた。

## 本論1 — 何が起きたのか：4日間のタイムライン

MailRouteの記事をもとに事実関係を整理する。

- **11月5日**：拒否が始まる。初日のバウンスメッセージには括弧内のコードがなく、`550 5.7.1 Message rejected: Message lacks SPF/DKIM/DMARC Auth Records` とだけ表示された。
- **11月6日**：MailRouteが元記事を公開。Microsoftはまだ告知していなかった。
- **11月9日11:02 UTC**：Microsoftが示した拒否の終了時刻。
- **11月10日**：MailRouteがアップデートを追記し、記事を過去形に書き直す。

特徴は三つあった。第一に、拒否は**断続的**だった。同じドメインから送ったメールでも、一部は拒否され一部は配信された。第二に、**送信量と無関係**だった。大量送信者だけでなく、ごく普通の少量送信者も影響を受けた。第三に、Microsoftの告知によれば、一部の送信者は `550 5.7.23` というコードを受け取ったという。

この件を理解するには、背景となるルールを知る必要がある。2025年5月以降、Outlook.comは1日5,000通以上を送るドメインに対し、SPF、DKIM、DMARCの合格を求めてきた。これに違反すると `550 5.7.515 Access denied` が返る。GmailもDMARCを1日5,000通を基準に求めていることがHNのコメントで言及された。つまり、大量送信者への認証義務はすでに業界標準であり、今回の事故は、その線が誤って「すべての送信者」へ広がった4日間だったのである。

MailRouteの推奨は技術的にはシンプルだ。

1. DMARCレコードがあるか確認する。`dig +short TXT _dmarc.example.com` で確認できる。
2. なければ `_dmarc` に `v=DMARC1; p=none` のTXTレコードを追加する。受信側の扱いを変えずにレポートだけを求めるので「安全な出発点」である。
3. SPFまたはDKIMがFromアドレスのドメインとアラインしているか確認する。DMARCはFromドメインについてSPFかDKIMのどちらかが合格して初めて合格となるため、レコードを置くだけでは足りない。
4. 11月5日から9日の間にバウンスした重要なメールは再送する。
5. レコードはそのまま維持し、長期的には `p=reject` を目指す。

実務でよく見落とされる落とし穴が一つある。Microsoft 365は、カスタムDKIMを有効にするまで `onmicrosoft.com` で署名するが、この署名は自社ドメインのDMARCアライメントには数えられない。M365を使っているから認証は済んでいるはずだと思っている組織が、実はDMARC不合格の状態にある可能性があるということだ。日本の中小企業でもM365の導入は広く進んでいるが、DKIMの独自ドメイン設定まで済ませている組織がどれほどあるかは、改めて点検する価値がある。

なお、MailRouteはメールセキュリティサービスを販売する企業であり、その推奨が自社製品寄りになりうる点は割り引いて読む必要がある。ただし上の5項目は、特定の製品とは無関係な一般的な対処である。

## 本論2 — なぜ繰り返されるのか：連合型プロトコルと事実上の規制者

HNの議論は、DMARCそのものより「なぜMicrosoftはいつもこうなのか」へと流れた。多くのコメントがOutlook.comを、メールを届けるのが最も難しい大手事業者に挙げた。黙って捨てる（silent drop）こと、公開されていないブロックリスト、登録の理由を説明も解決もできないサポート窓口がその根拠だった（直接の引用ではなく、複数のコメントの不満の要約）。

ここに今回の事故の逆説が現れる。今回、Microsoftはメールを**バウンス**させた。だからこそMailRouteはログで発見でき、事故として認識されてロールバックされた。HNの複数のコメントは、250応答で受理しておきながら実際には届かない、あるいは数時間遅れて届く事例を描き、ワンタイム認証コードのような時間に敏感なメールを信頼できなくしていると指摘した。そして、むしろバウンスの方が黙って捨てるより透明だと主張した（直接の引用ではなく、スレッドの論旨の要約）。今回の4日間は、逆説的に「見える失敗」だったから直されたのである。

より根本的な論点は中央集権化だった。メールは誰でもサーバーを立てられる連合型プロトコルだが、少数の大手事業者が受信側市場の大部分を占めれば、彼らのフィルタ規則がそのままプロトコルの規則になる。HNでは、シェア50%あれば一社がルールを押し付けられるという主張や、分散化は緩和策であって治療ではないという主張が交わされた（直接の引用ではなく、コメントの論点の要約）。今回、Microsoftはいかなる標準化団体も経ず、事前告知もなく、誤って世界中の送信者に新しい要件を適用した。誤りだったからロールバックされたが、意図したものであれば止める手段はほとんどない。

反対側の論理もある。大手事業者の厳格なフィルタリングはスパムへの対応であり、その門番の役割は理解できるというものだ。1通あたりの少額課金や送信者のホワイトリストといった提案も出た。スパムフィルタの見逃し（false negative）の方が中央集権化よりましだという反論もあった。AIがスパム分類を安くし、分散型メールを可能にするという側と、もっともらしいスパムを生成するコストは分類するコストより安いという側も対立した（直接の引用ではなく、スレッドの論争の要約）。

DMARC義務化をめぐる意見も割れた。DMARCは古くからあり設定も簡単で、まともな送信者なら当然やるべきだという側と、予期していなかった小規模・少量の送信者には負担だという側である。ここでトレードオフを整理するとこうなる。DMARCの `p=none` レコード自体はTXT一行だが、**アライメント**を揃える作業はそうではない。マーケティングSaaS、決済通知、ヘルプデスク、社内システムなど、会社名でメールを送る経路が多い組織ほど、それぞれのSPF includeとDKIM署名を自社ドメインに合わせる作業は、実際の棚卸し作業になる。そして、まさにその棚卸しをしたことのない中小の組織が、今回の事故の被害者だった。

セルフホスティングをめぐる議論も同じ軸の上にあった。問題が起きるたびにフォーラムを漁る夜を過ごさなければ、信頼性の負担からセルフホスティングは非現実的だという側と、かつてないほど簡単になったので受信は自分のサーバーに置き、送信だけリレーを使えばよいという側に分かれた。Outlook宛てのメールだけをOutlookの送信サーバー経由で送るハイブリッドな回避策も出たが、どの受信者にその経路が必要かどう分かるのかという問いに、MXとSPFレコードが教えてくれるという答えが付いた（直接の引用ではなく、コメントのやり取りの要約）。

## 本論3 — 展望と示唆：義務はないが、デフォルトは変わった

Microsoftの公式見解は明確である。小規模な送信者に新たなDMARC要件はない。しかし実務者がこの一文を「何もしなくてよい」と読むのは危険だ。今回の事故が示したことは三つある。

第一に、**認証要件は告知なしに、誤ってでも変わりうる。** ルールの更新一つが、4日間にわたり送信量に関係なくメールを拒否した。次の更新が意図的なものであれば、ロールバックもないだろう。大手受信事業者のルールは、公開の協議ではなく内部のデプロイで変わる。

第二に、**バウンスを監視していなければ事故に気づけない。** MailRouteは自社ログで初日に異常を見つけた。多くの中小組織は、バウンスメールを誰も読まないメールボックスに送っている。Outlook.comが拒否したメッセージを再送しないことを考えれば、バウンス監視の不在は、顧客とのコミュニケーションの無音の喪失にほかならない。

第三に、**DMARCは「大量送信者の義務」から「すべての送信者のデフォルト」へ収斂しつつある。** GmailとOutlook.com（2025年5月から）が1日5,000通の基準を置いたのに続き、今回の事故はその線がいかに簡単に下がりうるかを示した。誤って下がり、また上がったが、方向そのものは変わっていない。

シナリオで整理すると次のようになる。

- **楽観**：今回の事故を機に、DMARCのなかった中小ドメインの多くが `p=none` だけでもレコードを追加し、アライメントの点検を通じて自社の送信経路を初めて把握する。ロールバックされた誤りが、結果として業界の衛生水準を引き上げる。
- **悲観**：公式見解だけを見て「義務ではない」と流した組織は、次のルール変更でまた被害を受ける。今度は意図的な変更なのでロールバックもない。その間も黙って捨てられるメールは続き、なぜ届かないのか誰も分からない。
- **現実**：大手受信事業者は、認証のないメールの評判スコアを徐々に下げ、明示的な拒否、迷惑メールフォルダへの振り分け、黙っての破棄が混在するグレーゾーンが広がる。認証を備えた送信者とそうでない送信者の到達率の差は、公式な要件とは無関係に開いていく。

実務のチェックリストは短い。会社名でメールを送るすべての経路を洗い出す。各経路がSPFかDKIMでFromドメインとアラインしているか確認する。M365を使っているならカスタムDKIMが有効かを見る。`p=none` から始めてレポートを受け取り、経路が整理できたら `quarantine`、`reject` へと上げる。バウンスメールは人が読む場所へ送る。

## 結論

リードの問いに戻ろう。今回の騒動は過ぎ去った事故なのか、予告編なのか。形式的には事故である。Microsoftはルールの誤りを認めてロールバックし、小規模な送信者に新たな義務はないと明言した。しかし実質的には予告編に近い。大量送信者への認証義務はすでに業界標準であり、その線をどこに引くかは受信事業者がいつでも、たとえ誤ってでも変えられることが、今回証明されたからである。

より大きな教訓は、メールというプロトコルの性格にかかわる。連合型プロトコルという設計と、少数の事業者が受信側を握る現実との隙間で、ルールはRFCではなく大手事業者のフィルタ更新によって作られる。HNの議論がDMARCよりもMicrosoftの不透明さと中央集権化について多くを語ったのはそのためだ。今回はバウンスという見える形で失敗したから直された。次の失敗が黙っての破棄という形をとったとき、私たちはそれに気づけるだろうか。

だから読者に残す問いは、技術的というより運用的なものになる。あなたの組織は、自社名でメールを送る経路をすべて把握しているか。バウンスメールは誰が読んでいるのか。そして11月5日から9日の間に、送ったメールのうち届かなかったものがあったかどうかを確かめる手段はあるだろうか。
