# Discord はなぜ Electron を捨てるのか — GPUI へ移った290MB の意味

> クロスプラットフォームのデスクトップアプリの事実上の標準だった Electron を、最も有名な Electron アプリの一つが去る。これは「Web 技術でデスクトップアプリを作る」という10年来の合意が崩れるシグナルなのか。それとも、資金と人材に恵まれた企業だけが享受できる贅沢なのか。

## 導入

2026年11月5日（日本時間）、Hacker News に The Verge の記事「Discord is ditching Electron and its new app uses less RAM」が投稿され、496ポイント、コメント439件を集めた。翌日には Windows Latest の Abhijith M B による続報「Every Windows 11 app should kill Electron, and Discord just showed why」が、再び483ポイント、コメント512件を集めた。二日続けて同じテーマがフロントページに上がったわけである。

Windows Latest の整理によれば、Discord は Electron クライアントを Rust で書かれた新クライアントに置き換えつつあり、その UI は Zed エディタの開発陣が作った GPU アクセラレーション対応の UI フレームワーク GPUI の上に載っている。多くの人が予想していた Tauri ではない。この記事の筆者が確認したタスクマネージャーの画面では、新クライアント（「Discord Phoenix」）はアカウント二つにログインした状態で290.2MB を使っていた。筆者の PC では、Electron 版はアイドル状態でも通常1〜2GB を消費するという。

Discord はこの10年、「Electron でも大規模アプリは作れる」ことを示す代表例だった。その会社が去るという事実こそ、このニュースの重みである。

## 何が変わるのか — Rust、GPUI、そしてシステム WebView

Windows Latest の記事が伝える事実関係を整理する。（The Verge の原文は本稿執筆時点で直接確認できなかったため、続報と HN の議論に基づく。）

**フレームワーク。** 新しいデスクトップクライアントは Rust で書かれ、GPUI で UI を描画する。GPUI は HTML を介さず GPU でインターフェースを直接描くフレームワークである。Discord は2018年から Rust を使っており、GPUI に独自のパッチを当てて使っていて、その一部をアップストリームに還元する可能性もあるという。

**Web 技術は必要な場所だけに。** YouTube の埋め込みと Activities はシステム WebView を使う。ブラウザ版は HTML レンダリングを維持しつつ、ロジックを WebAssembly に移す。モバイルでは iOS・Android ともに React Native をやめ、ネイティブのインターフェースを保ちながら、Rust を通じてデスクトップとアプリコードを共有する。つまり「Web を捨てる」のではなく、「アプリの中核ロジックを Rust 一式に集約し、画面はプラットフォームごとに最も軽い手段で描く」という設計である。

**性能の数字。** CTO の Stanislav Vishnevskiy が共有した15秒の動画では、Rust クライアントは Electron クライアントがロードを終える前にフレンドリストを表示した。Discord の社員は、どちらもコールドスタートだったと確認している。記事の筆者がコマ送りで確認したところ、Electron 版は約3秒間、空の暗いウィンドウを表示した後にヒントを出し、Rust 版のウィンドウは起動から1秒以内に現れた。Vishnevskiy は、クリックが即座に反応するように感じられ、もう元には戻れないと語っている。

**RAM。** 先の290.2MB は、アカウント二つを同時に立ち上げた状態の数値である。2025年12月にある Discord 社員は通常の使用量は1GB 未満だと述べており、筆者は290.2MB がその基準より約70%低いと計算する。ただし筆者自身、これは初期ビルドのスナップショットであり、Discord は同一条件のベンチマークを公表していないと断っている。

**その他。** 新クライアントはログイントークンをシステムのキーリング（Windows では資格情報マネージャー）に保存し、「Starting」画面なしにバックグラウンドで更新する。マーケティングディレクターは Linux でも動作すると述べ、クローズドテストが「まもなく」始まるとしたが、一般公開の日程は示されていない。エンジニアリング担当 VP の Mark Smith は、アクセシビリティとセキュリティは性能と同じくらい重要だと語っている。

**Electron 側での最後の努力。** 興味深いのは、Discord が2026年9月に Electron 42 へアップグレードした際、CPU 使用率の中央値を約17%削減した一方で、p50 のメモリは約4%増えたという点である。Electron の上で最適化を続けても、メモリ面では大きな改善が見込めない、という判断が今回の決定の背景にあると読める。

## なぜ今なのか — Electron の損益計算が変わった三つの理由

Electron は Chromium 一式と Node.js をアプリごとに丸ごと同梱する。HN のコメントがあらためて整理したように、このコストは最初から知られていた（直接の引用ではなく、コメント群の説明の要約）。それでも Electron が10年間標準であり続けたのは、そのコストを相殺する利得が大きかったからである。HN の議論では、Web カメラやメディアへのアクセスが必要なクロスプラットフォームアプリを一つ出すには、かつてはプラットフォームごとのネイティブライブラリや Qt のパッケージング技術、あるいは JVM が必要で、Electron がそのパッケージング問題を解決したのだという説明が出た（コメントの論旨の要約）。一つのチームで複数のプラットフォームをカバーでき、採用しやすい Web 開発者を雇えるというビジネス上の論理も大きかった。

では、何が変わったのか。三つの変化が重なっている。

**第一に、Rust ネイティブ UI の選択肢が実用段階に入った。** GPUI は Zed という実在の製品で検証されたフレームワークである。HN では Iced、Slint、Blitz/Dioxus、Sciter といった代替案も挙がった。ただし GPUI の成熟度については意見が割れた。GPUI は基本的に Zed のニーズに合わせて作られており、crates.io での公式リリースがなく、互換性を壊す変更もあるという懸念が出され、Discord のチームが GPUI のメンテナに接触したという話も言及された（コメントの論旨の要約）。Discord が独自パッチを当てたフォークを使っているという事実は、この未成熟さを自社のエンジニアリング資源で埋めているということでもある。

**第二に、メモリが再び高くなった。** Windows Latest の筆者は、RAM への関心が再燃した理由の一つとして AI 需要が押し上げた DRAM 価格を挙げ、Microsoft も Windows 11 の RAM 使用量を削減しつつあると指摘する。16GB のノート PC でブラウザ、IDE、ローカル LLM を同時に動かす時代に、チャットアプリ一つが1GB を占めるのは、もはや無視できるコストではない。

**第三に、AI が書き直しのコストを下げたという主張。** HN では、AI のおかげでプラットフォームごとのネイティブアプリを別々に保守するコストが十分安くなり、Electron のトレードオフはもはや成り立たないという意見と、五つのプラットフォームをテストするオーバーヘッドは依然として大きいという反論がぶつかった（コメントの論旨の要約）。同じ文脈で、人間が書いたコードベースを AI が書き直せば組織の理解が失われるのではないか、という問いも大きなスレッドになった。反論は、新しいコードベースに参加するのと変わらず、エンジニアはすでに抽象化に頼って仕事をしている、というものだった（コメントの論旨の要約）。

反対側の論点も無視できない。最も白熱したのは**アクセシビリティ**だった。スクリーンリーダー対応は妥協できない条件であり、Rust の UI ツールキットは歴史的にこの点が弱かったという指摘に対し、GPUI には AccessKit ベースのアクセシビリティ経路ができたが、UIA のようなネイティブ API に比べれば未成熟だという回答が続いた（コメントの論旨の要約）。弱視のユーザーの中には、Web スタックのおかげでアプリごとの拡大やカスタマイズが容易だったという人もいれば、逆に Discord は Electron 時代もアクセシビリティが悪く、改善に何年もかかったという指摘もあった（コメントの論旨の要約）。Electron がアクセシビリティをタダでくれなかったように、GPUI もタダではくれない。結局は、実際のスクリーンリーダーで継続的にテストする組織の意志が決める。

もう一つ、メモリの数字をめぐる冷静な見方もあった。290MB という数字は印象的だが、空の Chromium タブ一つでも同程度を使うという指摘が出た（コメントの論旨の要約）。比較対象が「最適化されていない Electron アプリ」であること、そして全機能が入った正式版ではないことを考えれば、最終的な数値は今より上がる可能性が高い。

## 他のアプリは追随できるのか — 実務者への示唆

Windows Latest の筆者は、Meta（WhatsApp）と Microsoft（Teams）は「言い訳が尽きつつある」と書く。筆者のテストでは、WebView2 ラッパーである WhatsApp は最大1.2GB、Teams はアイドル時に963MB を使った。筆者は、WinUI は Windows でしか動かないため Discord の選択肢にはなりにくく、GPUI はすでに Windows、macOS、Linux で動いていると指摘する。

しかし、これを「みんな Electron を捨てろ」と読むのは早計である。実務者が持ち帰るべき教訓は、もっと具体的だ。

第一に、**Discord の戦略は「共有コア＋薄い UI」である。** 今回の書き直しの核心は GPUI という特定のフレームワークではなく、デスクトップ、モバイル、Web のアプリロジックを Rust 一式に集約した構造にある。Web は WebAssembly で、モバイルはネイティブ UI で、デスクトップは GPUI で、同じコアを包む。この構造は、Discord が2018年から Rust に投資してきたからこそ可能だった。Rust のコアを持たない組織が「Electron を GPUI に」置き換えるのは、Discord がやったこととはまったく別の規模の仕事である。

第二に、**WebView を完全には捨てていない。** YouTube の埋め込みや Activities のように Web コンテンツが本質である部分には、システム WebView を使う。全部ネイティブか全部 Web かの二者択一ではなく、画面単位で最も安い手段を選ぶハイブリッドこそが現実的な解である。

第三に、**計測が先である。** Discord が、Electron 42 で CPU を17%減らしメモリが4%増えたというデータを持っていたという事実が重要だ。書き直しを決める前に、既存スタックで何が改善可能で何が構造的な限界なのかを数字で把握していたということである。

シナリオで見るとこうなる。**楽観的には**、Discord の成功が GPUI のエコシステムに資源と関心を呼び込み、アクセシビリティとドキュメントが成熟して、中堅企業でも使える選択肢になる。**悲観的には**、アクセシビリティや機能の同等性の問題でリリースが長引き、「大企業にしかできない書き直し」という認識が定着する。**現実的には**、巨大なユーザー基盤を持つ少数のアプリが同様の道をたどり、大多数の社内ツールや中小 SaaS のデスクトップアプリは Electron や Tauri のような WebView ベースに留まる。クローズドテストの結果が、その分かれ道を示すことになるだろう。

## 結論

冒頭の問いに答えるなら、これは Electron 時代の終わりというより、「Electron がデフォルトである時代」の終わりに近い。Electron が解決したパッケージングとクロスプラットフォームの問題はいまも実在し、ほとんどのチームにとって損益計算は依然として Electron 側に傾く。変わったのは計算式の変数である。メモリ価格が上がり、Rust ネイティブ UI が実戦投入できるまでに育ち、書き直しコストへの期待が AI によって変わった。

Discord の今回の決定が証明しているのは「Electron は悪い」ではなく、「十分に規模が大きく、共有コアに投資してきた組織にとっては、Electron のコストが利得を上回った」ということである。数億人が毎日立ち上げっぱなしにするアプリにとって、数百 MB はユーザーの RAM を合算すれば莫大な資源になる。

読者に残す問いはこうだ。あなたのデスクトップアプリで Electron が買ってくれているものは何で、その対価としてユーザーに請求しているものは何か。その二つの数字を、実際に計測したことはあるだろうか。
