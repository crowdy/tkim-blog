# uBlock Origin のユニバーサルXSS — 拡張機能がWebページ内にUIを描かねばならない構造の代償

> 最も信頼されるセキュリティ拡張が、最も広い攻撃面になった。これは uBlock Origin という一プロジェクトのバグなのか、それともブラウザ拡張が自らのUIを敵対的なWebページの中に描かざるを得ないプラットフォーム構造が生んだ必然なのか。

## 導入

2026年11月15日、セキュリティ研究者の Smitty van Bodegom は自身のブログ iter.ca に「Universal XSS in uBlock Origin from website-driven element picker」という記事を公開した。翌日、この記事は Hacker News で619ポイント、コメント183件を集めた。内容は単純だが、居心地が悪い。Firefox 版 uBlock Origin（MV2版）において、悪意あるWebサイトがユーザーにワンクリックさせるだけで、拡張機能に任意の「trusted filter」を追加させることができた。trusted filter はページに JavaScript を注入できるため、結果として攻撃者は**他の任意のサイト**のコンテキストで任意のコードを実行できた。いわゆるユニバーサルXSS（UXSS）である。

GitHub のセキュリティアドバイザリ GHSA-cmqw-9r2w-6wv2 によれば、脆弱性は11月1日にメールで報告され、影響範囲は1.75.2以下、修正版は1.75.4（11月3日公開）である。メンテナの gorhill は2日でパッチを出し、その後1.76.0（11月8日）で追加の防御を入れた。対応速度だけを見れば模範的だ。それでもこの件が大きな議論を呼んだのは、攻撃経路が uBO 固有のミスというより、ほぼすべての「ページと相互作用する拡張機能」が共有する設計パターンを突いていたからである。さらに研究者は、脆弱性発見の大部分を GPT 系モデルが担ったと明かしており、これもコメント欄の論点の一つになった。

## 攻撃の解剖 — 4段階で積み上げたUXSS

原文が説明する攻撃は4段階である。①要素ピッカー（element picker）のURLを突き止める。②そのURLを透明な（opacity 0）iframe として自分のページに埋め込む。③ピッカーをメッセージで操作し、望むフィルタを入れさせる。④見えない「Create」ボタンの上にユーザーのクリックが落ちるよう iframe を配置する。

**第1段階：拡張UUIDの漏洩。** Firefox では拡張機能の内部リソースが `moz-extension://<UUID>/...` という形のURLを持ち、このUUIDはインストールごとにランダムである。したがって本来、Webページはピッカーの URL を推測できない。ところが uBO のデフォルトフィルタリスト（uAssets）には `no-fetch-if` スクリプトレットを使うルールがあった。広告サーバーへの `fetch` リクエストを横取りし、同じAPIを持つが何もしないダミースクリプト（web accessible resource、WAR）を代わりに返すルールである。問題は、このダミースクリプトを取得する際、スクリプトレット内部で `XMLHttpRequest` を使って `moz-extension://<UUID>/web_accessible_resources/...` をリクエストする点にあった。スクリプトレットはページのコンテキストで動くため、ページが事前に `XMLHttpRequest.prototype.open` を上書きしておけば、そのURL、つまりUUIDをそのまま覗き見ることができた。攻撃者は `fetch('/adsbygoogle.js')` の一行でそのルールを発動させるだけでよかった。

**第2・第3段階：ピッカーの遠隔操作。** UUIDが分かれば、ピッカーのUIである `epicker-ui.html` を iframe で開ける。このページは拡張のバックグラウンドスクリプトと通信し、フィルタを追加する権限を持つ。攻撃者は `MessageChannel` を作り、`postMessage({ what: 'epickerStart' }, '*', [port])` でピッカーを起動し、ダイアログ表示のメッセージとともにフィルタ内容を送る。正規のピッカーはスクリプトレットフィルタの入力を禁じているが、ネットワークリクエストの種類（例：`image`）を入れる `opt` フィールドが `$image` のようにフィルタ末尾へそのまま付け足される点を突き、そこに改行とともに `google.com##+js(trusted-rpnt, script, ...)` のような**任意の trusted フィルタ**を差し込めた。ピッカー経由で追加したフィルタは（再コンパイルまでは）常に信頼済みとして扱われるため、スクリプト注入の権限までついてくる。

**第4段階：クリックジャッキング。** 研究者はこの部分を実際には実装していないと明言している。しかし透明な iframe をボタンの上に重ねるのは古典的なクリックジャッキングの手口であり、「ページのどこかを一度クリックさせる」のは難しくない。

核心的な欠陥についての原文の診断は明確である。**ピッカーは攻撃者のメッセージを受け付けるべきではなかった。** 修正はまさにその点を正面から扱った。アドバイザリに記録されたコミットの順序はこうだ。1.75.2 で「スクリプトレットが汚染されうるXHRメソッドを使わないように」修正し、1.75.4 で「検証済みの秘密トークンがある場合にのみピッカーを起動する」ようにし、1.76.0 で「作成直前のフィルタを検証する」措置と「war: 関連フィルタを当面禁止する」措置を加えた。興味深いのは、1.75.2 のパッチ直後に研究者が再びメールを送り、`XMLHttpRequest.prototype` に `responseText` の getter を定義する方法でなおUUIDを取得できると指摘したくだりである。つまり最初のパッチは「UUIDを隠す」方向だったが、それだけでは防げないと分かると、「ピッカーは誰の指示を受けるのか」という信頼境界の側へ防御線が移ったのである。

原文によれば、MV3 版である uBO Lite にも、類似するがより軽微な問題があった。HN のあるコメントは、確認の目安として uBlock Origin 1.75.4、uBO Lite 2026.1110.1816 以上であるべきだと整理している（直接の引用ではなく、コメント内容の要約）。

## 構造的な原因 — 拡張のUIはなぜ敵の領土に描かれるのか

この件を「uBO が postMessage の送信元検証を怠った」とまとめるのは、半分しか正しくない。HN の議論で最も生産的だった流れは、**そもそもなぜ拡張機能のUIがWebページの中に存在しなければならないのか**という問いだった。

あるコメントは、拡張機能がページ上の要素と連携しなければならないとき（要素ピッカーやパスワードマネージャーの自動入力候補のように）、自分のインターフェースをWebサイトのDOMの中に入れるしかない現実がずっと気がかりだったと書いた。パスワードマネージャーの場合、ページが新たに生成されるDOM要素を監視すれば、ユーザーがどんなアカウントを持っているかまで漏れかねないという（共感コメントの空気の要約）。これに対し、「まともなパスワードマネージャーは closed shadow DOM やサンドボックス化された iframe にUIを入れるので、そのような漏洩はない」という反論も付いた。どちらにも一理ある。隔離の仕組みは存在するが、それを正しく使うのは各拡張開発者の責任であり、今回の uBO のように iframe で隔離していても、**その iframe を誰が開き、誰が話しかけるのか**を検証しなければ、隔離は無力になる。

最も示唆に富んでいたのは、ブラウザ開発に関わっていたと思われる利用者の回想だった。拡張機能専用のオーバーレイAPIをもっと強く推進しなかったことを悔やんでいるという内容で、本来は Top Layer をベースにするつもりだったが、拡張機能がサブツリーを取り付けられるプリミティブなAPIは結局追加されなかったという。彼は、開発者ツールがWebページの上に描画するために別の「オーバーレイページ」を使い、一部プラットフォームの日付ピッカーも同じ仕組みを使っているが、この機構が拡張機能に公開されたことはないと付け加えた（要約であり直接の引用ではない。当該利用者の経歴は確認していない）。別のコメントは、旧版 uBO（Pale Moon および Quantum 以前の Firefox 向け）が `chrome://ublock0` というブラウザクローム領域にピッカーを置いており、ページに注入される iframe は `about:blank` のドキュメントだったと指摘した。つまり XUL 時代には拡張のUIがページの外、ブラウザ側の信頼領域に住むことができたが、WebExtensions への移行でその選択肢が狭まったのである。

ここでトレードオフが鮮明になる。WebExtensions と Chrome の Manifest V3 は「拡張機能が力を持ちすぎている」という問題意識から権限を絞ってきた。あるコメントが整理したように、その問題意識の多くは脆弱性よりも、**無料の拡張機能を買収して閲覧履歴を抜き取ったり広告を注入したりする収益化パターン**に向けられていた（要約）。ところが権限を絞る方向の設計は、拡張機能に「ページの外に描ける安全なキャンバス」を与えることには相対的に無頓着だった。結果として拡張機能は依然としてページを書き換える強力な権限を持ちながら、その書き換えのUIは敵対的でありうるページと同じ空間に置かれることになった。「問題はページを書き換えることではなく、ページが書き換える側と相互作用できることだ」というコメントが核心を突いている（要約）。

第2の構造的原因は、**インストールごとのランダムUUIDをセキュリティ境界として使う慣行**である。Firefox が拡張UUIDをインストールごとにランダム生成するのは、フィンガープリント防止とリソース保護のための仕組みだが、今回の件は、その値がスクリプトレットのような「ページのコンテキストで動く拡張コード」を通じてあまりに簡単に漏れうることを示した。あるコメントは、最近別の事例で Firefox の拡張UUIDが追跡識別子として使われうると知ったばかりなのに、今度は `fetch('/adsbygoogle.js')` 一つで uBO のUUIDが露出するとは「皮肉な大惨事」だと書いた（要約）。追跡を防ぐために入れた拡張が、追跡識別子を漏らす構造である。原文も、UUIDが漏れる経路はこのフィルタルール一つではないと明言している。秘密値の秘匿に頼る防御は、その秘密がページのコンテキストに触れた瞬間、すでに半ば崩れている。

第3の論点は発見の方法である。研究者は「UXSS がフィルタ注入から出てきそうだ」という勘を持ってモデルに調べさせ、モデルが問題を見つけ、自分はそれを検証したと記している。記事の文章は自分で書き、PoC のコードは大部分を Claude が書いたとも明かした。HN では、この開示の仕方自体を歓迎する反応（人間が書いた文章だというシグナルがもっと増えてほしい）と、この程度に単純な脆弱性にAIの助けが必要だったことに失望するという反応が分かれた（いずれも要約）。どちらにせよ事実は一つだ。「勘」と「検証」は人間が、退屈なコードパスの追跡はモデルが担うという分業が、すでに実戦の脆弱性研究で回っているということである。

## 展望と示唆 — 何を直し、何に耐えるのか

実務者への第1の示唆は単純だ。**拡張機能のUIがページとメッセージをやり取りするなら、そのチャネルは外部APIとまったく同じに扱わなければならない。** `postMessage` の受信側は送信者を検証すべきであり、「iframe の中にあるから安全だ」という前提は、その iframe を誰が開いたのか分からない限り成り立たない。uBO が採用した秘密トークン方式、つまり正規経路のコンテンツスクリプトだけが知る値をピッカー起動メッセージに要求するやり方は、WebアプリケーションのCSRFトークンと同じ発想である。新しくもない解法が遅れて適用されたわけで、だからこそ他の拡張機能にも同じ穴がある蓋然性が高いと見るべきだろう［仮定］。

第2は**入力正規化の落とし穴**である。`opt` フィールドに改行を入れてフィルタ1行を2行にする手口は、「ユーザーが選べる値は数個しかない」というUIレベルの前提が、メッセージレベルでは何の意味も持たないことを示している。1.76.0 の「作成直前のフィルタ検証」は、その前提をデータの側で立て直す措置だ。画面が制限することと、サーバー（ここではバックグラウンドスクリプト）が強制することは違うという、Webセキュリティの最も古い教訓が、拡張機能でもそのまま繰り返された。

シナリオを分けてみよう。**楽観シナリオ**では、今回の件がブラウザベンダーに拡張機能専用のオーバーレイ・UI面を再び議論させる。要素ピッカーやパスワード候補がページDOMではなくブラウザが所有するレイヤーに描かれれば、クリックジャッキングとメッセージ偽装という二つの軸が一度に消える。**悲観シナリオ**では、今回の件が「拡張機能は危険だ」という物語を強化し、権限をさらに削る方向にだけ政策が動く。そうなれば広告ブロックのような機能はさらに弱まり、ユーザーは効果の落ちるDNSブロックやブラウザ内蔵機能に頼ることになる。HN でも「DNSベースのブロックで十分だ」という主張に対し、主要な動画・SNSサイトの広告はブラウザレベルのブロックなしには防げないという反論が続いた（要約）。**現実的シナリオ**はその中間である。個々の拡張機能がトークン検証、shadow DOM、入力検証を一つずつ採用して穴を塞ぎ、プラットフォーム次元の解決はゆっくりとやってくる。

ユーザーの観点では、自動アップデートが事実上唯一の防衛線だった点も押さえておくべきだ。脆弱なバージョンに対して2日で修正版が AMO に上がったが、HN には Android 版 Firefox では拡張機能を手動でアップデートする手段が乏しいという不満も見られた（要約）。アドバイザリとブログの公開が修正から約2週間後に行われたのは、自動アップデートが行き渡る時間を稼ぐ、責任ある開示の典型である。

## 結論

リード質問に戻ろう。これは uBO のバグなのか、構造の必然なのか。答えは「両方であり、比重は構造の側が大きい」である。直接的な欠陥、すなわちピッカーが送信元を確認せずにメッセージを受け取ったこと、`opt` フィールドを検証しなかったことは確かに uBO の責任であり、すでに修正された。しかしその欠陥が致命的になりえたのは、最も強力な権限を持つ拡張機能のUIが、最も信頼できない空間であるWebページの中に描かれなければならず、そのUIを守る手段がインストールごとのランダム文字列という薄い秘密だったからである。

ブラウザ拡張は、Web上でユーザーの側に立つほぼ唯一のレイヤーである。広告ブロッカー、パスワードマネージャー、アクセシビリティツールはすべてここに住んでいる。そのレイヤーをより安全にする方法が「権限をさらに奪うこと」だけなら、私たちはセキュリティを得る代わりにユーザー主権を失う。逆に、拡張機能にページの外の安全な描画場所を与える方向なら、同じ権限を保ったまま攻撃面を減らせる。

読者に残したい問いはこうだ。あなたが使い、あるいは作っている拡張機能のうち、ページの中にUIを描き、そのUIがページと言葉を交わしているものはいくつあるか。そしてその会話の相手が本当に自分の思っている相手なのか、誰が保証しているのか。
