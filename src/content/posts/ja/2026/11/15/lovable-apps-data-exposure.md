# Lovable 製アプリ2万4千サイトがログインなしでデータを送っていた — バイブコーディングのセキュリティ責任は誰にあるのか

> AI アプリビルダーで作られたサービスから大量の個人情報がログインなしで読めたとしたら、それはセキュリティを知らない個々のビルダーのミスなのか。それとも、非開発者に「アプリを作ってあげる」と約束したプラットフォームのデフォルト設定の問題なのか。

## 導入

2026年11月15日（KST）、Hacker News で一日中上位に居続けた投稿の一つが、ハンブルクのアプリケーションセキュリティ・ソフトウェアコンサルティング会社 Crissy Field GmbH が公開した調査レポートだった。HN のタイトルは "Lovable apps expose passport details and more than 200K private messages"（item 50499017）で、980点、370件超のコメントを集めた。

Lovable は、自然言語で説明すると Web アプリを生成してくれる AI アプリビルダーである。非開発者でも数回のプロンプトでデータベース付きのサービスを立ち上げられることが中核的な価値で、多くのプロジェクトがバックエンドに Supabase を使っている。Crissy Field はドイツの経済紙 Handelsblatt と協力してこのエコシステムを調査し、Handelsblatt の Lina Knees 記者が2026年11月2日付の記事で最初の結果を報じた。同社のページは、その記事より新しい数値を掲載していると述べている。

レポートの要約文は単純である。「個人情報と機密情報がログインなしでアクセス可能だった」。この一文が「いくつかのアプリ」ではなく「数千サイト」の単位で成り立っていたことが、今回の件の重さだ。本稿では、数字が実際に何を語っているのか、そして HN で交わされた責任論と研究倫理の論争が、バイブコーディング時代のセキュリティ構造について何を浮かび上がらせるのかを分析する。あらかじめ断っておくと、レポートのページはこの会社のコンサルティングサービスを宣伝する媒体でもある。数値を読む際にはこの文脈を念頭に置く必要がある。

## 本論1 — 数字が語ることと語らないこと

まず調査範囲を見よう。Crissy Field は Web アーカイブである Common Crawl のデータから、2025年12月から2026年9月の間に作られた Lovable プロジェクト159,041件を特定した。そのうち Supabase を使う34,545件が分析対象となった。そして24,664の Web サイトが、ログインや操作なしにページを開くだけで Supabase のデータベースレコードをブラウザに送っていた。

調査はさらに一歩踏み込んだ。同じ API キーで読み取り専用の追加リクエストを送ると、7,403サイト（24,664の30%）にまたがる10,560テーブルでメールアドレスが見つかった。ただし著者らは、これは確定した漏えい率ではなく、サンプルにも代表性はないと明記している。メールアドレスが公開の連絡先やテストデータである可能性があり、逆にメールアドレスを含まないレコードはこの方法では捕捉できなかった、という限界も併記されている。データは部分的にしか取得しておらず、さらなるアクセスを助長しないようアクセスの詳細は公開していない。

レポートが事例として挙げた露出データは次のとおりである。

- ドイツのあるライフスタイルフォーラム：8万件超のプロフィール（氏名、メールアドレス、生年月日、性別）と20万件を超えるチャットメッセージ
- イベント主催者とレストラン：チケット・飲食販売に関する数万件のレコード（メールアドレス、電話番号、住所、決済情報、チケットコード）
- あるサービス事業者：パスポート番号、有効期限、国籍を含む身分証明書情報のレコード1,000件超
- ある不動産管理会社：賃借人・オーナー・パートナーに関する社内メールを AI で要約した内容
- その他、数万件の契約書と請求書、個人の写真アルバム、社内の WhatsApp のやり取り、ニュースレター・ウェイティングリスト・サポートのデータ、ある事業者が顧客に送った28万件のメール

注目すべきは、レポートが根本原因を特定していない点である。ページは Supabase の行レベルセキュリティ（Row Level Security、RLS）や公開キー（anon key）といった具体的な設定ミスを明示せず、「データベース連携は繰り返されるパターンに従う」としてアクセス制御のミスを懸念するにとどまる。また Lovable 自体のデータベース機能は調査していないと述べている。

原因を明示的に指摘したのは、むしろ HN の議論だった。Lovable のセキュリティ責任者を名乗る参加者が、根本原因は不十分な RLS だったと答え、同社が提供する無料スキャナーと計画中の自動修正（auto-fix）機能に触れた（直接の引用ではなく、その回答の要旨の要約）。この構造を噛み砕くとこうなる。Supabase をブラウザから直接呼ぶアプリは、公開キーをクライアントのコードに載せる。このキーはもともと公開されても構わないよう設計されており、実際の保護はテーブルごとに設定された RLS ポリシーが担う。RLS が空だったり緩すぎたりすれば、公開キーを持つ誰でも、つまりページを開いたすべての人がテーブルを読めてしまう。

## 本論2 — 責任は誰に：ビルダー、プラットフォーム、そして Supabase

HN の議論の第一の軸は責任の所在だった。多くの参加者が、個々のビルダーだけでなくプラットフォームが責任を負うべきだと主張した。根拠は、Lovable が自らを非開発者向けのツールとして売り込んでいる点にある。セキュリティを知らない人に「アプリを作ってあげる」と売ったのなら、セキュリティの欠けたアプリが出てくるのはユーザーのミスではなく製品の欠陥だ、という論理である（直接の引用ではなく、プラットフォーム責任論側のコメントに共通する論旨の要約）。

Lovable 側の回答、すなわち無料スキャナーと予定されている自動修正機能に対しても批判が出た。ユーザーがセキュリティ修正を「後回し」にできてはならず、会社がより安全なデフォルトを強制すべきだという批判である（直接の引用ではなく、批判側コメントの空気の要約）。この批判は核心を突いている。スキャナーは警告を出すが、警告を読んで判断するのは結局ユーザーだ。そしてそのユーザーは、定義上その警告を判断する知識を持っていない可能性が高い人なのである。

第二の軸は Supabase の設計の問題だった。一部の参加者は、RLS は設定を誤りやすく推論も難しいため、リスクの一部は設計そのものにあると見た。反対側は、失敗は Supabase 自体ではなく Lovable が Supabase を統合したやり方にあると反論した。クライアント側からのデータベースクエリには基本的なレート制限すらない、という指摘も出た（直接の引用ではなく、その論争の双方の論旨の要約）。

この論争を構造的に見ると、問題は「責任境界の消失」である。伝統的な3層 Web アプリでは、サーバーのコードがデータベースの前に立ってアクセス制御を行う。そのサーバーコードを書いた開発者がアクセス制御の責任者だ。Supabase のような BaaS（Backend as a Service）はサーバーコードをなくし、その役割をデータベースのポリシー（RLS）に移す。開発速度は上がるが、アクセス制御は「コードを書けば生まれるもの」から「ポリシーを別途書かなければ生まれないもの」に変わる。書かなければ、何も防がない。

そこに AI アプリビルダーがもう一層を重ねる。いまやコードもポリシーも人間が書かない。AI が機能要件を満たすコードを生成するとき、「ログインしたユーザーだけが自分の行を読める」という非機能要件は、プロンプトに明示されない限り簡単に抜け落ちる。アプリはきちんと動く。データが画面に出て、フォームが保存される。その「きちんと動く」ことこそが問題を覆い隠す。すべての人にデータを見せるアプリは、ビルダー自身のブラウザでも完璧に動くからだ。

レポートの結論部の文章もこの点を狙っている。「使いやすい開発プラットフォームだからといって、アクセス権限に対する専門家のレビューが不要になるわけではない」。そして「自動チェックは専門的なセキュリティ評価の代わりにはならない」。ただし前述のとおり、これがセキュリティコンサルティング会社の結論だという点も合わせて読むべきだろう。

## 本論3 — 研究倫理の論争と実務への示唆

HN の議論で大きな比重を占めた第三の軸は、意外にも研究倫理だった。研究者は脆弱性を証明するために、どこまでデータにアクセスしてよいのか。一方は、範囲の確認は必要であり、著者は結果の最初のページだけを確認するなど一線を守ったと見た。もう一方は、欠陥の証明に必要な最小限を超えてデータを取得するのは重大な問題であり、事前に契約や法的な確認を得るべきだと主張した。著者は弁護士が関与していたと述べたが、その弁護士が誰の利益を代表していたのかをめぐって意見が割れた（直接の引用ではなく、その論争の流れの要約）。Aaron Swartz の事件や、セキュリティ研究者に不利だったドイツの控訴審判決といった先例も持ち出された。

開示と透明性については、企業がこの種の問題の規模を過小に伝えるだろうという懐疑が多かった。著者は、Lovable には数週間前に通知し、発見内容を共有したこと、Lovable は延期を求めたり法的措置をちらつかせたりしなかったことを明かした。多くの参加者は、公表こそが実際の修正を強いる唯一の信頼できる方法だと主張した（直接の引用ではなく、該当コメントの要旨の要約）。議論のかなりの部分が参加者同士の個人攻撃的な応酬に流れたことも記録しておくべきだろう。

この件が実務者に与える示唆は三つある。

第一に、BaaS を使うアプリなら「匿名ユーザーとしてページを開いたとき、ネットワークタブで何がやり取りされているか」を最初に確認すべきである。今回の調査が2万4千超のサイトを選り分けた基準はまさにそれ、つまりログインなしでページを読み込むだけでレコードが届くかどうかだった。この点検はシークレットウィンドウ一つでできる。攻撃者が最初に使う方法も同じだ。

第二に、AI が生成したアプリのセキュリティレビューは「コードレビュー」ではなく「ポリシーレビュー」でなければならない。生成されたフロントエンドのコードを読んでも、RLS の空白は見えない。テーブルごとに誰が何を読み書きできるかを表にし、実際のポリシーと突き合わせる必要がある。レポートが勧めるのも、実際の顧客・業務データを扱う前にアクセス権限、インターフェース、ユーザーアカウント間の分離をレビューし、大きな変更の後に繰り返すことである。

第三に、プラットフォーム事業者にとって「安全なデフォルト」の定義が変わりつつある。警告を出すことと、危険な状態を許さないことは別物だ。テーブルを作るときに RLS をデフォルトで有効にし、ポリシーがなければ誰も読めないようにする「閉じたデフォルト」は、アプリが最初は動かないという不便を生む。しかしその不便こそ、ユーザーが「アクセス制御」という概念に初めて向き合う地点でもある。

日本の文脈で言えば、現場部門がノーコード・ローコードツールで作った業務アプリが情報システム部門の管理外で顧客データを扱う「シャドー IT」の問題は以前からあった。AI アプリビルダーはその作成コストをさらに下げ、Web に公開されるまでの距離を縮めた。社内ガイドラインの対象に「AI で生成したアプリ」を明示的に含めているかどうかは、今すぐ確認する価値がある。

展望は分かれる。楽観的には、今回の件が AI アプリビルダーの間で閉じたデフォルトとデプロイ前の強制チェックを標準にするきっかけになる。悲観的には、スキャナーと警告バナーが増えるだけで終わり、非開発者のビルダーは警告を無視するすべを覚える。現実的には規制が変数となる。欧州では個人情報を大量に露出させたサービスの運営者は GDPR 上の責任を負うが、その運営者が「プロンプトでアプリを作った個人事業者」であるとき、責任がプラットフォームまで遡るかどうかはまだ開かれた問いである。

## 結論

リード質問に戻ろう。これは個々のビルダーのミスなのか、プラットフォームのデフォルトの問題なのか。法的・形式的には個々のアプリの運営者が責任を負う。しかし2万4千超のサイトという規模は、個人の不注意で説明できる水準を超えている。同じミスが数千回繰り返されるなら、それは個人ではなく経路の問題である。非開発者が AI にアプリを注文し、AI が機能を作り、BaaS がサーバーなしでデータを送り出す、その経路のどこにも「アクセス制御を設計する人」がいなかった。

バイブコーディングはアプリを作るコストを劇的に下げた。しかしセキュリティのコストは下げられず、むしろそのコストを払わなければならないという事実そのものを見えなくした。アプリが「きちんと動く」ことと「安全である」ことの間の隔たりは、プロの開発者には常識だが、Lovable の主要顧客にとっては存在すら知らない隔たりである。

読者に残す問いはこうだ。あなたの組織で、誰かが AI アプリビルダーで作った「ちょっとした社内ツール」が顧客データを扱ってはいないだろうか。もしそうなら、今日シークレットウィンドウでそのアプリを開き、ネットワークタブを確認してみてほしい。今回の調査の出発点は、まさにその一回の確認だったのである。
