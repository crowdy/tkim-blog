# Project Zero の「Full 90→30」 — AI 時代の脆弱性開示期限は誰のためにあるのか

> 報告から一定日数が過ぎれば無条件で開示するという Project Zero の新ポリシーは、AI が早めた攻撃速度への合理的な対応なのか。それとも、パッチ対応力の乏しい側にコストを転嫁する圧力なのか。

## 導入

2026年11月13日、Google の脆弱性研究チーム Project Zero が開示ポリシーの改定を発表した。執筆者は Natalie Silvanovich である。2021年から運用してきた「90 + 30」ポリシー、すなわちベンダーに90日の修正期限を与え、パッチが配布されたらさらに30日の「ソーク（soak）期間」を置いてから詳細を公開する方式を廃止した。新ポリシーは名前からして単純だ。「脆弱性はベンダーへの報告から X 日後に開示される」。そしてその X は時間とともに縮んでいく。

スケジュールは3段階である。発表当日の2026年11月13日から「Full 90」（報告から90日で開示）、2027年2月2日から「Full 60」、2028年1月3日から「Full 30」。修正されたかどうかは、もはや開示時期を決める要素ではない。猶予期間（grace period）やバリアント（variant）ポリシーといった特例も大半が廃止された。

Hacker News でこの発表（item 50496051）は300点超、190件ほどのコメントを集めた。同じ日の HN トップページは FAA の全米グラウンドストップや Nvidia 関連のニュースが占めていたが、セキュリティ実務者の間ではこのポリシー変更のほうが長く語られるだろう。理由は単純である。Project Zero の期限は事実上、業界標準の基準点として機能してきた。その基準点が3分の1に縮むという宣言だからだ。

## 本論1 — 何が変わったのか：「修正の有無」から「報告時点」へ

旧ポリシーと新ポリシーの違いは、期限の長さよりも基準点にある。「90 + 30」では、開示時期はベンダーの行動に連動していた。90日以内に修正すれば、パッチ配布後さらに30日待って公開し、その30日はユーザーがパッチを適用する時間として正当化されていた。つまり開示の時計は「修正」という出来事によってリセットされていた。

新ポリシーは時計を「報告」という一つの出来事に固定する。報告から90日（のちに60日、30日）が過ぎれば、直っていようがいまいが開示する。Project Zero は修正状況を引き続き追跡し、修正されていない場合はその旨を伝えるとしているが、それが開示時期を変えることはない。発表文の言葉どおり「パッチのソーク期間はもはや意味がない（Patch soak time is no longer meaningful）」。

例外は四つに整理されている。実際に悪用されている（in the wild）脆弱性は、Google のアプリケーションセキュリティ脆弱性開示ポリシーに従って別途扱う。すでに他の経路で公開されている場合は、Project Zero の裁量で詳細を公開しうる。ベンダーが要請すれば公開する。ハードウェアの脆弱性については、Spectre・Meltdown のときのように例外を認めたことがあり、今後もありうる。

発表文が挙げる根拠は三つの系統に分かれる。

第一に、AI を使った攻撃の加速である。LLM は脆弱性の発見とエクスプロイトの両方を速め、悪意ある主体を含む複数の当事者が同じバグを見つける可能性を高める。旧来の期限ではもはや十分でない、という主張だ。

第二に、パッチギャップである。攻撃者はいまやパッチを素早くリバースエンジニアリングできるため、パッチ後30日のソーク期間は実質的な保護をほとんど提供せず、かえって「まだ秘密が守られている」という錯覚を生みかねない。だから縮めるべきは開示までの時間ではなく、ユーザーがパッチを適用するまでの時間だという。

第三に、件数である。発表文に引用された唯一の数値はここに出てくる。「かつて年に数件しか見つからなかった対象で、いまは週に数件の脆弱性を見つけている」。報告件数がこれだけ増えれば、案件ごとに期限を交渉する方式は回らない。

段階的なスケジュールにも理由が付されている。ベンダーからのフィードバックによれば、急激な変更はベンダーがプロセスを改善している最中に未修正のバグを露出させかねず、チームが深刻度ではなく期限の緊急度で報告を優先順位付けするようになり、ベンダーが期限超過をそもそも受け入れてしまう結果にもつながりうる。そこで「挑戦的だが現実的な」段階的縮小を選んだという。

興味深いのは深刻度に関する立場である。発表文は、深刻度が開示時期を左右すべきではないと言う。深刻度はユーザーへの影響を示すだけで、攻撃者がそのバグを見つける可能性とは無関係だという論理だ。同時に、Project Zero のレポートは高い品質基準を守っており、ベンダーが低品質な報告を別扱いするのは合理的でありうるとも付け加えている。AI が生成した低品質なバグ報告がオープンソースプロジェクトを悩ませている状況を意識した但し書きと読める。

## 本論2 — なぜ今なのか：発見コストの崩壊と交渉モデルの限界

このポリシー変更の構造的な背景は「発見コスト」の崩壊である。脆弱性開示期限という制度は、もともと一つの前提の上に成り立っていた。熟練した研究者が長い時間をかけなければ見つからないバグなら、見つけた者が沈黙している間に別の誰かが同じバグを見つける確率は低い。その確率が低いからこそ、ベンダーに90日、あるいはそれ以上を与えてもユーザーにとって大きなリスクにはならなかった。

LLM がこの前提を揺るがした、というのが Project Zero の診断である。同じツールを使う複数の研究者と攻撃者が同じコードベースを走査すれば、「独立した再発見」の確率は上がる。開示を遅らせる期間は、もはや「誰も知らない期間」ではなく「善意の発見者だけが黙っている期間」になる。この論理を受け入れるなら、期限短縮はベンダーを締め付ける手段というより、沈黙のコストを計算し直した結果である。

HN の議論でも、この論点が支持の中心だった。AI ツールが発見を速めるので攻撃者も似たような窓の中で同じバグを見つけうる、ならば期限を縮めるのが正しい、という意見が複数の方向から出ていた（直接の引用ではなく、支持派コメントに共通する論旨の要約）。逆に、深いバグを見つける作業は依然として熟練した人間に依存しており、パッチを作りレビューするには人間の監督が必要だという反論もあった（直接の引用ではなく、懐疑的なコメントの空気の要約）。

二つ目の構造的要因は、交渉モデルの限界である。「90 + 30」時代の開示スケジュールは、事実上の案件別交渉だった。ベンダーが「このバグは構造的なのでもっと時間が要る」と言えば猶予を協議し、バリアントが見つかれば元のバグとまとめるか別に数えるかを協議した。年間の報告件数が少なければ、この交渉は品質を高めた。しかし週に数件報告する状況では、案件別交渉は研究チームの時間を交渉に費やさせる。固定期限は交渉コストをゼロにする制度的な単純化である。

もちろん単純化にはコストが伴う。HN で最も目立った反論は、30日という最終目標が非現実的だというものだった。修正の難しいバグやメンテナの少ないプロジェクトでは、パッチそのものよりテストと段階的なロールアウトのほうが時間がかかり、急いだ修正が新たな障害を引き起こすリスクがあるという指摘である（直接の引用ではなく、反対派コメントの論旨の要約）。

Android エコシステムの観点も出た。端末メーカーや通信キャリアを経由するパッチ配布は遅く、とりわけ低価格端末やカスタム ROM のベンダーはさらに遅い。短い期限は主に自社のアップデートパイプラインを持つ側に有利で、予算の乏しいベンダーは相変わらず遅いだろうという見方だ。EU のサイバーレジリエンス法（Cyber Resilience Act）のような規制に言及する声もあったが、執行が強力かどうかは疑わしいという反応が添えられていた（直接の引用ではなく、該当するコメントの流れの要約）。

オープンソースのメンテナの声も大きかった。ボランティアの燃え尽き、さばききれない報告の洪水が語られ、オープンソースに依存する企業が保守に資金を出すかパッチを貢献すべきだという提案が続いた。一方で、バグは開示時期と関係なくすでに存在しているのだから、本当の問いはユーザーがどう緩和できるかだという反論もあった（直接の引用ではなく、メンテナ関連コメントの空気の要約）。

動機をめぐる論争もあった。このポリシーはベンダーへの強要だという批判に対し、Project Zero は公表されたスケジュールに従ってバグを報告しているだけだという反論が出され、Google 自身の案件も期限を超過した例があるので Google が特別扱いされているわけではない、という指摘もあった（直接の引用ではなく、その論争の双方の論旨の要約）。

## 本論3 — 展望と示唆：「開示期限」ではなく「適用時間」の競争へ

このポリシーの最も重要な含意は、競争の軸が変わる点にある。Project Zero は、縮めるべきは「ユーザーがパッチを適用するまでの時間」だと明言した。開示期限が短くなれば、ベンダーは修正の速さだけでなく、配布・適用の速さまで競争対象にしなければならない。自動アップデート、段階的ロールアウトの自動化、ロールバック可能性といった配布インフラが、セキュリティ能力の一部になる。

実務者への示唆は三つの層に分かれる。

ベンダー（とりわけ Project Zero の報告対象になりうる規模のプロダクト組織）には、2028年の「Full 30」を基準に逆算したプロセス設計が必要になる。報告受付から再現、修正、テスト、配布までを30日以内に終えられるか。その経路で最も長い区間はどこか。多くの組織で、その区間は修正ではなくリリースサイクルと QA である。段階的スケジュールは、この構造改善に約14か月の時間を与えたことになる。

オープンソースのメンテナにとっては、さらに難しい問題である。期限が短くなるほど、「報告→開示」の間に使えるボランティアの時間は減る。現実的な対応は、セキュリティ窓口と対応手順をあらかじめ文書化し、依存している企業にセキュリティ対応の支援を明示的に求めることだ。今回の HN の議論で繰り返された「依存する企業がお金を出すべきだ」という主張は、期限短縮が進むほど、より具体的な要求に変わっていく可能性が高い。

ユーザー組織（企業の情報システム部門、SRE）にとっては、パッチ適用のリードタイムがそのまま露出時間になる。ソーク期間がなくなれば、パッチが出た日と詳細が公開される日の間隔は縮まりうる。「パッチは次の定期メンテナンスで」という運用は、ますます危うくなる。月次・四半期のメンテナンス窓を前提に変更管理を組んでいる日本企業の情報システム部門にとっては、変更承認プロセスそのものの見直しを迫られる話でもある。

シナリオを描いてみよう。楽観的には、大手ベンダーが Project Zero の期限を業界基準として受け入れ配布パイプラインを改善し、他の研究組織も同様の期限を採用して、エコシステム全体のパッチ速度が上がる。悲観的には、大手ベンダーは適応するが小規模ベンダーとオープンソースプロジェクトは期限を守れず、未修正脆弱性の開示が増え、その被害はアップデートの遅い低価格端末のユーザーに集中する。現実的には両者が混ざるだろう。Project Zero の報告対象は主に大手ベンダーなので直接の衝撃は限定的だが、基準点が変われば、他の研究者やバグバウンティプログラムの期待値もゆっくりとそれに追随していく。

## 結論

リード質問に戻ろう。このポリシーは AI が早めた攻撃速度への合理的な対応なのか、パッチ対応力の乏しい側にコストを転嫁する圧力なのか。正直な答えは「両方」である。発見コストが崩壊した世界では沈黙の期間は善意の発見者だけが黙っている期間になる、という Project Zero の診断には説得力がある。同時に、その対応コストは均等には配分されない。自動アップデートのパイプラインを持つ大手ベンダーにとって30日は挑戦だが、ボランティアが保守するライブラリにとっては存続の問題になりうる。

Project Zero が段階的なスケジュールを選び、その理由としてベンダーのフィードバックを公開したことは、この非対称性を認識しているというシグナルである。しかし、ポリシーが解決できるのは「いつ開示するか」までだ。「その間のコストを誰が払うか」はポリシーの外側の問題、すなわちオープンソースへの資金支援と規制、そして各組織のパッチ運用が引き受けるべき領分として残る。

読者に残す問いはこうだ。あなたの組織が明日外部から報告を受けたら、30日以内に修正・検証・配布を終えられるだろうか。そして、あなたが依存しているオープンソースライブラリのメンテナはそれができるだろうか。2028年1月までに残された時間は、この二つの問いに答えるのに決して長くはない。
