# Windows 11 はあなたがどのコーディングエージェントを使うかを数えている — 1ビットのテレメトリの重さ

> プロンプトも、ソースコードも、使用時間も送らない。送るのは「このマシンで Codex が実行された」という1ビットだけだ。これはOSベンダーのありふれた製品診断なのか、それとも競合ツールのシェアをOSレベルで測る市場情報の収集なのか。

## 導入

2026年11月16日、セキュリティ研究者の Xusheng Li は「Windows 11 Is Collecting Data on Which Coding Agents and Developer Tools You Use」という記事を公開した。この記事は Hacker News で738ポイント、コメント625件を記録した。出発点は些細なものだった。研究者がAIに最新の Windows バイナリから文書化されていない機能を探させたところ、その手がかりの一つが目を引いた。`codex.exe`、`claude.exe`、`copilot.exe`、`cursor.exe` といったコーディングエージェントの実行ファイル名が、`python.exe`、`dotnet.exe`、`gcc.exe`、`code.exe` のようなおなじみの開発ツール名と並んで、Windows のシステムDLLの中に埋め込まれていたのである。

DLLの名前は `MissionControlAggregator.dll`。研究者はこれらの文字列の参照をたどり、これが実際に動作している Windows コンポーネントであり、どのコーディングエージェントと開発ツールが使われたかを記録し、ローカルに保存し、Windows の診断基盤に報告していることを確認した。そして「オプション」の診断データをオフにしていなければ、そしてそれはデフォルトでオンになっているのだが、このデータは Microsoft にアップロードされる。この記事が興味深いのは暴露の規模のせいではない。収集される情報はごく小さい。興味深いのは**何を数えているか**である。2026年の開発ツール市場で最も激しい戦場であるコーディングエージェントを、その市場のプレイヤーの一人でもあるOSベンダーが、OSレベルで数えているのだ。

## リバースエンジニアリングが示したこと — 実行ファイル名からアップロードキューまで

原文の調査は「文字列がある」で止まらず、データがマシンを離れるかどうかまで段階的に追跡している点で模範的である。

**何と比較しているのか。** Binary Ninja でDLLを開くと、実行ファイル名が比較演算に使われている。CLIエージェントのスロットは4つで、`copilot.exe`、`claude.exe`、`codex.exe`、`agy.exe` をチェックし、WSL経路では拡張子なしの名前で同じ比較を行う。デスクトップエージェントのスロットは5つで、`github.exe`、`claude.exe`、`codex.exe`、`cursor.exe`、`antigravity.exe` である。この比較を囲む機能フラグの名前は、露骨にも `CLICodingAgentUsage`（feature ID 62580080）だ。リストはAIエージェントにとどまらない。`node.exe`、`python.exe`、`dotnet.exe`、`gcc.exe`、`clang.exe`、`gdb.exe`、`javac.exe`、`devenv.exe`、`code.exe` などが、より広い「開発ツールカテゴリ」にまとめられている。一部は発行元まで確認する。Node.js のスロットは Node.js Foundation、Python は Python Software Foundation、.NET と Visual Studio は Microsoft Corporation を期待する。一方、GCC・Clang が属するコンパイラ／デバッガグループには、この経路では発行元チェックがない。

**どこから情報を得るのか。** このコンポーネントはプロセスを自らスキャンしない。既存の Windows イベントを購読している。Windows プログラムについては `KernelProcess.AppStateChangeSummary` と `Win32kTraceLogging.AppInteractivitySummary` を、WSL については `Microsoft.Windows.Lxss.Manager.Exec` を受け取り、実行ファイル名をマッチャーに渡す。つまりWSL内のLinuxプログラムだけでなく、通常の Windows 上の `codex.exe` もCLIエージェントのチェックに引っかかる。元のイベントには実行時間、フォーカス時間、操作カウンタ、リソース使用量まで含まれているが、研究者の見立てでは、このコンポーネントはそれらの詳細を捨て、**どのエージェントが観測されたかのビットマップだけ**を残している。

**どう報告するのか。** マッチが成立すると状態スロットが立ち、その後 `ReportCohorts<12,4,5>` がそれをビットセットに変換し、`Segments.SubCohorts` という ETW（Event Tracing for Windows）イベントとして出力する。12・4・5 はそれぞれ、広いツールカテゴリ12個、CLIエージェント4個、デスクトップエージェント5個に対応する。状態は `C:\ProgramData\Microsoft\Diagnosis\AggregatorStorage\` 以下に保存され、報告はおおむね1日単位である。

**本当に動いているのか。** 研究者は、Windows 11 ARM64 のVM（ビルド 26200.9974）で `CLICodingAgentUsage` がすでにサービス実験として有効になっており、自分で手動有効化した覚えはないと述べている。テレメトリサービス DiagTrack が自動起動で動いており、その子プロセス `AggregatorHost.exe` が問題のDLLをロードしていた。実験は単純だった。`cmd.exe` を `codex.exe` という名前でコピーして実行すると、名前だけで Codex と認識されてCLIスロット2が立ち、報告ウィンドウを強制的に進めると `CliAgentSubCohorts: 4`、すなわち `1 << 2` の Codex ビットを含むイベントが出力された。`gcc.exe` としてコピーした実験では開発ツールスロット3が立った。こちらは GCC 個別のビットではなく、コンパイラ／デバッガのカテゴリビットである。

**本当に送られているのか。** ETWイベント自体はローカル診断にもよく使われるため、それだけで「送信される」とは言えない。研究者は `Diagtrack-Listener` セッションが入力側（KernelProcess）と出力側（MissionControlAggregator）の両プロバイダを購読していることを確認し、DiagTrack の `EventStore.db` のアップロードキューから実際に当該イベントを見つけ出した。イベントには `"isRequired": false` が付いていた。つまり必須ではないオプションの診断データに分類されている。そして地域を米国に設定した最新の公式ISOによる Windows 11 Home のクリーンインストールで、プライバシー設定に触れる前の時点で診断データのトグルはすでに「Include Optional」になっており、`AllowTelemetry` の値は3だった。研究者の結論はこうだ。インストール中かその後にオフにしていなければ、あなたのコーディングエージェント使用データはアップロードされている。

## なぜ論争になるのか — データの大きさと意味の大きさは違う

擁護の論理は簡単に組み立てられる。プロンプトもソースもなく、実行時間すら捨てている。数ビットの集計は、Windows がどの開発者のために何を最適化するかを判断するための、ありふれた製品診断かもしれない。オプションのデータであり、設定でオフにできる。研究者自身も、レポートの中にプロンプトやソースコードは見つからなかったと明記している。それでも彼は「どのエージェントと開発ツールを使っているかを収集すること自体が、すでに重大なプライバシー上の含意を持つ」と付け加える。この二つの間の溝こそが、今回の論争の核心である。

第一に、**何を数えるかは、誰が数えるかと切り離せない。** スロットのリストには Microsoft 系（`copilot.exe`、`github.exe`、`code.exe`）と競合製品（`claude.exe`、`codex.exe`、`cursor.exe`、`antigravity.exe`）が並んでいる。コーディングエージェント市場において、Microsoft は審判ではなく選手だ。膨大な数の Windows 端末から、1日単位で「Copilot だけを使った端末」「Claude と Cursor を併用した端末」の比率が分かるとすれば、それはどの市場調査会社も持たないシェアのパネルデータである。このデータが実際にどう使われているかは原文にも分からず、私たちにも分からない［仮定：競合分析目的だという証拠はない］。ただ、データの**潜在的な用途**が非対称であるという事実は残る。

第二に、**「オプション」がデフォルトでオンになっている**という点だ。原文が確認したのは米国地域設定のクリーンインストール1件である。他の地域、特にGDPRが適用されるEUでデフォルト値が同じかどうかは確認されていない［仮定］。オプションという言葉は本来、ユーザーが選んだという意味であるべきだが、ほとんどのユーザーはインストール画面をそのまま進める。デフォルト値こそが事実上のポリシーであることは、UX設計者なら誰でも知っている。

第三に、**サンプルの偏り**という技術的な反論もある。HN のあるコメントは、テレメトリを有効にしている Windows ユーザーからだけプログラミングツールの使用を測れば、ひどく歪んだデータになるだろうと指摘し、それに「テレメトリを切るほど賢い人は、そもそも彼らが関心を持つ市場セグメントではない」という冷笑的な返信が付いた（いずれも直接の引用ではなく、コメント内容の要約）。この冗談には真実がある。デフォルトを変えない大多数のユーザーの分布を知ることのほうが、製品判断にはより有用なのだ。

HN の議論の多くは予想通りに流れた。「なぜこれがニュースなのか、Windows はもともとそうだ」という諦め、そして Linux への移行の勧めと、ディストリビューションやゲーム互換性をめぐる議論が続いた（要約）。その中に考える価値のある反論が一つあった。Android、iOS、ChromeOS、macOS も、どのアプリが使われているかは当然知っているはずなのに、なぜ Windows にだけ追跡しないことを期待するのか、という問いである（要約）。正当な問いだ。ただし今回の件の特異点は、「アプリ使用統計」一般ではなく、**特定の競合カテゴリを名指しした専用の機能フラグとビットマップ**を作っていたところにある。汎用テレメトリの副産物ではなく、コーディングエージェントを数えるために意図的に設計された計測なのである。

## 展望と示唆 — 開発マシンは誰の計測装置か

実務者にとって最も直接的な示唆は設定である。原文が案内するとおり、インストール時にオプションの診断を拒否するか、その後「設定 → プライバシーとセキュリティ → 診断とフィードバック」で「オプションの診断データを送信する」をオフにできる。企業環境であればグループポリシーやMDMで `AllowTelemetry` のレベルを管理している可能性が高いが、個人の開発機やBYODは死角になる。特に顧客との契約上、どのAIツールを使っているかさえ機微情報になる組織、たとえば特定ベンダーのモデル使用を禁止または義務付ける契約を抱える組織であれば、ツールの使用事実そのものがOSベンダーに出ていくという点を、セキュリティ評価の項目に加えるべきだろう［仮定：これを明示的に扱う組織ポリシーの事例は確認していない］。日本の受託開発の現場で「生成AIの利用可否」を案件ごとに取り決める慣行が広がっていることを考えれば、この論点は他人事ではない。

第二の示唆は方法論である。原文は「AIにバイナリを洗わせて手がかりを見つけ、人間が実機で再現して確認する」という作業スタイルを示している。前日に HN に上がった uBlock Origin の脆弱性公開も、同様の分業を明かしていた。文書化されていないOSの挙動は、これまで少数のリバースエンジニアの領域だったが、探索コストが下がるにつれ、こうした発見はより頻繁に出てくるだろう。OSベンダーにとっては、「文書化されていない計測」が静かに残り続けることが難しい環境になった。

シナリオを分けてみよう。**楽観シナリオ**では、Microsoft がこの計測の存在と目的を文書化し、診断データビューアーでユーザーが確認できるようにし、EUなどの規制地域では明示的な同意の対象に切り替える。**悲観シナリオ**では、何の説明もないまま機能フラグが名前だけ変えて維持され、類似の計測がブラウザ・IDE・ターミナルへと広がる。ツールベンダーの側も、OSのテレメトリに対抗して実行ファイル名を変えるような回避を試みるかもしれないが、それは軍拡競争にすぎない。**現実的シナリオ**は、今回の暴露が規制当局の関心リストに一行加わる程度で終わり、開発者コミュニティでは「開発マシンは Linux で」という古くからの助言が少しだけ説得力を増す、というものだ。

より大きな文脈もある。コーディングエージェントは今や、開発者のマシン上で最も多くの権限を持つプロセスの一つだ。ファイルを読み、コマンドを実行し、ネットワークに接続する。それらのエージェントをめぐる競争は、モデルの品質だけでなく**配布チャネル**の競争でもある。OS、IDE、コードホスティング、クラウドのすべてを持つ企業が、OSレベルのテレメトリで競合エージェントの使用を観測できるということは、プラットフォーム独占の議論で繰り返し出てきた「プラットフォームが自らのマーケットのデータを見る」問題の新しい版である。

## 結論

リード質問に戻ろう。1ビットのテレメトリはありふれた製品診断なのか、市場情報の収集なのか。原文が証明したのは収集とアップロードの**事実**であって、意図ではない。意図は Microsoft にしか分からない。しかし判断に必要な材料は十分にある。競合製品を名指しした専用の機能フラグがあり、ユーザーが手動で有効にしていないのにサービス実験として有効化されており、「オプション」のデータがデフォルトでオンになっていた。データの大きさは小さいが、そのデータが答える問い、すなわち「開発者たちはどのエージェントを使っているのか」は、いま業界で最も高価な問いの一つである。

個人の開発者がやるべきことは明確だ。診断設定を確認し、望まなければオフにする。組織に残る問いはもっと広い。私たちの開発マシンのOSは私たちの味方なのか、それとも私たちが使うツールの市場で競う一人の選手の計測装置なのか。そしてその問いに答えるために、私たちはドキュメントではなくバイナリを読まなければならない時代に生きているのだろうか。
