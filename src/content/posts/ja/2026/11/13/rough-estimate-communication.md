# 「ざっくりどのくらい？」に数字ひとつで答えてはいけない理由 — 概算見積もりを式と分布で語る

> 概算見積もりとは、経験豊富なエンジニアの「勘」で投げる一つの数字なのか。それとも、相手と合意するために設計された式と確率分布なのか。

## 導入

「このアプリを作ろうと思ったら、ざっくり工数どのくらい？」ソフトウェア業界で働いたことのある者なら、会議室の廊下やチャットでこの質問を受けた経験があるだろう。そして少なからぬ人が「ざっくり〇人月くらいですかね」と答えた経験もあるはずだ。聞く側にも答える側にも悪意はない。事業責任者はやるかやらないかを早く決めたいし、エンジニアはその判断を助けたい。ところが、まさにその一つの数字が、数週間後に正式な見積もりを出したとき「前は〇人月って言ってたよね」という言葉になって返ってくる。

2026年11月13日に Qiita に投稿された「『ざっくり工数どのくらい？』に『ざっくり工数このくらい』で答えてはいけない」は、このおなじみの場面を正面から扱った記事である。筆者（tsutorm）は以前に書いた「"工数が足らない" からの脱却」の前段、すなわち見積もりをどう出し、どう伝えるかをテーマに据えた。タグには自ら「ポエム」を付けているが、内容はかなり具体的である。記事は投稿直後に いいね 67、ストック 54 を集めた（2026-11-16 の API 取得時点）。

主張は三行に要約できる。第一に、概算見積もりはステークホルダーと意思疎通できる数量 × 単位あたりの工数という式で出す。第二に、単位あたりの工数は予想ではなく過去の実績から求める。第三に、見積もりは予想なので、一つの数字ではなく幅と確率の分布で伝える。本稿では、この三原則が単なる「見積もりテクニック」ではなく、組織コミュニケーションの設計問題である理由を分析する。

## 本論1 — 一つの数字が生む「空中戦」

記事がまず指摘するのは、聞く側の事情である。事業責任者や経営者は、詳細な見積もりを何週間も待っていられない。投資するか否か、優先順位、他プロジェクトとの資源配分を早く決めなければならない。だから「ざっくり」という言葉は怠慢ではなく、意思決定のスピードに対する要求である。問題は、その要求に根拠のない数字一つで応えてしまうときに生じる。

筆者の言葉を借りれば、一度口にした数字は独り歩きする。後で正式な見積もりを出すと最初の数字と比べられ、「なんでこんなにかかるの？」と聞かれても根拠がないので、感覚同士の言い合いになる。いわゆる空中戦である。地に足の着いた根拠なしに、互いの印象だけが飛び交う議論だ。

解決策として最初に示される道具が式である。

```
工数 = 画面数 × 1画面あたりの工数
```

たとえば 20画面 × 0.5人月 = 10人月となる（記事中の数字はすべて説明用の例だと筆者は明記している）。肝心なのは「何を数量にするか」だ。筆者は精緻さよりも、ステークホルダーが理解できる単位を優先せよと言う。定期バッチや API は画面とは単価感がまったく違う。相手がその違いを理解してくれるなら「画面◯個、バッチ◯本、API◯本」と分けて扱えばよい。しかし現実にはそうでないことのほうが多く、画面は目に見えて誰でも数えられる。だから合意の単位は多くの場合、画面数になる。

では、バッチや API の工数はどこへ消えるのか。記事の答えは明快である。過去案件の「総工数」に設計・テスト・PM・バッチ・API をすべて含めて記録しておけば、1画面あたりの平均の中にすでに吸収されている。だから別に数えなくても漏れない。

二つ目の道具が実績である。「この画面は0.5人月くらいかな」と予想で単価を決めれば、式の形をしていても中身は勘だ。筆者は1画面あたりの工数を「過去案件の総工数 ÷ 過去案件の画面数」で求めよと言い、これを戸建ての坪単価にたとえる。ハウスメーカーに最初の相談をすると「坪単価◯万円なので、35坪なら◯◯万円くらい」と返ってくる。その坪単価は過去に建てた家の平均である。キッチンや外壁のグレードで金額は変わるが、それは仕様が決まってからの話だ。さらに家の見積もりは「本体工事は坪単価、外構や諸費用は別」と分けて出てくるが、これは施主が外構は別にかかるものだと理解しているからである。バッチや API を分けて出すか画面単価に含めるかも、同じ論理で決めればよい。

実績記録の最低限の型も示されている。案件名、画面数、総工数（人月）、期間、メモ。そこに二つのルールが付く。画面の数え方をチームで固定すること（例：URLが変わるものを1画面、モーダルやタブは数えない）、そして総工数には案件全体の工数を漏れなく入れること。数え方がブレれば平均もブレる。

三つ目の道具が分布である。天気予報は「明日は雨です」ではなく「降水確率70%」と言う。仕様も決まっていない概算段階で「10人月です」と一つの数字で答えるのは、筆者の言うとおり、わからないことをわかったふりをするのと同じである。

## 本論2 — なぜ「式＋実績＋分布」は構造的に機能するのか

この記事が興味深いのは、個々の手法が新しいからではない。筆者自身が書いているように、似た過去案件の実績から予測するという発想は、Flyvbjerg らが提唱した参照クラス予測（Reference Class Forecasting）とほぼ同じである。仕様が決まるにつれて見積もりの幅が狭まるという考え方は、McConnell が広めた不確実性のコーン（Cone of Uncertainty）だ。三点見積もりと PERT のベータ分布近似も、プロジェクトマネジメントの教科書に載っている。新しいのは、この三つを「ざっくりどのくらい？」という日常会話への応答フォーマットとして組み直した点にある。

まず、式が果たす役割を見よう。式があると議論の軸が変わる。「高い・安い」という価格交渉が、「この画面は本当に必要か」というスコープの議論に移る。画面数が変われば式に入れ直せばよい。つまり式は計算道具である前に、交渉のアジェンダを再設定する装置なのである。値引き要求はエンジニアの信頼を削る圧力として働くが、画面を減らそうという提案は事業側が自ら決められる選択肢である。

次に、実績が果たす役割。式の係数を勘で決めれば、空中戦は係数をめぐって再開する。「1画面に0.5人月もかかるの？」という問いに「過去5件の平均です」と答えられれば、論争の対象はエンジニア個人の判断からチームのデータへと移る。これは参照クラス予測の本来の趣旨でもある。個別案件の特殊性を内側から積み上げる「内部の視点」は楽観バイアスに陥りやすく、似た案件群の実際の結果を見る「外部の視点」がそれを矯正する。

最後に分布。記事は実績から三点を導く。画面数は20〜24（画面は減るより増えがちだ）、過去実績の1画面あたり工数が最小0.4・平均0.5・最大0.75人月だとすると、

```
楽観値 a = 20画面 × 0.4人月  = 8人月
最可能 m = 20画面 × 0.5人月  = 10人月
悲観値 b = 24画面 × 0.75人月 = 18人月
```

PERT の式で期待値は (a + 4m + b) / 6 = 11人月、標準偏差は (b − a) / 6 ≒ 1.7人月となる。注目すべきは、最可能値が10なのに期待値が11になるという事実である。筆者はこれをソフトウェア開発の非対称性で説明する。早く終わる方向には限界があるのに、遅れる方向にはいくらでも延びる。悲観側に裾が長いぶん、平均は右にずれる。

この非対称性は、数字一つで答える慣行がなぜ系統的に失敗するのかも説明する。エンジニアが「ざっくり」と言われて思い浮かべる数字は、たいてい「いちばんありそうな場合」、つまり最可能値に近い。だが右に裾の長い分布で最可能値を約束すれば、実際の結果がその数字を超える確率は半分を大きく上回る。筆者はさらに、期待値で約束するのも危ういと言う。期待値は「五分五分の線」なので、11人月で約束すれば半分近い確率で超過する。予算や約束は約8割の確率で収まる線、例では期待値＋標準偏差 ≒ 12.7人月に置け、というのが記事の勧めである。筆者は、これは正規分布に近いとみなしたときの目安（厳密には約84%）だという但し書きも添えている。

但し書きは他にもある。PERT の式自体がベータ分布の近似であり、精密さより幅で話すための道具と割り切る。規模が大きくなるほど1画面あたりの工数は増えがち（規模の不経済）なので、規模の近い案件の実績を参照する。チームによって生産性は違うので、他チームの実績を使うときは補正が要る。期間を人数で割るのは単純計算にすぎず、人を増やせば比例して短くなるわけではない。そして実績が十分に溜まっているなら、三点に丸めず実績のばらつきそのものを使うほうが素直だと付け加える。三点見積法は実績が少ないときの近似だということである。

これらの但し書きは些細に見えて重要だ。見積もり手法を紹介する記事は、しばしば数式のエレガンスに寄りかかって限界を隠す。この記事は逆に、道具がどこまで近似なのかを先に明かす。それが読者に、この道具を「正解生成器」ではなく「対話の枠組み」として受け取らせる。

## 本論3 — 実務への示唆：見積もりは計算ではなく応答の設計である

この記事で最も実用的な部分は、結局のところ応答のスクリプトである。筆者は「ざっくりどのくらい？」と聞かれたとき、たとえば次のように返す例を挙げる（人月単価100万円、3人チームの仮定）。今の話だと画面が20くらい。実績では1画面あたり平均0.5人月なので、いちばんありそうなのは1,000万円くらい。ただ、決まっていないことが多いので800〜1,800万円の幅がある。平均すると1,100万円、8割方収まるのは1,300万円弱と見ているので、予算はそこで確保してもらえると安心だ。仕様が固まれば幅は狭まり、画面を減らせば金額も下がる。

それでも「いいから一つの数字で言ってよ」と返されることはある。そのときも記事は、一つの数字に確率を添えよと言う。一つに絞るなら1,300万円弱で、8割方はこの中に収まる。1,000万円と答えることもできるが、その場合は半分以上の確率で超える。ここが肝である。一つの数字を求められる状況そのものを拒むのではなく、その数字が分布のどこにあるのかをラベルとして付けて渡すのだ。

この方法が実務に与える示唆は三つに整理できる。

第一に、実績の記録は今日始めなければならない。式も分布も、実績テーブルがなければ空虚である。記事が示す五列の表は導入コストがほぼゼロだ。逆に言えば、実績のないチームがこの記事の方法を真似ても、「式の形をした勘」が残るだけである。計測なき見積もり改善はない。

第二に、事業側が握れるレバーを明示しなければならない。幅で伝えると「で、私は何を決めればいいの？」という反応が来る。記事は三つのレバーを示す。予算は上側の線（8割の線）で確保し、余れば戻す。仕様を早く決めて不確実性のコーンを狭める。画面を減らして金額と幅を同時に下げる。見積もりが事業側の行動リストに翻訳されたとき、初めて「幅」は逃げではなく情報になる。

第三に、この方法には限界もはっきりある。悲観的に見れば、画面数という単位が通用しない案件が増えている。画面のほとんどないデータパイプライン、エージェントベースの自動化、レガシー移行は「画面あたり単価」に換算しにくい。こうした場合は、相手と合意できる別の単位（連携先システム数、移行テーブル数など）を探す必要があるが、その単位がステークホルダーにとって直感的でなければ、式の利点は弱まる。さらに、AI コーディングツールが1画面あたりの工数そのものを急速に変えているなら、過去実績の平均は系統的に古い数字になりうる。参照クラスを「規模が近く、時期も近い案件」に絞れという記事の但し書きは、この問題にもそのまま当てはまる。

現実的なシナリオはこうだ。多くの受託・社内開発組織にとって、画面数ベースの式は今後も最も速く合意を作る道具であり続ける。ただし実績テーブルの「メモ」欄の重要性が増していく。決済連携の有無、外部 API の数、AI ツールの活用度合いのように平均を歪める要因を記録しておかなければ、次の見積もりの参照クラスを選べない。日本の SIer で長く使われてきた画面数・帳票数ベースの見積もり慣行にとっても、これは「数え方」と「記録」の規律を問い直す話でもある。

## 結論

リード質問に戻ろう。概算見積もりとは、勘で投げる一つの数字なのか、合意のために設計された式と分布なのか。この記事の答えは明らかに後者である。そしてその答えが説得力を持つのは、数学が精緻だからではなく、見積もりを「当てる問題」から「合意する問題」へと定義し直したからである。

「ざっくり」と聞く人は、早い判断を求めている。その要求に根拠を添えて素早く応える道具が、式と分布だ。式は議論を価格からスコープへ移し、実績は議論を個人の勘からチームのデータへ移し、分布は約束を五分五分の線から8割の線へ移す。三つとも、空中戦を地上戦へ引きずり下ろす装置である。

読者に残す問いは単純だ。あなたのチームには、直近5件の案件の画面数と総工数を書いた表があるだろうか。なければ、次の「ざっくりどのくらい？」に対する最も誠実な答えは、おそらく「幅はこのくらいで、その幅を狭めるにはまずこの表を作る必要がある」である。
