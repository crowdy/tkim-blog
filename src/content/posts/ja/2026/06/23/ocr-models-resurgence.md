# OCR の復活：解決済みの問題が再び熱を帯びる理由

> Tesseract やクラウド OCR API で「解決済み」と見なされた問題が、同じ日に二つのモデルで Hacker News の上位を占めた。解決済みの問題が再び熱を帯びるとは、何を意味するのか。

## 導入 — 同じ日、OCR モデルが二つ上位に並んだ風景

2026 年 6 月 23 日 (KST)、Hacker News のトップページに OCR モデルが二つ並んで上がった。一つは Mistral が発表した 「Mistral OCR 4」 で 498 点にコメント 134 件、もう一つは Baidu が公開した 「Unlimited OCR: One-shot long-horizon parsing」 で 491 点にコメント 110 件だった。商用 lab の商業モデルとオープンソースの研究モデルが、同じ日に、ほぼ同じ点数で、同じ主題の上に並んだという事実は偶然とは見なしにくい。

OCR (光学文字認識) はコンピュータビジョンの最も古い問題の一つである。1970 年代の郵便番号認識から、Tesseract のようなオープンソースエンジン、Google・AWS・Azure のクラウド OCR API まで、この問題はとうに「解決済み」と見なされてきた。印刷された文字をテキストに変える仕事は、もはや研究テーマではなく API 呼び出し一行の商品だった。ところが 2026 年のある日、その解決済みの問題が二つの新しいモデルで再びコミュニティの上位に上がった。本稿が問うのは単純だ。なぜ今 OCR なのか。その答えは、OCR という言葉の定義が静かに変わったという事実にある。

## 二つのモデルの解剖 — 構造を読む OCR、一度に読む OCR

まず二つのモデルが何を掲げたかを見る。両者はアプローチが違うが、指し示す方向は同じだ。

**Mistral OCR 4 — 抽出ではなく構造化。** Mistral が 2026 年 6 月に出したこのモデルは、自らを単なる OCR ではなく 「文書インテリジェンス (document intelligence)」 モデルと規定する。PDF、Word、PowerPoint、OpenDocument を入力として受け、テキストを抜き出すにとどまらず、そのテキストを構造化する。各ブロックにバウンディングボックスを与え、そのブロックが見出しか表か数式か署名かを分類し、ページと単語の単位で信頼度スコア (confidence score) をインラインで付ける。すなわち出力が平坦なテキストの塊ではなく、座標と分類と確信度をもつ構造化オブジェクトである。

言語の幅も広い。10 の言語群にまたがる 170 言語を扱い、特に学習データの少ない低資源 (low-resource) 言語での強みを掲げた。配備の面では、単一コンテナで自己ホスティング (self-hosted) が可能だと強調したが、これは文書を外部へ出せない企業のデータ主権 (data sovereignty) の要求を正面から狙った設計だ。価格は 1000 ページあたり 4 ドル、バッチ API では 2 ドル、構造化 JSON を返す Document AI は 1000 ページあたり 5 ドルである。あるユーザーは、先進的なエージェント型文書パーサーに比べて 「同等の精度を 8 倍低いコストと 17 倍低い遅延 (latency) で」 得たと報告した。

**Baidu Unlimited-OCR — 一度に長い文書を読む。** Baidu のモデルは別の軸に触れる。DeepSeek-OCR を基盤とし、「一度に長い地平をパースする (one-shot long-horizon parsing)」 という標語を掲げる。核心は、長い文書を分割して複数回推論するのではなく、単一推論でまるごと処理することにある。32,768 トークンの文脈長をもち、解像度と効率の折衷が異なる 「gundam」 と 「base」 の二モードを提供する。単一画像は Huggingface Transformers で、複数ページは SGLang で動かす。反復出力を防ぐために no-repeat n-gram 制約を入れたカスタム logit processor を付けた点も目を引く — ビジョン・言語モデルが同じ語句を無限に繰り返す持病への直接的な対応だ。

Baidu が自らの作業を呼ぶ名は 「テキスト抽出」 ではなく 「文書パース (document parsing)」 である。構造、レイアウト、意味的関係まで読むという意味だ。公開時点で GitHub スター 9.2k、フォーク 713 を集め、arXiv 論文 (2606.23050) で手法を公開した。二つのモデルは形が違うが — 一方は商業 API、一方はオープン重み — 同じ一点を共有する。両者ともビジョン・言語モデル (VLM) の上に立ち、両者とも出力として平坦なテキストではなく構造を返すということだ。

## なぜ今なのか — テキスト抽出から文書理解へ

解決済みの問題が再び熱を帯びた理由は、その問題を取り巻く需要が変わったからである。その需要の名は LLM と RAG だ。

**古典 OCR が捨てたもの。** Tesseract やクラウド OCR API は一つの仕事をよくこなした。ピクセルを文字に変える仕事だ。しかしその過程で一つを捨てた。構造である。表のセル境界、多段組み (multi-column) の読み順、見出しと本文の階層、脚注と本文の関係 — これらすべてのレイアウト情報が古典 OCR の出力からは消える。人間が紙を読むときに真っ先に使う情報が、テキスト一行へ平坦化される中で蒸発するのだ。印刷物を検索可能なテキストへ変える時代には、その損失は問題ではなかった。どうせ人がもう一度読むはずだったからだ。

**RAG が要求するもの。** LLM の時代に、文書を読む主体が変わった。いまや文書を食べる側は人ではなく検索拡張生成 (RAG, Retrieval-Augmented Generation) パイプラインだ。RAG は文書を意味単位に刻み (chunking) ベクトルで索引し、質問が来れば関連断片を引いて LLM に食わせる。このとき構造がなければすべての段階が崩れる。表が平坦なテキストに潰れればセル間の関係が消え、多段組みの読み順が狂えば文がかき混ぜられ、見出しと本文の階層がなければ意味単位の分割が見当違いになる。RAG が引用可能な (citation-ready) 答えを出すには、文書がどこから来たかを座標の単位で知らねばならない。まさに Mistral OCR 4 がバウンディングボックスとブロック分類を出力する理由だ。

この需要の転換を一行に縮めるとこうなる。OCR の定義が 「テキスト抽出 (text extraction)」 から 「文書理解 (document understanding)」 へ移った。ピクセルを文字に変えることはもはや目標ではない。ピクセルから構造と意味と関係をともに引き出すことが目標である。そしてその仕事は古典 OCR エンジンにはできない。その仕事をするのがビジョン・言語モデルだ。VLM は画像とテキストを同じ表現空間で扱うので、文字だけでなくその文字が置かれたレイアウトをともに読む。解決済みと思われた問題が再び開いた理由は、問題が難しくなったのではなく、問題の定義が変わったからである。

**日本語文書という難所。** この転換が日本の企業にとって他人事でない理由がある。日本語文書は OCR にとって世界有数の難所だ。縦書きと横書きが同じ紙面に混在し、ルビが本文に絡み、古文書のくずし字は連綿で続き、何より企業を縛るのは複雑な帳票である。複数の表が入れ子になり、押印欄と手書き記入が混じり、罫線が意味をもつ日本の請求書・申請書・契約書は、平坦なテキスト抽出では本質を失う。どのセルにどの数字が、どの欄にどの署名が入ったかという構造こそが帳票の中身だからだ。DX 推進を掲げながら紙の処理から抜け出せない多くの日本企業にとって、構造を保持する OCR は単なる効率化ではなく、デジタル化の前提条件である。Mistral が掲げた低資源言語への強さと自己ホスティングは、データを外に出せない国内企業の事情にそのまま響く。

**optical compression という逆説。** この転換で最も興味深い分岐が、DeepSeek-OCR が切り開いた光学圧縮 (optical compression) である。発想は逆だ。通常 OCR は画像からテキストを取り出す。ところが DeepSeek-OCR の洞察は、テキストを画像へエンコードすれば同じ情報をより少ないトークンで LLM の文脈に詰め込めるというものだ。文字 1000 個をテキストトークンで入れれば 1000 個近いトークンを食うが、それを一枚の画像に圧縮すればはるかに少ないビジョントークンで表現される。OCR が単なる入力変換器ではなく、長い文書を LLM の文脈に詰め込む圧縮層になるのだ。Baidu Unlimited-OCR が DeepSeek-OCR を基盤とし、一度に長い文書を読める理由がここにある。OCR が LLM の前処理器を超え、LLM の文脈経済を再設計する道具になった。

## オープンと商業の競争、そして VLM OCR の代償

二つのモデルが同じ日に上位へ上がった風景は、ある産業の競争構図を凝縮する。一方には DeepSeek から Baidu へ続くオープン重みの系譜があり、他方には Mistral のような商業 API がある。オープン側は自己ホスティングと微調整の自由を武器とし、商業側は品質と運用の手軽さを武器とする。興味深いことに、Mistral でさえ単一コンテナの自己ホスティングを掲げた点は、文書というデータの機微性がこの市場を普通の API 市場と違うものにするという信号だ。文書は契約書であり医療記録であり財務諸表である。外部へ出せないデータが多いほど、自己ホスティング可能なオープンモデルの居場所が広がる。

しかし VLM ベースの OCR はただではない。代償が三つある。

**第一に、速度とコスト。** 古典 OCR は軽い。CPU でもページをミリ秒単位で処理する。VLM ベースの OCR は重い。GPU の上で数十億パラメータの推論を回さねばならず、ゆえに遅く高い。あるユーザーが報告した 「8 倍低いコスト、17 倍低い遅延」 は印象的だが、その比較対象がより重いエージェント型パーサーだった点を忘れてはならない。Tesseract と比べれば VLM OCR はなお数十倍高い。すべての文書に VLM を使う理由はない。単純な印刷テキストなら古典 OCR がいまだに正解だ。

**第二に、幻覚。** これが最も重い代償だ。古典 OCR は文字を読み違えることはあっても、存在しない文字を作り出しはしない。だが VLM は本質的に生成モデルである。ぼやけた領域に出会うと、見えるものを読む代わりにもっともらしいものを作り出しかねない。数字が一つ変わった財務諸表、なかった条項が生えた契約書は、単なる認識誤りより危険だ。誤りがもっともらしく検出しにくいからである。Baidu が no-repeat n-gram 制約を logit processor に入れたのも、この生成的本性の副作用 — 無限反復 — への防御だ。VLM OCR を高リスク文書に使うとき、信頼度スコアと人手検収が必須となる理由がここにある。

**第三に、ベンチマークの信頼性。** Mistral は人間評価者が 72% の比率で自社モデルを選好し、OlmOCRBench で 85.20、OmniDocBench で 93.07 と最上位だと明かした。だが同じ発表で Mistral はベンチマークの限界を異例なほど率直に認めた — 正解 (ground-truth) 自体の誤り、数式表記の不一致、多段組み読み順の曖昧さ。だから自社のベンチマーク数値を信じず 「あなたの文書で直接試せ」 と勧める。解決済みと思われた問題が再び開いた領域では、正解が何かさえ合意されていないということだ。ベンチマーク数値の競争がまだ信頼に足る段階に達していない点は、この分野が成熟ではなく入口にあることを逆に証明する。

## 結論 — 解決済みの問題は定義が変わると再び開く

同じ日に OCR モデルが二つ上位へ上がった風景の意味は明らかだ。OCR は解決済みの問題だったが、定義が変わることで再び開いた問題になった。ピクセルを文字に変える仕事はなお解決されている。しかしピクセルから構造と意味を引き出して LLM に食わせる仕事は、いままさに開いた。Mistral OCR 4 のバウンディングボックスとブロック分類、Baidu Unlimited-OCR の一度に読む長い地平、DeepSeek の光学圧縮は、すべて同じ転換の変種である — テキスト抽出から文書理解へ。

この転換が指すより大きな含意が一つある。AI の次のボトルネックはモデルではなくデータの供給、なかでも世界中に紙と PDF で閉じ込められた膨大な文書のデジタル化だということだ。人類の知識の相当量は、いまだ構造化されない文書の中にある。その扉を開ける鍵が OCR であり、その鍵が VLM で削り直されている。日本企業の倉庫に眠る帳票と古文書もまた、その扉の向こう側にある。解決済みと思われた最も古い問題が、最も新しい需要の最前線へ戻ってきたのだ。速度とコストと幻覚という三つの代償は残るが、同じ日に二つのモデルが受けた 989 点の合算が指す方向は明らかだ。OCR の第二の時代が始まった。
