# コードベース知識グラフ：MCPサーバーがエージェントにコードを「理解」させる方法

> AIエージェントがコードベースを探索する方法は根本的に変わりうるか？ C/C++で書かれた単一バイナリ1つが、Linuxカーネル2800万行を3分で知識グラフに変換するなら、エージェントとコードベースの関係を最初から問い直さなければならない。

## はじめに

2026年は、AIコーディングエージェントが開発者ワークフローの深部まで浸透した年として記録されるだろう。Claude Code、GitHub Copilot、Cursor、OpenAI Codex CLI、Gemini CLI——名前を列挙するだけで手が追いつかないほど多くのツールが登場し、それらはすべて自然言語でコードを書いたり修正したりできると主張する。しかし、これらのツールが数十万行規模の実際のプロダクションコードベースに直面したとき、共通して露呈する限界がある。

エージェントはコードベースを把握するためにファイルを1つずつ開いて読む。関数Aがどこから呼ばれているかを追跡するには、grep的な検索を繰り返すか、複数のファイルを順序なく掻き集めてコンテキストウィンドウに詰め込む。大規模なモノレポで特定APIの全呼び出しグラフを把握する作業は、数十から数百回のファイル読み取りリクエストにつながりかねない。これはトークン消費に直結し、結果としてコストと待ち時間の急激な増大として現れる。

`codebase-memory-mcp`はこの問題を、ファイル単位ではなく構造単位——知識グラフ(knowledge graph)——でアプローチすることで解決しようとしている。このプロジェクトがGitHub Trendingの週間チャートで8,024個のスターを獲得したことは、エージェント開発者コミュニティがこの問題の深刻さを十分に認識していることを示している。以下では、このMCPサーバーの技術設計、実質的な効用、そしてエージェントエコシステムへの示唆を順に検討する。

## 技術構造分析：Cで書かれたコード知識グラフエンジン

`codebase-memory-mcp`の第一の設計判断は実装言語である。このサーバーはPythonでもTypeScriptでもなく、C/C++で書かれており、依存性なしの単一静的バイナリとして配布される。この選択は単なるパフォーマンス好みの問題ではなく、大規模コードベースを現実的な時間内にインデックス化するためのエンジニアリング上の必然だ。ランタイムインタープリタ、パッケージマネージャ、仮想環境がないため、インストール時に生じる依存関係の衝突や環境変数の問題もない。

### Tree-sitterによる多言語パーシング

ソースファイルを意味のある単位に分割する最初のステップはパーシングである。`codebase-memory-mcp`はTree-sitterをパーサーエンジンとして採用し、158言語をAST(抽象構文木)に変換する。Tree-sitterは増分パーシング(incremental parsing)をサポートしているため、ファイルの一部が変更された場合に全体を再パーシングする必要なく、変更されたサブツリーのみを更新できる。これによりインデックスの維持コストが大幅に下がる。

ASTパーシング段階で抽出される情報は、関数定義、クラス宣言、インポート文、型アノテーションなどである。この情報が知識グラフのノードを構成する。ノードの種類は大きく3つ——関数(function)、クラス(class)、ファイル(file)——であり、エッジは呼び出し関係(calls)、インポート関係(imports)、型使用(type usage)に分類される。このグラフ構造により、エージェントはコードベースの「地形図」を手に入れる。ファイルを開いて読む前に、どの部分がどの部分と繋がっているかを先に照会できるのだ。

### Hybrid LSP：型認識解釈

Tree-sitterだけでは、動的ディスパッチやインターフェース実装のような型レベルの関係を正確に追跡するのが難しい。`codebase-memory-mcp`が「ハイブリッドLSP」と呼ぶ第2のレイヤーはこの限界を補完する。Python、TypeScript/JavaScript、PHP、C#、Go、C/C++、Java、Kotlin、Rustなど9言語について型認識解釈を実行し、知識グラフのエッジ品質を高める。

LSP(Language Server Protocol)はもともとIDEが言語サーバーと通信するための標準プロトコルだ。これをMCPサーバー内部で非同期サブプロセスとして運用しながら、言語サーバーが提供する型情報をグラフエッジの解釈に活用する。結果として単純な文字列マッチングのレベルを超え、「この変数が実際にどの型のインスタンスか」を考慮して呼び出し関係をグラフに記録する。例えばTypeScriptコードでインターフェースを実装する複数のクラスがある場合、どのクラスのメソッドが実際に呼ばれるかを型フロー分析を通じてグラフに反映できる。

### RAMファースト・インデックスとLZ4圧縮

大規模コードベースのインデックス化における速度問題は、多くの場合I/Oバウンドである。このサーバーはインデックス化中できるだけ多くのデータをRAMに載せて処理した後、最終結果をLZ4で圧縮してSQLiteに保存する方式を採用している。LZ4は圧縮速度と圧縮率のバランスに優れ、リアルタイム性が重要なインデックス化作業に適している。SQLiteのFTS5拡張でフルテキスト検索をサポートし、グラフ探索用のBFS(幅優先探索)アルゴリズムも内蔵している。

ベンチマークによれば、Linuxカーネル(2800万行、7万5000ファイル)を約3分でインデックス化できる。ローカルマシンでこの速度は、インデックス化が開発サイクルのボトルネックにならないことを意味する。インデックス成果物である`graph.db.zst`ファイルはチームリポジトリにコミットして共有でき、チームメンバー全員が初回クローン時点から完成したインデックスを即座に使える。大規模オープンソースプロジェクトの場合、メンテナーがグラフアーティファクトをリリースに含めるワークフローも考えられる。

### Cypher的クエリとtrace_path

知識グラフが構築された後、エージェントはCypher文法からインスピレーションを得たクエリ言語でグラフを探索する。Cypherはグラフ指向データベースNeo4jで広まったクエリ言語で、ノードと関係を直感的なASCIIアート表記で表現する。`trace_path`ツールはこの探索の核心インターフェースで、双方向呼び出しチェーン(bidirectional call-chain)検索を10ms未満で実行する。特定の関数がどこから呼ばれているか、逆に特定の関数が何を呼んでいるかを単一クエリで追跡できる。これはバグの原因追跡やインターフェース変更の影響分析のような、呼び出しチェーン探索が核心となる作業で特に強力だ。

## 99.2%トークン削減が実際に意味するもの

99.2%という数値はマーケティング上の誇張に見えるかもしれない。しかしこの数値がどこから来るのか、そしてそれが実際の作業で何を意味するのかを分けて分析する必要がある。

### ファイル探索方式の構造的比較

既存のエージェントが新しいコードベースを探索するとき使う方法は概ね2つだ。1つはディレクトリ構造を再帰的に辿ってファイルを1つずつ読む方法であり、もう1つはripgrepやfindのような検索ツールを繰り返し呼び出して関連ファイルを絞り込んでいく方法だ。どちらもコードの意味的構造を知らない状態から始まるため、関係のないファイルを大量に読まなければならなかったり、不完全な情報で結論を出さなければならない状況が頻繁に発生する。数百のファイルを持つモノレポでは特にこの非効率が際立つ。

`codebase-memory-mcp`はエージェントがファイルを開く前に構造的クエリをまず発行できるようにする。「関数Xの呼び出し元は誰か？」「ファイルYがインポートするモジュールのリストは？」「インターフェースZを実装するクラスは？」といった質問への答えが知識グラフから直接返ってくる。エージェントが実際にファイルを読まなければならないのは、実装の詳細を確認したりコードを直接変更するときに限定される。つまり探索(exploration)のコストが大幅に削減され、実際の作業(execution)に集中できるようになる。

この方式の効率性はコンテキストウィンドウの希少性(scarcity)と結びついている。128Kあるいは200Kトークンのコンテキストウィンドウは大きく感じられるが、数百のファイルを読んでいくとあっという間に埋まる。構造的クエリは数千トークンのファイル内容の代わりに、数十トークンのグラフ応答で必要な情報を伝える。99.2%はこの差を極端に示す数値であり、実際の削減幅はコードベースの構造と作業の種類によって異なるが、構造的アプローチの優位性は明らかだ。

### コストと遅延の実質的な削減

トークン削減は直接的なコスト削減につながる。AIのAPIはほとんどが入力トークン基準で課金するため、ファイル探索に使われるトークンを大幅に削減すれば、エージェント実行コスト全体のかなりの部分を節約できる。特に大規模リファクタリングやコードレビューのような作業は数十回のファイル読み取りを伴うが、構造的クエリで事前探索を済ませれば実際に読まなければならないファイル数を劇的に減らせる。企業環境で何百人もの開発者がエージェントを日常的に使用すれば、このコスト削減は無視しがたい規模になる。

遅延時間も減少する。ファイルシステムへのアクセスとモデルコンテキストの充填を繰り返す方式は、往復遅延を積み重ねる。エージェントが5番目のファイルを読んで初めて次の質問をモデルに送れるなら、その往復遅延が5回積み重なる。グラフクエリはローカルSQLiteへのアクセスなのでネットワーク往復がなく、結果が数十ミリ秒以内に返ってくる。エージェント作業の体感速度が変わる理由がここにある。

### トレードオフと現実的な限界

すべての抽象化にはコストが伴う。`codebase-memory-mcp`の場合、インデックスが実際のコードと同期された状態を維持しなければならないという負担がある。コードが急速に変更される開発ブランチでインデックス再生成のタイミングを逃すと、グラフが古い情報を返す可能性がある。増分更新がサポートされているが、クラス階層の全面的な再設計や大規模なリネームのような構造的変化は相当な再インデックス化を要求することがある。

Hybrid LSPの型認識解釈も万能ではない。動的言語のランタイム動作、リフレクション、メタプログラミングベースのコードでは、静的分析ベースのグラフが不完全な情報を持つ可能性がある。Pythonの`__getattr__`オーバーライドやJavaScriptのプロキシパターンのようにランタイムで決定される呼び出し関係は、静的グラフには記録されない。エージェントはグラフクエリの結果を参照しつつも、クリティカルな判断の前には依然としてソースを直接確認すべきだ。

また現在Hybrid LSPの恩恵を受ける9言語以外の言語——Ruby、Swift、Scala、Elixirなど——はTree-sitterレベルの構造パーシングのみが行われる。この場合、型関係の精度が下がる。今後の言語サポート拡大がプロジェクトの重要な開発方向として予想される。

## エージェントエコシステムとMCP標準化の示唆

`codebase-memory-mcp`が単純なパフォーマンス改善ツールを超えて注目される理由は、エージェントエコシステムの構造的問題を標準プロトコルレベルで解決しようとする設計哲学にある。

### 11エージェントの自動設定

このMCPサーバーはClaude Code、OpenAI Codex、Gemini CLI、Zed、VS Codeなど11の主要コーディングエージェントへの自動設定をサポートしている。設定メカニズムはMCPのPreToolUseフックを活用する。ノンブロッキング(non-blocking)方式で動作し、MCPサーバー初期化時にエージェント設定ファイルを自動的に更新する。開発者は手作業で各エージェントの設定ファイルを編集する必要なく、たった1回のMCPサーバー起動ですべてのサポートエージェントで`codebase-memory-mcp`を使用できる。これは複数のエージェントを並行して使うチーム環境で特に実質的な利便性を提供する。

このアプローチはMCPを単純なツールインターフェースではなく、エージェント環境設定のオーケストレーターとして活用するパターンだ。MCPサーバーがエージェントにツールを提供しながら、エージェント自身の設定まで管理するという点で役割の拡張が起きている。

### インフラストラクチャコードの統合インデックス化

現代のソフトウェアシステムはアプリケーションコードだけで構成されているわけではない。Dockerfile、Kubernetesマニフェスト、Terraform HCL、Helmチャートのようなインフラストラクチャコード(Infrastructure-as-Code)が実際のシステムの動作を決定する核心部分を成している。`codebase-memory-mcp`はこれらのファイルも知識グラフに統合インデックス化する。

これによりエージェントは「このサービスがどのポートで公開されているか」「このコンテナのリソース制限は？」「このデプロイ設定がアプリコードのどの環境変数を参照しているか」のようなクロスレイヤーの質問に答えられるようになる。アプリケーションコードとインフラコードをつなぐグラフエッジは、従来のコード探索ツールが提供できなかった次元だ。

### プライバシーとセキュリティ設計

`codebase-memory-mcp`は外部APIの呼び出しが一切ない。すべての処理はローカルで行われ、コードがサードパーティのサーバーに送信されることはない。SLSA Level 3証明(provenance)を提供し、ビルドアーティファクトの出所と完全性を検証できる。MITライセンスで配布されているため、企業環境での採用障壁も低い。セキュリティ感度が高いコードベースを扱うチームにとって「AIツールが自分のコードをクラウドに送るか」は核心的な導入判断要素であり、完全なローカル処理はその懸念を断ち切る設計上の選択だ。

### MCPエコシステムの成熟化シグナル

MCP(Model Context Protocol)はAnthropicが主導して開発した標準だが、すでに主要なAIコーディングツールのほとんどが採用した事実上のエージェント-ツール通信標準となった。`codebase-memory-mcp`のような高性能特殊目的MCPサーバーの登場は、エコシステムが基本的なツール供給段階を超えてエージェント能力の構造的拡張段階へ移行していることを示している。エージェントにどんなツールを与えるかがエージェントの能力を決定する核心変数として浮上しており、このツールレイヤーの競争が今後エージェントエコシステム発展の重要な軸となるだろう。

今後、コードベースインデックス化以外にも、ランタイムテレメトリ、CI/CDパイプラインの履歴、依存関係の脆弱性データベース、イシュートラッカーのデータなどを知識グラフに統合する方向でMCPサーバーエコシステムが発展することが予想される。エージェントはますます広い文脈の上でコードを扱うようになるだろう。

## まとめ

`codebase-memory-mcp`が提起する核心命題はシンプルだ。AIエージェントがコードベースを探索する方式は現在根本的に非効率であり、ファイルではなく構造——知識グラフ——を媒介としてコードを「理解」させることが正しい方向だということだ。

C/C++単一バイナリ、Tree-sitter 158言語サポート、Hybrid LSPベースの型解釈、SQLiteとLZ4を活用した高速インデックス、10ms以下の双方向呼び出しチェーン追跡。これらの技術的選択はそれぞれ独立した利点を持つが、合わさるとエージェントがコードを扱う方法に質的変化をもたらす可能性がある。

99.2%のトークン削減が個々の開発者のAPIコスト問題に見えるかもしれないが、これは本質的にエージェントの「理解の仕方」に関する問題だ。ファイルを読んで把握するエージェントと、構造を照会して把握するエージェントは、同じコードベースを前にしても質的に異なる判断を下すだろう。知識グラフはエージェントにコードの「地形」をあらかじめ示すことで、探索から実行へと重心を移す。

MCPエコシステムが成熟するにつれ、エージェントにコードをよく理解させるツールレイヤーの重要性はさらに高まるだろう。`codebase-memory-mcp`はその方向で現在最も真剣な試みの1つである。
