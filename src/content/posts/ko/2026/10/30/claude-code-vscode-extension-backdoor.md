# 공식 확장이라는 착각 — Cursor 마켓플레이스에 숨어든 Claude Code 백도어

> "Anthropic 제작"이라는 표시는 서명인가, 그저 이름표인가. 개발자가 매일 설치하는 IDE 확장이 공격자가 가장 적은 비용으로 가장 넓은 권한을 얻는 통로가 될 때, 그 신뢰는 누가 보증하는가.

## 도입

2026년 10월 30일, 보안 업체 Phorion은 Cursor 마켓플레이스에 올라온 Claude Code용 VS Code 확장 2.1.312, 2.1.313 버전에 지속형 SSH 백도어가 심겨 있었다고 공개했다. 확장은 설치되는 순간 사용자 권한으로 즉시 실행되며, 별도의 클릭이나 확인 절차 없이 로컬 파일, 소스코드, 자격 증명, 개발 도구 전체에 접근할 수 있는 위치를 차지한다. 신고 초기에는 공식 VS Code 마켓플레이스가 영향을 받았다는 오보가 돌았지만, 같은 날 정정을 거쳐 Cursor가 운영하는 별도 마켓플레이스만 영향을 받았다는 사실이 확인됐다. 이 사건이 흥미로운 지점은 코드 자체의 정교함이 아니다. 공격자가 한 일은 단지 "Anthropic.claude-code"라는 이름을 가져다 쓴 것뿐이었고, 그것만으로 수많은 개발자의 노트북에 지속적인 원격 접근 통로를 심을 수 있었다는 사실이다.

## 백도어의 동작 방식과 피해 범위

Phorion의 분석에 따르면 공격자는 확장의 번들 파일인 extension.js 맨 앞에 즉시 실행 함수(IIFE)를 주입했다. 이 함수는 Node.js의 표준 모듈만으로 작성되어 있었고, 확장의 정상적인 activate 함수가 호출되기도 전에 파일이 로드되는 즉시 실행됐다. 사용자가 확장을 켜거나 명령을 실행할 필요조차 없었다.

실행된 코드가 하는 일은 네 단계로 나뉜다. 첫째, 공격자가 통제하는 Ed25519 공개키를 ~/.ssh/authorized_keys에 추가해 로그인 경로를 확보한다. 이때 키 자체가 아니라 "svc-telemetry"라는 주석 문자열만 확인하기 때문에 중복 삽입이나 탐지 우회 여지가 있다. 둘째, 로컬 SSH 데몬을 활성화하려 시도한다. 리눅스에서는 systemctl이나 service, macOS에서는 sudo -n systemsetup, 윈도우에서는 PowerShell을 통한 OpenSSH 설치를 시도하는데, 어느 경우든 기존에 이미 가진 권한 이상을 넘보지는 않는다. 셋째, 포트를 0으로 지정한 리버스 SSH 터널을 공격자 서버(134.209.82.225)로 열어, 서버가 동적으로 할당한 포트를 통해 피해자의 22번 포트로 되돌아오는 경로를 만든다. autossh가 있으면 그것을, 없으면 평범한 ssh를 60초 간격 재시도 루프로 백그라운드에서 돌린다. 넷째, OS별로 서로 다른 지속성 메커니즘을 심는다. macOS에서는 com.apple.sysmond로 위장한 LaunchAgent, 리눅스에서는 재부팅 시 실행되는 crontab 항목, 윈도우에서는 SysMon이라는 이름의 예약 작업이나 시작 프로그램 스크립트다. 마지막으로 호스트명, 사용자명, OS, 공인 IP, Git 이메일, 키 관련 패턴에 맞는 환경 변수 이름(값은 제외) 등을 담은 정찰 정보를 평문 HTTP POST로 공격자 서버에 한 차례 전송한다.

흥미롭게도 macOS 버전에는 구현상의 결함이 있었다. systemsetup -getremotelogin 명령을 관리자 권한 없이 실행하면 오류를 출력하면서도 종료 코드는 0을 반환하는데, 스크립트는 이 출력에서 "Off"라는 문자열을 찾으려 했기 때문에 조건이 성립하지 않아 원격 로그인 활성화 단계를 건너뛰었다. 그 결과 이미 SSH가 켜져 있지 않은 macOS 사용자의 경우 키와 지속성 메커니즘은 심어졌어도 외부에서 즉시 접속하는 경로는 막혀 있었을 가능성이 크다. 다만 Phorion은 이것이 안전망으로 작동한다고 보장할 수 없다고 못박았다. 사용자가 나중에 원격 로그인을 켜는 순간 백도어는 정상 작동하기 때문이다.

Phorion은 탐지와 사후 조치를 위한 구체적인 흔적도 함께 공개했다. 변조된 extension.js의 SHA-256 해시, 공격자가 심은 로그인용 키와 터널용 키의 SHA256 지문, 리버스 터널 목적지인 134.209.82.225의 22번 포트와 8099번 포트(POST /beacon 경로), 그리고 macOS의 ~/Library/LaunchAgents/com.apple.sysmond.plist, 리눅스의 @reboot crontab 항목, 윈도우의 SysMon 예약 작업과 같은 OS별 지속성 흔적이 그것이다. 중요한 것은 확장을 삭제하는 것만으로는 백도어가 제거되지 않는다는 점이다. Phorion은 터널 프로세스와 재시도 루프를 먼저 중단하고, OS별 지속성 아티팩트를 모두 걷어낸 뒤, authorized_keys에서 svc-telemetry 키를 제거하고, 해당 계정이 접근할 수 있던 자격 증명 전체를 교체하라고 권고했다. 확장 하나를 지우는 몇 초짜리 조치로는 복구가 끝나지 않는다는 뜻이다.

## "Anthropic 제작"이라는 이름표가 가진 무게

이번 사건에서 가장 많은 논쟁을 낳은 지점은 기술적 세부사항이 아니라 책임 소재였다. Hacker News의 관련 스레드에서 Anthropic 소속으로 알려진 개발자 felixrieseberg는 "악의적인 행위자가 Cursor 마켓플레이스에 대한 접근 권한을 이용해 Claude Code 확장의 변조된 복제본을 게시했다"고 설명하며, 이는 Anthropic의 시스템이나 직원 노트북이 뚫린 사건이 아니라고 선을 그었다. 같은 조직의 ddworken도 문제의 2.1.313 버전이 OpenVSX나 공식 VS Code 마켓플레이스, Anthropic 자체 호스트에는 한 번도 게시된 적이 없다는 점을 강조했다.

하지만 HN 댓글에서 tzone은 확장이 Anthropic의 브랜드를 달고 있는 이상 "Anthropic의 문제이기도 하다"고 반박하며, Anthropic이 직접 통제하는 키로 서명하거나 아예 브랜딩을 떼어내야 한다고 주장했다. ghshephard 역시 "Made by Anthropic"이라는 표시를 서명된 아티팩트로 오해했다고 털어놓으며, Cursor의 서명 체계 도입과 더불어 Anthropic이 자사 이름의 무단 도용을 상표권 차원에서 단속해야 한다고 요구했다. bagels는 이 논쟁을 "Anthropic의 문제이기도 하고, Cursor의 문제이기도 하다"는 한 문장으로 요약했다. 반대편에서 IshKebab과 dboreham은 공격자가 그저 "Anthropic.claude-code"라는 이름으로 확장을 올렸을 뿐이고 이를 걸러내지 못한 것은 명백히 Cursor의 실패라고 못박았다.

더 근본적인 문제는 VS Code 확장 생태계 자체의 검증 공백이다. AtNightWeCode는 VS Code 확장이 애초에 서명을 요구하지 않는다는 설계를 "말도 안 되게 어리석은 결정"이라 평했다. 그러나 Rohansi가 지적했듯, Cursor 마켓플레이스는 OpenVSX를 미러링하면서 자체 추가 확장을 끼워 넣는 독립된 운영 주체이기 때문에, 서명 체계가 있어도 이름 자체를 도용하는 위장 행위까지는 막지 못한다. Lazare는 한발 더 나아가 "Open VSX에는 사실상 보안이랄 게 없다"고 잘라 말했다. 이런 구조를 두고 yunnpp는 Let's Encrypt식 도메인 검증 모델을 제안했지만, Rohansi는 이것이 모든 퍼블리셔에게 도메인 구매와 갱신을 강제한다는 부담을 지적했고, dkersten는 "제작사" 표시가 필요한 경우에만 선택적으로 검증을 요구하는 절충안을 내놓았다.

사고 대응 커뮤니케이션 자체도 도마에 올랐다. 보안 사고 대응 경험이 있다고 밝힌 bostik은 Anthropic의 공식 커뮤니케이션이 부실했고, 실제 기술적 세부사항은 별도의 Mastodon 스레드를 통해서야 흘러나왔다고 비판했다. troupo와 giancarlostoro도 Anthropic이 공식 성명 대신 직원 개개인의 비공식 게시물에 의존하고 있다고 지적했으며, Rapzid는 애초에 Cursor 측 자격 증명이 어떻게 유출되어 악성 버전을 게시할 수 있었는지조차 아무도 설명하지 않았다는 점을 짚었다. 한편 실무 차원의 대응도 엇갈렸다. bg24는 주요 AI 기업들이 마켓플레이스에서의 사칭 공격면 자체를 줄여야 한다고 주장했고, bhouston과 satellites처럼 아예 Cursor를 떠나 VS Code와 터미널 기반 에이전트 조합으로 돌아갔다고 밝힌 개발자들도 있었다.

## 전망과 시사점

이번 사건은 고립된 사고가 아니라 패턴의 일부로 읽어야 한다. AI 코딩 도구가 짧은 기간에 폭발적으로 확산되면서, 그 이름값을 노리는 공격자에게도 그만큼 매력적인 표적이 늘어났다. 이 블로그가 최근 다뤘던 OpenCode 콘솔 유출이나 LLM 프록시를 거치지 않은 에이전트의 불투명한 행동, WhatsApp 도움말 페이지에 숨어 있던 LLM 지시문 사례와 마찬가지로, 공통된 축은 AI 도구를 둘러싼 신뢰 인프라가 도구 자체의 발전 속도를 따라가지 못한다는 것이다. 다만 이번 사건은 벡터가 다르다. 패키지 레지스트리에 악성 코드를 심는 공급망 공격이 아니라, 신뢰받는 이름 자체를 복제해 마켓플레이스의 검증 공백을 파고드는 상표 사칭형 공격이다.

낙관적 시나리오는 이번 사건을 계기로 VS Code 확장 생태계 전반에 서명 검증과 퍼블리셔 신원 확인이 표준화되는 것이다. 실제로 darkwi11ow는 Eclipse 재단과 협력한 OpenVSX 패키지 서명 체계를 제안했고, skydhash는 리눅스 배포판이 소수의 신뢰 서클을 통해 출처를 보증하는 모델을 참고 사례로 들었다. 비관적 시나리오는 Cursor 마켓플레이스처럼 메이저 플랫폼의 그림자에서 운영되는 중소 마켓플레이스가 계속 늘어나면서, 검증 부담이 분산된 채로 방치되는 것이다. 현실적으로는 당분간 기업 차원의 방어가 먼저 움직일 가능성이 크다. LooseMarmoset이 전한 것처럼 이미 일부 대기업은 VS Code 확장을 기본 차단하고 승인제로 운영하고 있으며, ashishb가 제안한 에이전트 샌드박싱(홈 디렉터리 전체가 아니라 필요한 범위로만 접근을 제한하는 방식)도 단기적으로 실질적인 완화책이 될 수 있다.

npm의 event-stream 사건이나 xz-utils 백도어처럼, 오픈소스 공급망을 겨냥한 공격은 매번 "이번엔 패키지 레지스트리가 문제였다"는 식으로 특정 생태계의 결함으로 좁혀서 기억된다. 하지만 패턴을 넓혀 보면 공통점은 더 단순하다. 개발자가 이름과 다운로드 수, 그럴듯한 설명만으로 코드를 신뢰하고 자신의 실행 환경에 끌어들인다는 것이다. VS Code 확장도, npm 패키지도, PyPI 패키지도 구조만 다를 뿐 신뢰 모델의 공백은 동일하다. Claude Code처럼 이름값이 큰 AI 코딩 도구일수록 그 공백을 파고드는 공격의 기대 수익도 커진다는 점에서, 이번 사건은 다음 사건의 예고편에 가깝다.

## 결론

"Anthropic 제작"이라는 문구는 지금 이 순간에도 암호학적 서명이 아니라 그저 신뢰해 달라는 요청에 불과하다. 개발자가 확장을 설치할 때 실제로 검증하는 것은 이름과 로고뿐이고, 그 이름을 보증하는 장치는 플랫폼마다 제각각이거나 아예 없다. bostik이 지적했듯 이번 사건에서 실질적인 기술 정보가 공식 성명이 아니라 개별 개발자의 비공식 포스트를 통해 흘러나왔다는 점도, 신뢰의 공백이 사고 대응 커뮤니케이션에서조차 반복되고 있음을 보여준다. 질문은 단순하다. 당신이 다음에 설치할 확장의 이름표는, 누가 보증하고 있는가.
