# LiteLLM 공급망 침해 사건 — AI 개발 도구 레지스트리는 왜 뚫렸는가

> 패키지 매니저의 신뢰 모델은 소스 코드를 검증하는가, 빌드 파이프라인을 검증하는가. 2026년 10월 21일 PyPI에 올라온 LiteLLM 1.107.0은 이 둘이 전혀 다른 질문이라는 사실을 보여주었다.

## 도입

LiteLLM은 OpenAI, Anthropic, Google 등 서로 다른 LLM 제공자의 API를 하나의 인터페이스로 통합해 주는 오픈소스 프록시 라이브러리다. 수많은 AI 애플리케이션과 에이전트 프레임워크가 이 라이브러리를 거쳐 모델 호출을 라우팅한다. 2026년 10월 21일, 이 라이브러리의 1.107.0 버전이 PyPI에 올라온 지 약 두 시간 만에 삭제되는 사건이 벌어졌다. 보안 업체 SafeDep의 분석에 따르면, 해당 버전에는 자격 증명 탈취기와 원격 코드 실행이 가능한 백도어가 심어져 있었다. Linux, macOS, Windows용 wheel 7개가 모두 영향을 받았고, 같은 버전의 Docker 이미지도 Docker Hub와 GHCR에서 약 두 시간 반 동안 오염된 상태로 배포되었다. 공격자는 코드 저장소를 직접 수정하지 않았다. 대신 패키지 빌드 설정 파일에 단 한 줄을 추가해, 업스트림 GitHub 소스에는 전혀 보이지 않는 파일들을 최종 배포판에만 몰래 끼워 넣었다. 이 사건이 드러낸 것은 단순한 패키지 하나의 취약점이 아니라, AI 개발 도구가 서로를 신뢰하며 연결되는 공급망 전체의 구조적 위험이다.

## 침해의 전말 — 한 줄의 빌드 설정이 만든 틈

공격의 시작점은 LiteLLM 팀 내부에 있었다. SafeDep의 분석에 따르면 공격자는 개발자 세 명의 GitHub CLI 자격 증명을 확보하고 있었다. 이 자격 증명이 어떻게 유출되었는지는 LiteLLM 메인테이너 측의 설명과 외부 분석이 엇갈린다. 메인테이너 detente18은 HN 토론에서, Claude Code가 GitHub CLI OAuth 토큰을 도구 호출 응답에 포함시켰고, 이 값이 요청·응답 로깅 과정에서 그대로 기록되어 유출되었다고 설명했다. 여러 조건이 겹쳐야 성립하는 "정교한 공격"이었다는 것이다. 그러나 다른 개발자 fny는 이를 "새로운 공격 기법이 아니라 새로운 과실"이라고 반박했다. 로그에 비밀 값이 남는 사고는 오래전부터 알려진 패턴이고, 이를 막는 로그 스캐너를 두지 않은 쪽의 책임이라는 지적이다.

탈취된 자격 증명으로 공격자는 조직 소유자 권한의 토큰을 손에 넣어 브랜치 보호 규칙을 우회했다. 이후 비공개 릴리스 워크플로를 수정해, 대문자 하나만 다른 유사 이름의 저장소 "Berri-AI/litellm"에서 빌드가 실행되도록 바꿨다. 두 번째 개발자의 자격 증명으로 승인 게이트까지 통과시키자, 공식 CI/CD 파이프라인이 변조된 소스를 정상적으로 빌드하고 서명하고 배포했다. 타임라인은 다음과 같다. 10월 21일 10시 8분(UTC) 브랜치 보호 우회와 워크플로 변경이 일어났고, 10시 46분 스테이징 빌드가 실행되었으며, 11시 39분부터 40분 사이 악성 wheel 7개가 PyPI에 업로드되었다. 11시 46분에는 같은 코드를 담은 Docker 이미지가 Docker Hub와 GHCR에 게시되었다. PyPI가 해당 릴리스를 삭제한 시각은 13시 23분으로, 노출 시간은 약 한 시간 사십 분이었다.

변조의 흔적은 공개 저장소의 커밋 기록에는 전혀 남지 않았다. 유일한 가시적 변경점은 sdist의 `pyproject.toml`에 추가된 `[tool.maturin]` 섹션의 `data = "cook"` 한 줄뿐이었다. 이 설정 때문에 wheel을 빌드할 때 `cook/` 폴더가 `site-packages`에 통째로 복사되었지만, sdist 자체에는 그 폴더가 존재하지 않았다. 즉 소스 코드를 아무리 검토해도 찾을 수 없고, 빌드 산출물을 직접 열어 봐야만 드러나는 종류의 침해였다. 설치된 세 파일 중 `cook.pth`는 파이썬이 시작할 때 자동으로 `cook` 모듈을 import해 탈취기를 구동시켰고, `sitecustomize.py`는 `litellm`을 import하지 않는 프로세스에서도 로드되는 파이썬의 특수 파일이었다. 두 메커니즘 모두 패키지를 실제로 사용하지 않는 환경에서조차 코드가 실행되게 만든다는 공통점을 가진다.

탈취기 `cook.py`는 약 61킬로바이트 분량의 코드를 zlib과 base64로 압축해 숨겼으며, 수집 대상은 16개 범주에 이른다. 브라우저에 저장된 비밀번호와 방문 기록, SSH 키, 셸 명령 기록, AWS·Azure·GCP 클라우드 자격 증명과 kubeconfig, GitLab·Jenkins·Terraform의 CI/CD 비밀, 그리고 Claude Code·Cursor·GitHub Copilot·Codex 같은 AI 개발 도구의 토큰까지 포함되었다. 특히 LiteLLM 프록시 자체의 데이터베이스에 저장된 LLM 제공자 API 키까지 노렸다는 점은, 이 공격이 LLM 인프라를 다루는 개발자를 정조준했음을 보여준다. 수집한 데이터는 무작위 AES-256-CBC 키로 암호화한 뒤 그 키를 다시 내장된 RSA-4096 공개 키로 감싸, `www.litellm[.]dev`라는 공식 도메인과 흡사한 주소로 전송했다. `sitecustomize.py`에 심긴 두 번째 페이로드는 한 시간마다 공격자의 GitHub 저장소에서 명령 서버 주소를 읽어와 추가 코드를 내려받아 실행하는 백도어 데몬이었다. 다행히 SafeDep이 확인한 13시 40분, 해당 GitHub 계정은 이미 404 상태였다. 그러나 그 이전에 감염된 호스트가 이미 2단계 코드를 내려받아 실행했을 가능성은 배제되지 않는다.

## PyPI 신뢰 모델의 구조적 한계 — 서명은 무엇을 증명하는가

이 사건이 흥미로운 이유는 공격자가 PyPI 계정 자체를 탈취하지 않았다는 데 있다. HN 토론에서 zahlman은 이 지점을 가장 날카롭게 짚었다. 그는 악성 `.pth` 파일이 겉보기에는 평범한 데이터 파일로 포장되어 `site-packages`에 설치되고, 파이썬이 시작할 때 임의 코드를 실행하게 만든다고 설명했다. 이런 구조에서는 패키지가 실제로 import되는지 여부가 중요하지 않다. 설치되는 순간 이미 코드 실행 권한을 얻기 때문이다. 그는 또한 PyPI가 도입한 "신뢰된 퍼블리싱(Trusted Publishing)" 체계도, 공격자가 여러 메인테이너 계정과 CI 파이프라인 자체를 장악한 경우에는 우회될 수 있다고 지적했다. 서명과 증명서(attestation)는 "이 코드가 변조되지 않았다"를 보장하는 장치가 아니라, "이 빌드가 등록된 파이프라인에서 나왔다"를 보장하는 장치에 가깝다는 것이다. Aurornis와 madamelic도 비슷한 지적을 내놓았다. 공격이 일어난 지점은 PyPI 계정이 아니라 비공개 빌드 파이프라인이었고, 파이프라인이 변조된 소스로 빌드하더라도 서명과 증명서는 정상적으로 발급된다. 결국 공개된 태그에서 독립적으로 다시 빌드해 배포된 아티팩트와 비교하는 재현 가능한 빌드(reproducible build) 검증 없이는, 서명이 있다는 사실만으로 안전을 보장할 수 없다는 뜻이다.

대응책을 둘러싼 논쟁도 갈렸다. LiteLLM 측 abhisek은 패키지를 설치하기 전 24시간 정도의 쿨다운(cooldown)만 두어도 이번처럼 급조된 공격의 상당수를 막을 수 있다고 주장했다. 이번 공격이 새로 등록한 유사 도메인을 명령 서버로 쓰고, 이미 알려진 `.pth` 기법을 그대로 사용한, 기법 자체는 새롭지 않은 공격이었다는 것이 근거였다. 그러나 lrvick은 쿨다운이 공격을 막는 게 아니라 발견 시점을 늦출 뿐이며, 핵심은 "무엇을 검토하느냐"라고 반박했다. 그는 주요 오픈소스 코드에 대한 조직적인 검토 체계와, 재현 가능하고 서명된 릴리스 관행을 함께 요구했다. 실무적인 반론도 적지 않았다. robinhoodexe는 내부 PyPI 프록시에 7일 쿨다운을 걸어 두었다가, 정작 필요한 보안 업데이트까지 지연되는 부작용을 겪었다고 전했다. 공격이 쿨다운 기간보다 오래 잠복한다면 쿨다운 자체가 무의미해진다는 지적도 나왔다. 샌드박스로 위험을 줄이자는 제안(isityettime) 역시, 샌드박스 도구 자체도 같은 방식의 공급망 공격에 노출될 수 있다는 반론(drdaeman)에 부딪혔다. 결국 이 논쟁이 수렴한 지점은 하나다. 어떤 단일 장치도 공급망 신뢰 문제를 완전히 해결하지 못하며, 쿨다운·재현 빌드·격리·로그 위생 같은 여러 장치를 겹겹이 쌓는 것만이 현실적인 완화책이라는 것이다.

이번 사건은 LiteLLM에게 처음 겪는 보안 사고가 아니었다는 점도 논쟁을 키웠다. TZubiri, staticman2, atmosx 등은 반복되는 사고 앞에서 "애초에 이 의존성이 꼭 필요한가"를 되물었다. 여러 제공자의 API를 하나의 인터페이스로 묶어 주는 라우팅 기능은, 호출하는 엔드포인트 주소 하나만 OpenAI 호환 규격에 맞춰 바꾸면 자체 구현으로도 대체 가능하다는 것이다. 반대로 특정 버전에 의존성을 고정해 두면 새로 나오는 모델을 지원받지 못하는 손해가 따른다는 반론도 나왔다. 또 다른 갈래의 논쟁은 LiteLLM이 엔터프라이즈 고객에게 공개 패치보다 먼저 비공개 레지스트리로 수정판을 제공한다는 사실이 알려지면서 불거졌다. hmokiguess와 petesergeant는 보안 패치를 돈을 낸 고객에게 먼저 주는 구조 자체가 문제라고 비판했다. 이에 대해 LiteLLM 직원 chias는, 패치를 공개하는 순간 사실상 취약점 내용을 공개하는 것과 다름없기 때문에 엔터프라이즈 고객에게 먼저 배포해 대응 시간을 벌어 주는 것이라고 해명했다. 어느 쪽이 옳다고 단정하기는 어렵지만, 이 논쟁은 오픈소스 보안 패치의 공개 시점을 둘러싼 오래된 딜레마가 AI 인프라 라이브러리에서도 똑같이 반복되고 있음을 보여준다.

## 전망과 시사점 — AI 개발 도구가 서로를 신뢰하는 시대의 위험

LiteLLM이 표적이 된 것은 우연이 아니다. 이 라이브러리는 수많은 AI 에이전트 프레임워크와 애플리케이션이 LLM 제공자에 접근하는 관문 역할을 한다. 공격자가 탈취 대상 목록에 Claude Code, Cursor, GitHub Copilot, Codex 같은 AI 코딩 도구의 토큰을 명시적으로 포함시킨 사실은, 공급망 공격의 표적이 더 이상 전통적인 서버 인프라에 그치지 않는다는 것을 보여준다. AI 코딩 에이전트는 개발자의 셸 권한, 클라우드 자격 증명, 저장소 접근 권한을 폭넓게 위임받는 경우가 많다. 이런 에이전트가 설치하는 의존성 하나가 오염되면, 탈취 범위는 단순한 API 키를 넘어 개발 환경 전체로 확장된다. 실제로 이번 사건의 최초 침투 경로 자체가, Claude Code의 도구 호출 로그에 남은 자격 증명이었다는 점은 이 악순환을 상징적으로 보여준다.

HN 토론에서 joshheitzman이 "에이전트에게 셸 권한을 주지 않고, 커밋과 배포는 직접 한다"고 밝힌 태도는 당분간 현실적인 방어선이 될 가능성이 크다. 동시에 eddythompson80의 지적처럼, 자동화된 공격 도구 앞에서 "정교한 공격"이라는 표현 자체가 점점 의미를 잃고 있다는 점도 주목할 만하다. 과거에는 조직적인 국가 배후 공격자나 숙련된 해커 집단만 시도할 법했던 빌드 파이프라인 탈취가, 이제는 유출된 토큰 하나와 유사 이름 저장소 하나로도 실행 가능한 수준이 되었다. 패키지 생태계가 재현 가능한 빌드와 독립적인 아티팩트 검증을 표준으로 받아들이지 않는 한, 이런 사건은 LiteLLM이 아니라 다음 인기 라이브러리에서 반복될 것이다.

## 결론

이번 사건은 두 시간 안에 발견되고 차단되었다는 점에서 '성공적으로 막은 사고'로 분류될 수도 있다. 그러나 그 두 시간 동안 이미 설치된 호스트들, 그리고 백도어 데몬이 외부 서버에 접속할 수 있었던 짧은 창은 여전히 열려 있었다. PyPI의 서명 체계도, 신뢰된 퍼블리싱도, 빌드 파이프라인 자체가 장악된 공격 앞에서는 똑같이 무력했다. 질문은 이제 "어떻게 하면 이런 사고를 완전히 막을 것인가"가 아니라, "이런 사고가 두 시간이 아니라 이틀, 혹은 두 달 동안 발견되지 않았다면 무엇이 달라졌을까"에 가깝다. AI 개발 도구들이 서로의 자격 증명과 권한을 점점 더 깊이 위임하는 지금, 공급망의 약한 고리 하나를 찾아내는 비용은 계속 낮아지고 있다. 재현 가능한 빌드, 격리된 자격 증명 주입, 로그 위생이라는 세 가지 장치 중 어느 하나라도 갖추지 않은 조직이라면, 다음 차례가 자신이 아니라고 장담하기 어렵다.
