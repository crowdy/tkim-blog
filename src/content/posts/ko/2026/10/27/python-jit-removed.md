# 파이썬 실험적 JIT 철회 — 호환성이라는 벽은 왜 넘기 어려운가

> 느려도 모두가 쓸 수 있는 언어로 남을 것인가, 빨라지되 일부를 떨어뜨리는 언어가 될 것인가. 파이썬 코어 팀이 2년의 실험 끝에 내놓은 답은 전자에 가까웠다.

## 도입

2026년 10월 19일, 파이썬 코어 개발자 Savannah Ostrowski는 표준 트랙 PEP 836("JIT Go Brrr")을 철회한다고 공지했다. 이유는 거창하지 않았다. 팀의 가용 역량(bandwidth)이 더 이상 이 작업을 지속하기 어렵다는 것이었다. 이 발표 하나로, 2024년 초 Brandt Bucher가 CPython 3.13에 병합했던 실험적 JIT 컴파일러는 사실상 종료 수순에 들어갔다. Brett Cannon은 main 저장소에서의 작업이 중단되며, JIT 코드 자체는 Python 3.16 개발 주기 초반에 제거될 것이라고 밝혔다.

표면적으로는 한 기능의 조용한 퇴장처럼 보인다. 그러나 이 결정에 이르기까지의 2년은 파이썬이라는 언어가 성능과 호환성, 실험과 안정성 사이에서 어떤 기준으로 판단하는지를 드러내는 사례였다. Bucher는 애초에 표준 트랙 PEP 없이 JIT를 병합했고, 그 설계는 비공식 정보성 문서인 PEP 744로만 설명됐다. 2026년 6월 스티어링 카운슬이 "6개월 안에 정식 PEP를 내지 않으면 코드를 제거하겠다"고 못 박은 순간부터, 이 실험은 명확한 시한부 판정을 받은 셈이었다.

파이썬은 이미 세계에서 가장 널리 쓰이는 언어 중 하나이면서도, 동시에 "느린 언어"라는 꼬리표를 수십 년째 달고 있다. 그 꼬리표를 떼려는 시도는 이번이 처음이 아니다. Unladen Swallow, Pyston, 그리고 Meta가 사내에서 운영해 온 Cinder까지, CPython에 JIT를 붙이려는 시도는 반복적으로 등장했다가 메인 저장소로 역병합되지 못한 채 흩어졌다. 2024년의 실험적 JIT는 그중 처음으로 공식 CPython 배포판 안에 들어온 시도였다는 점에서 의미가 컸다. 그렇기에 이번 철회는 단순한 기능 하나의 문제가 아니라, "CPython 안에서 JIT가 생존할 수 있는가"라는 오래된 질문에 대한 또 하나의 데이터 포인트로 읽어야 한다.

## 실험에서 철회까지, 2년의 타임라인

이야기는 2024년 초로 거슬러 올라간다. Bucher는 CPython 3.13에 실험적 JIT를 병합하면서 정식 PEP 승인 절차를 밟지 않았다. 대신 설계 의도를 설명하는 정보성 문서 PEP 744만 남겼다. 이런 방식 자체가 이례적이었다. 보통 CPython에 새로운 실행 모델을 들여올 때는 표준 트랙 PEP를 통해 커뮤니티 검토와 스티어링 카운슬의 승인을 거치는 것이 관례이기 때문이다. JIT는 "실험"이라는 이름 아래 이 절차를 우회한 채 메인 브랜치에 자리를 잡았다.

문제는 2년 가까이 이 실험 상태가 정리되지 않았다는 데 있었다. 2026년 6월, 스티어링 카운슬은 더 이상 이 상태를 방치할 수 없다고 판단하고 작업을 일시 중단시켰다. 카운슬이 요구한 것은 단순했다. 6개월 안에 표준 트랙 PEP를 제출해 이 기능을 정식으로 지원할지, 아니면 코드를 들어내고 실험을 끝낼지 결정하라는 것이었다. 이에 대한 응답으로 2026년 7월 3일, Ostrowski를 비롯한 팀이 PEP 836, 별명 "JIT Go Brrr"을 공개했다. 공개 직후 커뮤니티 피드백에서는 이 PEP가 다루는 범위가 너무 넓어 두 개의 문서로 나눠야 한다는 지적이 여러 차례 나왔다.

그리고 2026년 9월 21일, 스티어링 카운슬은 중간 응답을 내놓았다. 카운슬은 PEP가 제기된 질문들에 답을 하긴 했다고 인정하면서도, "일부 답변은 다른 답변만큼 설득력이 있지는 않았다"는 유보적인 평가를 달았다. 구체적으로 카운슬이 우려한 지점은 네 가지였다. 플랫폼 간 지원 수준의 불균형(플랫폼 패리티), 사용자에게 드러나는 동작 변화, 보안 영향, 그리고 호환성 검토 시점이 너무 늦다는 것. 카운슬은 호환성 검토가 2028년 8월로 예정된 Python 3.17 릴리스 후보 시점까지 미뤄지는 대신, 지금부터 지속적인 과정으로 이뤄지길 원한다고 명시했다.

결국 약 한 달 뒤인 10월 19일, Ostrowski는 제한된 역량을 이유로 PEP를 철회했다. 다만 완전한 포기는 아니었다. 그는 free-threaded 지원과 메서드 기반 프런트엔드를 포함한 기술적 방향성에 대해서는 여전히 확신이 있다고 밝혔고, 철회된 PEP에서 링크된 참조 구현을 별도로 공개하겠다고 했다. 커뮤니티가 이 작업을 CPython 바깥에서 이어갈 여지는 남겨둔 셈이다.

## 왜 호환성이 성능을 눌렀는가

이 사건의 핵심은 단순한 일정 관리 실패가 아니다. 더 구조적인 질문, 즉 CPython이라는 플랫폼의 설계 철학과 JIT라는 최적화 기법이 근본적으로 긴장 관계에 있다는 사실이 드러난 것에 가깝다.

CPython의 C API는 인터프리터 내부의 포인터를 외부 확장 모듈에 직접 노출하는 구조를 갖고 있다. NumPy, Pandas, 수많은 C 확장 라이브러리가 이 API에 의존해 동작한다. JIT 컴파일러가 성능을 극대화하려면 인터프리터 내부 표현을 자유롭게 바꾸고 최적화할 수 있어야 하는데, C API 호환성을 유지하려면 바로 그 내부 표현을 함부로 바꿀 수 없다. 두 요구는 서로 충돌한다. JIT가 C API 호환성을 철저히 지키는 쪽을 택하면 최적화의 여지가 줄어들고, 반대로 최적화를 우선하면 기존 확장 모듈들이 깨질 위험이 커진다. 스티어링 카운슬이 "사용자에게 드러나는 동작 변화"를 명시적으로 우려 사항에 올린 것은 바로 이 지점을 겨냥한 것이다.

여기서 흥미로운 비교 대상이 PyPy와 GraalPy 같은 대안 구현체들이다. 이들은 이미 CPython보다 훨씬 공격적인 JIT 최적화로 더 큰 성능 향상을 보여준다. 그런데도 파이썬 생태계 전체가 이들로 옮겨가지 않는 이유는 명확하다. 지원되는 파이썬 버전이 제한적이고, C 확장 모듈과의 호환성이 완전하지 않으며, 기존 툴체인과의 통합이 매끄럽지 않기 때문이다. 즉 "더 빠른 파이썬"은 이미 존재하지만, 실무에서 그것을 채택하는 비용이 성능 이득을 넘어서는 경우가 많다는 것이다.

이 구도를 CPython 내장 JIT에 대입하면 문제가 선명해진다. CPython에 JIT를 넣는 시도는 PyPy가 이미 증명한 성능 이득을 "호환성을 희생하지 않는 선"에서 재현하려는 시도였다. 그런데 호환성을 지키기 위해 타협할수록 JIT가 낼 수 있는 성능 이득은 줄어든다. HN 토론에서도 이 지점을 지적하는 댓글들이 눈에 띄었다. 한 개발자는 JIT가 가져다준 실측 성능 향상이 구현에 들인 공학적 난이도에 비해 크지 않았다고 평가했고, 다른 댓글은 애초에 진짜 속도가 필요한 작업은 Cython이나 Rust로 작성한 확장 모듈이 이미 그 역할을 떠맡고 있어 JIT의 존재 이유 자체가 좁아졌다고 지적했다. 즉 JIT가 해결하려던 문제의 상당 부분을, 다른 방식으로 이미 풀어놓은 생태계가 존재했던 셈이다.

스티어링 카운슬이 진짜로 문제 삼은 것은 "JIT를 지원할 것인가 말 것인가"가 아니었다. 더 근본적인 문제는 통일된 설계 없이 실험이 메인 브랜치에서 2년 가까이 지속되는 상황 그 자체였다. 핵심 개발자는 자신이 건드리는 코드가 JIT와 상호작용할지 매번 확인해야 했고, 패키지 메인테이너는 C 확장 모듈이 미래에도 계속 동작할지 장담할 수 없었으며, 일반 사용자는 자신이 쓰는 파이썬 버전의 성능 특성이 언제 바뀔지 예측할 수 없었다. 불확실성 자체가 비용이라는 인식이 이번 철회 결정의 바탕에 깔려 있다.

같은 문제를 다른 조직이 먼저 겪은 전례도 있다. Meta가 사내용으로 만든 Cinder는 처음부터 "완전한 C API 호환성을 포기하는 대신 더 큰 성능을 얻는다"는 방향으로 설계됐고, 그 결과 Instagram 서버 스택처럼 Meta가 통제하는 환경에서는 유의미한 성능 향상을 냈지만 범용 CPython으로 역병합되지는 못했다. 즉 "호환성을 전부 지키면서 큰 폭의 성능을 얻는다"는 목표 자체가 CPython 같은 범용 공개 런타임에서는 거의 모순에 가깝다는 사실을, 업계는 이미 여러 차례 다른 경로로 확인해 온 셈이다. 이번 PEP 836 철회는 그 모순이 CPython 코어 안에서도 똑같이 재현됐다는 추가 증거에 가깝다.

## 언어 런타임 투자가 남긴 교훈

이번 사례가 보여주는 것은 오픈소스 언어 런타임에 새로운 실행 모델을 들이는 일이 구조적으로 얼마나 어려운지다. 표준 트랙 PEP 없이 실험을 먼저 병합하고 나중에 정식화하는 방식은, 당장 코드를 돌려보고 커뮤니티 반응을 빠르게 확인할 수 있다는 점에서 매력적이다. 하지만 "실험"이라는 이름표가 붙은 코드가 메인 브랜치에 장기간 머무르면, 그 코드와 상호작용해야 하는 모든 당사자에게 암묵적인 부채를 지우게 된다. 이번 PEP 836 철회는 그 부채가 결국 청구되었다는 신호로 읽을 수 있다.

실무자 입장에서 이 사건이 주는 시사점은 두 가지다. 첫째, 파이썬에서 당장 큰 폭의 성능 향상이 필요하다면 CPython 자체의 JIT를 기다리기보다는 PyPy, GraalPy, 혹은 C/Rust 확장을 통한 우회로가 여전히 현실적인 선택지라는 점이 재확인됐다. 둘째, free-threaded 파이썬(GIL 제거)과 JIT가 묶여서 논의돼 온 그간의 흐름에서, 이번 철회로 JIT 쪽은 당분간 커뮤니티 주도 프로젝트로 넘어갈 가능성이 크다는 점이다. Ostrowski가 참조 구현을 공개하겠다고 밝힌 만큼, CPython 바깥에서 이 작업을 이어받는 포크나 별도 프로젝트가 등장할 여지는 남아 있다.

더 넓게 보면, 이번 결정은 스티어링 카운슬이라는 거버넌스 구조가 실제로 작동하고 있다는 증거이기도 하다. 유력 코어 개발자가 이미 메인 브랜치에 병합해 둔 기능이라도, 정식 승인 절차를 거치지 않으면 결국 되돌려질 수 있다는 전례가 만들어진 것이다. 앞으로 CPython에 실험적 기능을 제안하려는 개발자들은 "일단 넣고 본다"는 전략이 더는 안전하지 않다는 점을 염두에 둬야 할 것이다.

성능에 민감한 조직의 입장에서 보면 이번 철회는 당장의 마이그레이션 계획을 바꿀 사건은 아니다. JIT는 어디까지나 실험 플래그 뒤에 숨어 있던 기능이었고, 기본값으로 꺼져 있었기 때문에 이를 적극적으로 켜서 운영 환경에 쓰고 있던 조직은 애초에 많지 않았을 것이다. 다만 "CPython이 머지않아 자체 JIT로 PyPy 수준의 성능을 낼 것"이라는 기대를 품고 로드맵을 짜고 있었다면, 그 전제를 다시 검토해야 한다. 당분간 파이썬에서 CPU 바운드 작업의 성능을 끌어올리는 현실적인 경로는 여전히 NumPy·Numba 같은 네이티브 확장, Rust/Cython으로 작성한 모듈, 혹은 PyPy·GraalPy로의 부분적 이전이다.

## 결론

파이썬 코어 팀이 내린 선택은 단기적인 성능 향상보다 장기적인 생태계 안정성을 우선한 것으로 요약할 수 있다. CPython의 C API 호환성이라는 제약은 JIT가 낼 수 있는 성능 이득의 상한선을 낮췄고, 그 상한선이 2년에 걸친 실험과 검토를 정당화할 만큼 높지 않다는 결론에 코어 팀은 도달했다. 이는 파이썬이 성능 경쟁에서 손을 뗀다는 의미가 아니라, 성능을 추구하는 방식을 어디에 둘 것인가에 대한 재확인에 가깝다. 수백만 개의 기존 C 확장 모듈과 수십 년 쌓인 하위 호환성 위에서 돌아가는 언어에게, 속도는 언제나 두 번째 우선순위였다. 다음 질문은 이것이다. CPython 바깥에서 이 실험을 이어받을 공동체가 실제로 나타날 것인가, 아니면 파이썬의 성능 과제는 또다시 PyPy와 확장 모듈의 몫으로 남겨질 것인가.
