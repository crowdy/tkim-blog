# 자체 LLM 프록시 없이, 에이전트가 무엇을 하는지 어떻게 아는가

> LLM 트래픽의 가시성은 경로를 소유해야 얻어지는 것인가, 아니면 하네스가 내보내는 텔레메트리로 충분한가?

## 도입

2026년 10월 18일, Jared Siegel이 자신의 블로그에 3분 분량의 짧은 글을 올렸다. 제목을 순화해 옮기면 「자체 LLM 프록시를 돌리지 않는다면, 대체 무슨 일이 일어나는지 어떻게 아는가」다. 원제에는 비속어가 들어 있고, 글의 문체도 그만큼 거칠다. 해커뉴스에서는 비속어를 뺀 제목으로 올라가 300점을 받았고, 최상위 코멘트만 42개가 달렸다.

글의 주장은 단순하다. 우리는 대부분 어떤 벤더의 유료 구독에 연결된 프런트엔드, 즉 TUI든 GUI든 음성 통화든 무언가를 통해 모델과 대화한다. 내 데이터가 들어가고 그들의 데이터가 돌아온다. 저자는 그것을 사는 데 지금은 불만이 없다고 말한다. 문제는 벤더가 「일이 일어나고 있다는 증거」로 보여 주는 사용량 화면이다. 저자는 그것을 주의를 흐리는 장치라고 부르고, 엔지니어를 위한 시계열 토큰 사용량 통계가 아니며 그것으로는 아무 결정도 내릴 수 없다고 적는다.

이 글이 흥미로운 이유는 결론보다 댓글 쪽에 있다. 「프록시를 써라」는 글 아래에, 프록시는 단일 장애점이라는 반론, OpenTelemetry로 충분하다는 반론, 그 OpenTelemetry는 하네스가 보여 주고 싶은 것만 보여 준다는 재반론, 그리고 애초에 구독제에서는 프록시를 쓸 경제적 이유가 약하다는 지적이 차례로 쌓였다. 이 글은 그 논쟁을 정리해, 에이전트 트래픽의 관측 가능성을 어디서 확보해야 하는지 따져 본다.

## 현상 분석: 프록시가 보여 주는 것

먼저 원문이 제시한 근거를 그대로 옮긴다. 저자는 「OTel 내보내기 옵션이 있잖아」라는 반론을 미리 예상하고, 그것도 이유 중 하나일 뿐이라며 즉석에서 다섯 가지를 더 든다.

- 여러 제공자와 여러 모델을, 내가 통제하는 단일 엔드포인트에서 다룬다.
- 어떤 키가, 어떤 클라이언트로, 언제, 어떤 모델을 호출했고 상태가 무엇이었는지 로그가 남는다.
- 가상 API 키를 써서 하나뿐인 메인 키를 업무, 에이전트, 하네스 곳곳에 흩뿌리지 않는다.
- 내가 통제하는 인프라다.
- 모든 설정을 다시 하지 않고도 모델과 제공자를 아주 빠르게 바꿀 수 있다.

저자는 특정 프록시 제품을 추천하지 않는다. 자신이 통제하는 곳에서 직접 돌리라는 것, 그리고 고른 뒤에는 실제 필요에 맞춰 수정할 수 있다는 것만 강조한다. 그는 자신의 프록시를 더 나은 통찰을 위해, 그리고 커스텀 MCP 서버 엔드포인트 같은 추가 기능을 위해 고쳐 썼다고 밝힌다. 가장 구체적인 사례는 하나다. 코딩 세션 중에 캐시 미스가 보이면, 그 원인을 손으로 20초 안에 짚어 낼 수 있다는 것이다. 아직 자동화하지는 않았지만 그가 쓰는 프록시에 API가 있어 자동화도 가능하다고 덧붙인다.

이 「캐시 미스」 사례가 왜 중요한지는 댓글에서 드러난다. @viccis는 캐시 TTL이 결국 발목을 잡는다고 썼다. Claude 구독에서도 서브에이전트는 5분 TTL을 가지며, 그 사실을 알기 전까지 서브에이전트가 10분가량 걸리는 테스트를 기다리는 동안 5시간 사용 한도가 크게 깎였다는 것이다. 회사의 API 사용에서도 5분 TTL은 전혀 충분하지 않으며, 모니터링하지 않으면 회사 예산을 태우게 된다고 했다(직접 인용은 아니고, 코멘트의 요지를 요약). 이 진술 자체를 검증할 수는 없지만, 「캐시가 왜 깨졌는가」라는 질문은 벤더 대시보드의 일별 막대그래프로는 답할 수 없고 요청 단위의 기록이 있어야 답할 수 있다는 점은 분명하다.

프록시가 무엇을 해 주는지에 대한 가장 짧은 설명도 댓글에 있다. @andai는 LLM은 JSON API 위에서 동작하니 그 JSON을 읽으면 무슨 일이 일어나는지 알 수 있다고 했다. 남의 하네스를 쓸 때는 모델이 실제로 무엇을 보는지 알 수 없어 답답했고, 맥락이 LLM에서 거의 전부라는 점을 생각하면 그것이 문제라는 것이다. 가장 간단한 방법은 `OPENAI_API_URL` 같은 설정을 로컬호스트로 바꾸고, 요청을 그대로 전달하며 파일에 덤프하는 20줄짜리 Python 스크립트를 띄우는 것이라고 했다. 그리고 그것이 애초에 필요해서는 안 된다고 덧붙였다(직접 인용은 아니고, 코멘트의 요지를 요약).

즉 프록시가 드러내는 것은 크게 네 가지로 정리된다. 첫째, 실제로 전송된 프롬프트 전체, 다시 말해 하네스가 사용자 몰래 덧붙인 시스템 프롬프트와 도구 정의까지 포함한 맥락이다. @Havoc은 Claude Code가 처음 나왔을 때 프록시를 만져 봤지만 실행 가능한 통찰은 얻지 못했고, 얻은 것이라고는 Claude Code와 그 비대한 시스템 프롬프트를 버린 것뿐이라고 썼다(직접 인용은 아니고, 코멘트의 요지를 요약). 역설적이게도 그 「버린 결정」 자체가 프록시가 만든 결정이다. 둘째, 요청 단위의 토큰과 캐시 상태다. 셋째, 키와 클라이언트 단위의 귀속, 즉 누가 무엇을 썼는가다. @redmalang은 비용을 프로젝트 단위로 귀속시키는 데 쓰고 있고 그것이 실제로 꽤 유용하다고 답했다. 넷째, 비밀 관리다. @hoppp은 LiteLLM 프록시를 서버에 구축하는 중이라며, 가상 키를 발급할 수 있어 제공자 API 키가 샌드박스 근처에 가지 않는다는 점, 모든 것을 볼 수 있다는 점, 가드레일을 걸 수 있다는 점을 꼽았다. 그것 없이는 샌드박스 안의 에이전트들을 조율할 수 없다는 것이다(직접 인용은 아니고, 코멘트의 요지를 요약).

댓글에는 구체적인 도구 이름도 많이 나왔다. LiteLLM, GoModel, Bifrost, OpenRouter, Tailscale의 Aperture, mitmproxy가 언급됐고, 자작 프록시를 소개하는 댓글도 여럿이었다. 다만 그 상당수는 개발자 본인의 홍보였다는 점은 기억해 둘 만하다. LiteLLM의 메인테이너라고 밝힌 @ij23이 여러 스레드에 답을 달았고, GoModel을 소개한 @verdverm은 스스로를 열성 팬이라고 칭했다. 원문 저자가 자기가 무엇을 쓰는지 밝히지 않은 것을 두고 @jFriedensreich가 이상하다고 지적한 것도 같은 맥락에서 읽힌다.

## 심층 분석: 프록시가 떠안는 것, 그리고 OpenTelemetry라는 대안

가장 체계적인 반론은 @CharlieDigital에게서 나왔다. 요지는 이렇다. 이 일을 하는 데 프록시는 필요 없고, 오히려 쓰지 말아야 한다. 프록시는 생산성의 경로 한가운데 놓인 단일 장애점이 되기 때문이다. Codex와 Claude Code는 OTel 트레이스를 내보내고, OpenCode나 Pi 같은 다른 하네스는 플러그인 구조에 훅을 걸어 OTel을 직접 내보내면 된다. 컬렉터를 띄우거나 기존 컬렉터 인프라를 쓰면 도구 호출, 전체 프롬프트, 토큰 사용량과 비용이 모두 들어온다. 그리고 결정적으로 OTel 송신과 수집은 최선 노력(best-effort) 방식이라, 일부 트레이스를 잃어도 생산성 손실은 없다. 반면 장애가 나거나 과부하에 걸린 프록시는 해결될 때까지 팀 전체를 묶어 둔다(직접 인용은 아니고, 코멘트의 요지를 요약).

이 반론의 사실 부분은 확인할 수 있다. Claude Code의 공식 모니터링 문서는 OpenTelemetry로 메트릭을 시계열로, 이벤트를 로그 프로토콜로, 선택적으로 분산 트레이스를 내보낸다고 설명한다. 최소 설정은 환경 변수 몇 개다.

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
```

다만 문서를 자세히 읽으면 「전체 프롬프트가 들어온다」는 말에는 조건이 붙는다. 사용자 프롬프트 내용 기록(`OTEL_LOG_USER_PROMPTS`)과 도구 인자 기록(`OTEL_LOG_TOOL_DETAILS`)은 기본값이 비활성이다. 요청과 응답의 Messages API JSON 전체를 이벤트로 내보내는 `OTEL_LOG_RAW_API_BODIES`도 기본 비활성이며, 문서는 그 본문에 대화 이력 전체가 포함된다고 명시한다. 이 이벤트는 요청 시도마다 하나씩 나오므로 재시도도 각각 기록된다. 토큰 쪽에서는 `cache_read_tokens`와 `cache_creation_tokens`가 입력 토큰과 분리돼 보고된다. 다시 말해 원문 저자가 프록시로 하는 캐시 미스 추적은, 적어도 Claude Code에 한해서는 OTel로도 원리상 가능하다.

그런데 이 대안에는 구조적 한계가 있다. @ProjectBarks는 OTel에 대한 정당한 비판은 하네스가 보여 주려는 것만 보게 된다는 점이 아니냐고 물었다. 그는 AI 기업들이 내놓은 코딩 도구가 수집해서는 안 될 데이터를 수집한 사례들을 링크로 들며, 모든 하네스는 샌드박스에서 돌리고 네트워크 전체를 기록해야 한다고 주장했다(직접 인용은 아니고, 코멘트의 요지를 요약). 그가 든 개별 사례들은 이 글에서 검증하지 않았다. 하지만 논리 자체는 사례와 무관하게 성립한다. 자기 보고형 텔레메트리는 관측 대상이 관측 데이터를 생산하는 구조이고, 그 신뢰는 관측 대상에게 달려 있다. @InsidiousWombat의 한 줄 댓글도 같은 지점을 찌른다. OTel은 내가 무엇을 하는지 보여 줄 뿐, 상대가 내 질의로 무엇을 하는지는 보여 주지 않는다는 것이다.

그렇다고 프록시가 이 문제를 완전히 해결하는 것도 아니다. @jeena는 하네스가 오픈 소스가 아닌 한 프록시도 도움이 되지 않으며, 다른 서브도메인으로 몰래 통신하는 것은 쉽다고 지적했다(직접 인용은 아니고, 코멘트의 요지를 요약). LLM 프록시는 모델 API로 가는 트래픽만 본다. 하네스가 텔레메트리나 다른 데이터를 별도 경로로 보낸다면 그것은 프록시 바깥이다. 그래서 「신뢰하지 않는 하네스」를 전제로 하면 답은 프록시가 아니라 @ProjectBarks가 말한 VM 단위의 네트워크 로깅 쪽으로 간다. 관측의 층위가 셋으로 나뉘는 셈이다. 하네스가 스스로 보고하는 OTel, 모델 API 경로를 가로채는 프록시, 그리고 호스트의 모든 송신을 보는 네트워크 계층이다.

예방과 사후 분석의 차이도 있다. @pavelmelnichuk은 OTel은 프록시가 해결하는 것의 4분의 1에 불과하다며, 에이전트가 엉뚱한 토끼굴로 빠져 눈치채기 전에 100달러를 태우면 어떻게 하느냐고 물었다. OTel은 사고 뒤의 가시성을 주지만, 프록시는 하드 한도를 걸어 사고를 막는다는 것이다. 그 역시 자신이 만드는 오픈 소스 프록시를 소개하는 맥락이었다. 이 논점은 정확하다. 관측만 하는 경로는 정의상 아무것도 막을 수 없다. 예산 상한, 키 회수, 모델 차단 같은 통제는 요청 경로 위에 있어야만 가능하다. 그리고 단일 장애점 문제에 대해서는 @lokar가 짧게 답했다. 단일 장애점이 아닌 프록시 구성도 만들 수 있다는 것이다.

마지막으로 프록시 자체의 보안이 있다. 프록시는 정의상 모든 제공자 키를 쥔 병목이다. @jubilanti는 프록시를 써야 한다는 데는 동의하면서도, LiteLLM을 비롯한 이런 도구들이 버그투성이에 바이브 코딩으로 만들어진 것처럼 느껴지고, 업데이트 속도를 보면 취약점이 있을 수밖에 없다고 썼다(직접 인용은 아니고, 코멘트의 요지를 요약). 다른 이용자들은 Bifrost가 낫다고 했지만, 한 사람은 그것이 부분적으로 셰어웨어라고 덧붙였다. 키를 흩뿌리지 않으려고 세운 집중점이, 잘못 고르면 키를 한꺼번에 잃는 집중점이 된다. 원문의 「내가 통제하는 인프라」라는 장점은 내가 그 인프라를 관리할 역량과 시간이 있을 때만 장점이다.

## 전망과 시사점: 구독과 API, 그리고 어디에 무엇을 둘 것인가

이 논쟁에서 가장 많은 댓글을 모은 스레드는 기술이 아니라 경제였다. @NeutralWanted는 Claude Max 20배 요금제(월 200달러)를 쓰며 매주 주간 한도를 거의 다 쓰는데, API 키로 시험해 보니 2~3일 만에 200달러에 도달했다고 썼다. 그러니 API 키를 쓰는 사람들이 그 비용을 어떻게 정당화하는지 모르겠다는 것이다(직접 인용은 아니고, 코멘트의 요지를 요약). @paid_dot_expert는 월 100달러 구독을 쓰면서 하루 비용이 300.82달러, 208.72달러로 집계된 날들의 표를 붙였다(어떤 기준의 비용인지는 코멘트에 명시돼 있지 않다). @dcss_gardener는 구독이 크게 보조금을 받고 있으며 싼 토큰은 고객 획득 수단이라고 봤다.

이것이 관측 가능성과 연결되는 이유는 명확하다. 프록시는 API 키 경로에서 가장 자연스럽다. @jakozaur는 API 가격을 낼 때는 프록시가 좋지만, 구독이라면 `~/.claude/projects/` 같은 디렉터리의 JSONL 파일을 모으는 편이 쉽고 서브에이전트 구조까지 프록시보다 잘 정리돼 있다고 했다. 다만 가장 큰 가치는 조직 전체의 에이전트 세션을 모을 때 나오며, 그때는 자격 증명을 지우고 보안을 다뤄야 한다고 덧붙였다(직접 인용은 아니고, 코멘트의 요지를 요약). @skerit은 구독으로도 mitmproxy를 거쳐 Claude Code를 돌리며 모든 입출력을 기록하고 있다고 했고, @kqr은 구독으로 다른 하네스를 쓰는 것이 이용 약관 위반이 아니냐고 물었다. 구독과 프록시의 관계는 기술적으로는 가능하지만 약관상 회색 지대라는 인식이 댓글 전반에 깔려 있다. 또 몇몇 이용자는 150명이 넘는 조직은 엔터프라이즈 계약에서 API 과금으로 가게 된다고 주장했는데, 이 수치는 이 글에서 확인하지 못했다.

이를 바탕으로 실무적 권고를 정리하면 다음과 같다. 이것은 댓글과 문서를 근거로 한 필자의 분석이다.

첫째, 개인이 구독으로 쓰는 경우라면 프록시보다 로컬 세션 로그 수집이 먼저다. 이미 디스크에 있는 JSONL을 읽는 것이 가장 비용이 낮고 경로에 아무것도 끼워 넣지 않는다. @vasco처럼 이 모든 것이 캐시 히트를 손으로 들여다보려는 허세이며 더 큰 요금제를 사면 된다고 보는 시각도 있고, 개인 규모에서는 일리가 있다.

둘째, 팀이 API 키로 에이전트를 돌리는 순간 계산이 바뀐다. 키 귀속, 예산 상한, 가상 키 발급은 요청 경로 위에서만 할 수 있다. 이 경우 프록시는 관측 도구가 아니라 통제 도구이며, 그렇다면 단일 장애점이 되지 않도록 이중화하고 키를 쥔 컴포넌트로서 보안 업데이트를 따라가는 운영 부담을 받아들여야 한다.

셋째, OTel과 프록시는 양자택일이 아니다. 하네스의 OTel은 도구 호출과 서브에이전트 같은 하네스 내부 구조를 보여 주고, 프록시는 실제로 선을 넘어간 바이트를 보여 준다. 두 기록을 대조할 수 있다면 「하네스가 보고한 것」과 「실제로 보낸 것」의 차이 자체가 신호가 된다. 프롬프트 본문을 기록하는 순간 그 로그는 민감 정보 저장소가 된다는 점도 함께 기억해야 한다. @lionkor는 EU에서는 채팅에 개인 정보가 들어갈 수 있으며, 「난독증이 있어서 죄송하다」 같은 한 문장도 개인 정보라고 경고했다. Claude Code가 프롬프트 기록을 기본 비활성으로 둔 것도 같은 이유로 읽힌다.

넷째, 하네스를 신뢰하지 않는다면 관측의 층위를 한 단계 더 내려야 한다. 모델 API 프록시는 다른 서브도메인으로 가는 송신을 보지 못한다.

## 결론

원문은 「직접 돌려라, 그래야 안다」라는 한 문장으로 요약된다. 저자는 집에서는 재미있고 배우는 방식이라 그렇게 하고, 직장에서는 그렇게 하지 않으면 일을 제대로 하는 것이 아니라서 그렇게 한다고 썼다. 대형 언어 모델이 어떻게 동작하는지 면접 화이트보드에 그릴 만큼 이해하지 못할 수는 있어도, 추론을 서빙하는 동안 계측은 해 둘 수 있다는 것이다.

댓글이 덧붙인 것은 그 문장의 조건이다. 무엇을 알고 싶은지에 따라 관측 지점이 달라진다. 내 에이전트가 무엇을 했는지는 하네스의 텔레메트리로, 실제로 무엇이 전송됐는지는 프록시로, 하네스가 그 밖에 무엇을 하는지는 네트워크 계층으로만 알 수 있다. 그리고 통제하고 싶다면, 관측이 아니라 경로를 소유해야 한다.

@hdra는 스레드 한가운데서 이렇게 물었다. 사람들이 이 도구들로 어떤 결정을 내리려고 어떤 데이터를 얻으려는 것인가(직접 인용은 아니고, 코멘트의 요지를 요약). 프록시를 세우기 전에 먼저 답해야 할 질문은 이것이다. 당신의 팀은 지난달 에이전트가 쓴 토큰 가운데 캐시 미스로 날아간 몫을 알고 있는가. 모른다면, 그것을 알기 위해 필요한 것은 무엇이고 그것을 어디에 두어야 하는가.
