# Windows 11 은 당신이 어떤 코딩 에이전트를 쓰는지 센다 — 비트 하나짜리 텔레메트리의 무게

> 프롬프트도, 소스 코드도, 사용 시간도 보내지 않는다. 보내는 것은 「이 기계에서 Codex 가 실행되었다」는 비트 하나뿐이다. 이것은 OS 벤더의 평범한 제품 진단인가, 아니면 경쟁 도구의 점유율을 OS 레벨에서 측정하는 시장 정보 수집인가?

## 도입

2026년 11월 16일, 보안 연구자 Xusheng Li 는 「Windows 11 Is Collecting Data on Which Coding Agents and Developer Tools You Use」라는 글을 공개했다. 이 글은 Hacker News 에서 738점, 댓글 625개를 기록했다. 출발점은 사소했다. 연구자가 AI 에게 최신 Windows 바이너리에서 문서화되지 않은 기능을 찾아 달라고 했고, 그중 하나의 단서가 눈길을 끌었다. `codex.exe`, `claude.exe`, `copilot.exe`, `cursor.exe` 같은 코딩 에이전트의 실행 파일 이름이, `python.exe`, `dotnet.exe`, `gcc.exe`, `code.exe` 같은 익숙한 개발 도구 이름과 나란히 Windows 시스템 DLL 안에 박혀 있었던 것이다.

DLL 의 이름은 `MissionControlAggregator.dll`. 연구자는 이 문자열들의 참조를 따라가, 이것이 실제로 동작 중인 Windows 컴포넌트이며 어떤 코딩 에이전트와 개발 도구가 사용되었는지를 기록하고, 로컬에 저장하고, Windows 진단 체계에 보고한다는 것을 확인했다. 그리고 「선택적(optional)」 진단 데이터를 끄지 않았다면 — 그리고 그것은 기본으로 켜져 있다 — 이 데이터는 Microsoft 로 업로드된다. 이 글이 흥미로운 것은 폭로의 크기 때문이 아니다. 수집되는 정보는 극히 작다. 흥미로운 것은 **무엇을 세느냐**다. 2026년 개발 도구 시장에서 가장 치열한 전장인 코딩 에이전트를, 그 시장의 플레이어 중 하나이기도 한 OS 벤더가 OS 레벨에서 세고 있다.

## 역공학이 보여 준 것 — 실행 파일 이름에서 업로드 큐까지

원문의 조사는 「문자열이 있다」에서 멈추지 않고, 데이터가 기계를 떠나는지까지 단계별로 추적한다는 점에서 모범적이다.

**무엇을 비교하는가.** Binary Ninja 로 DLL 을 열면, 실행 파일 이름들이 비교 연산에 쓰이고 있다. CLI 에이전트 슬롯은 네 개로 `copilot.exe`, `claude.exe`, `codex.exe`, `agy.exe` 를 확인하고, WSL 경로에서는 확장자 없는 이름으로 같은 비교를 한다. 데스크톱 에이전트 슬롯은 다섯 개로 `github.exe`, `claude.exe`, `codex.exe`, `cursor.exe`, `antigravity.exe` 다. 이 비교를 감싸는 기능 플래그의 이름은 노골적이게도 `CLICodingAgentUsage`(feature ID 62580080)다. 목록은 AI 에이전트에 그치지 않는다. `node.exe`, `python.exe`, `dotnet.exe`, `gcc.exe`, `clang.exe`, `gdb.exe`, `javac.exe`, `devenv.exe`, `code.exe` 등이 더 넓은 「개발 도구 카테고리」로 묶인다. 일부는 게시자까지 확인한다. Node.js 슬롯은 Node.js Foundation, Python 은 Python Software Foundation, .NET 과 Visual Studio 는 Microsoft Corporation 을 기대한다. 반면 GCC·Clang 이 속한 컴파일러/디버거 그룹은 이 경로에서 게시자 확인이 없다.

**어디서 정보를 얻는가.** 이 컴포넌트는 프로세스를 직접 스캔하지 않는다. 이미 존재하는 Windows 이벤트를 구독한다. Windows 프로그램에 대해서는 `KernelProcess.AppStateChangeSummary` 와 `Win32kTraceLogging.AppInteractivitySummary` 를, WSL 에 대해서는 `Microsoft.Windows.Lxss.Manager.Exec` 를 받아 실행 파일 이름을 매처에 넘긴다. 즉 WSL 안의 리눅스 프로그램만이 아니라 일반 Windows 의 `codex.exe` 도 CLI 에이전트 검사에 걸린다. 원본 이벤트에는 실행 시간, 포커스 시간, 상호작용 카운터, 자원 사용량까지 들어 있지만, 연구자가 본 바로는 이 컴포넌트가 그 세부를 버리고 **어떤 에이전트가 관찰되었는지의 비트맵만** 남긴다.

**어떻게 보고하는가.** 매치가 성공하면 상태 슬롯이 켜지고, 이후 `ReportCohorts<12,4,5>` 가 이를 비트셋으로 바꿔 `Segments.SubCohorts` 라는 ETW(Event Tracing for Windows) 이벤트로 내보낸다. 12·4·5 는 각각 넓은 도구 카테고리 12개, CLI 에이전트 4개, 데스크톱 에이전트 5개에 해당한다. 상태는 `C:\ProgramData\Microsoft\Diagnosis\AggregatorStorage\` 아래에 저장되고, 보고는 대략 하루 단위다.

**정말 도는가.** 연구자는 Windows 11 ARM64 VM(빌드 26200.9974)에서 `CLICodingAgentUsage` 가 이미 서비스 실험으로 켜져 있었고, 자신은 수동으로 활성화한 적이 없다고 밝힌다. 텔레메트리 서비스 DiagTrack 이 자동 시작으로 돌고 있었고, 그 자식 프로세스 `AggregatorHost.exe` 가 문제의 DLL 을 로드하고 있었다. 실험은 단순했다. `cmd.exe` 를 `codex.exe` 로 복사해 실행했더니 이름만으로 Codex 로 인식되어 CLI 슬롯 2 가 켜졌고, 보고 창을 강제로 넘기자 `CliAgentSubCohorts: 4` — 즉 `1 << 2`, Codex 비트 — 를 담은 이벤트가 나왔다. `gcc.exe` 로 복사한 실험에서는 개발 도구 슬롯 3 이 켜졌다. 이 경우는 GCC 개별 비트가 아니라 컴파일러/디버거 카테고리 비트다.

**정말 나가는가.** ETW 이벤트 자체는 로컬 진단에도 흔히 쓰이므로 그것만으로 「전송된다」고 할 수는 없다. 연구자는 `Diagtrack-Listener` 세션이 입력 쪽(KernelProcess)과 출력 쪽(MissionControlAggregator) 프로바이더를 모두 구독하고 있음을 확인했고, DiagTrack 의 `EventStore.db` 업로드 큐에서 실제로 해당 이벤트를 찾아냈다. 이벤트에는 `"isRequired": false` 가 붙어 있었다. 즉 필수가 아닌 선택적 진단 데이터로 분류된다. 그리고 미국 지역으로 설정한 최신 공식 ISO 의 Windows 11 Home 클린 설치에서, 개인정보 설정을 건드리기 전 진단 데이터 토글은 이미 「Include Optional」 상태였고 `AllowTelemetry` 값은 3 이었다. 연구자의 결론은 이렇다. 설치 중이나 이후에 끄지 않았다면, 당신의 코딩 에이전트 사용 데이터는 업로드되고 있다.

## 왜 이것이 논쟁이 되는가 — 데이터의 크기와 의미의 크기는 다르다

방어 논리는 쉽게 세울 수 있다. 프롬프트도 소스도 없고, 실행 시간조차 버린다. 비트 몇 개짜리 집계는 Windows 가 어떤 개발자를 위해 무엇을 최적화할지 판단하는 평범한 제품 진단일 수 있다. 선택적 데이터이고, 설정에서 끌 수 있다. 연구자도 보고서에서 프롬프트나 소스 코드는 발견하지 못했다고 명시한다. 그럼에도 그는 「어떤 에이전트와 개발 도구를 쓰는지 수집하는 것 자체가 이미 상당한 프라이버시 함의를 갖는다」고 덧붙인다. 이 둘 사이의 간극이 이번 논쟁의 핵심이다.

첫째, **무엇을 세느냐는 누가 세느냐와 분리되지 않는다.** 슬롯 목록에는 Microsoft 계열(`copilot.exe`, `github.exe`, `code.exe`)과 경쟁사 제품(`claude.exe`, `codex.exe`, `cursor.exe`, `antigravity.exe`)이 함께 있다. 코딩 에이전트 시장에서 Microsoft 는 심판이 아니라 선수다. 하루 단위로 수많은 Windows 기기에서 「Copilot 만 쓴 기기」, 「Claude 와 Cursor 를 같이 쓴 기기」의 비율을 알 수 있다면, 그것은 어떤 시장조사 회사도 갖지 못한 점유율 패널이다. 이 데이터가 실제로 어떻게 쓰이는지는 원문도 알 수 없고 우리도 모른다 [가정: 경쟁 분석 목적이라는 증거는 없다]. 다만 데이터의 **잠재적 용도**가 비대칭적이라는 사실은 남는다.

둘째, **「선택적」이 기본값으로 켜져 있다**는 점이다. 원문이 확인한 것은 미국 지역 설정의 클린 설치 한 건이다. 다른 지역 — 특히 GDPR 이 적용되는 EU — 에서 기본값이 같은지는 확인되지 않았다 [가정]. 선택적이라는 단어는 사용자가 선택했다는 뜻이어야 하지만, 대부분의 사용자는 설치 화면을 그대로 넘긴다. 기본값이 곧 정책이라는 것은 UX 설계자라면 누구나 아는 사실이다.

셋째, **표본의 편향**이라는 기술적 반론도 있다. HN 의 한 댓글은 텔레메트리를 켠 Windows 사용자에게서만 프로그래밍 도구 사용을 측정하면 매우 왜곡된 데이터가 나올 것이라고 지적했고, 이에 「텔레메트리를 끌 정도로 영리한 사람은 애초에 그들이 관심 있는 시장 세그먼트가 아니다」라는 냉소적인 답이 붙었다(둘 다 직접 인용이 아니라 댓글 내용의 요약). 이 농담에는 진실이 있다. 기본값을 바꾸지 않는 다수 사용자의 분포를 아는 것이 제품 결정에는 더 유용하다.

HN 토론의 상당 부분은 예상대로 흘렀다. 「이게 왜 뉴스냐, Windows 는 원래 그렇다」는 체념, 그리고 Linux 로 옮기라는 권유와 배포판·게임 호환성 논쟁이 이어졌다(요약). 그 가운데 생각해 볼 만한 반론이 하나 있었다. Android, iOS, ChromeOS, macOS 도 어떤 앱이 쓰이는지 당연히 알 텐데, 왜 유독 Windows 만 추적하지 않기를 기대하느냐는 질문이다(요약). 정당한 질문이다. 다만 이번 사안의 특이점은 「앱 사용 통계」 일반이 아니라, **특정 경쟁 카테고리를 이름으로 지목한 별도의 기능 플래그와 비트맵**을 만들었다는 데 있다. 범용 텔레메트리의 부산물이 아니라, 코딩 에이전트를 세기 위해 의도적으로 설계된 계측이다.

## 전망과 시사점 — 개발 기계는 누구의 계측 장치인가

실무자에게 가장 즉각적인 시사점은 설정이다. 원문이 안내하듯 설치 중 선택적 진단을 거절하거나, 이후 설정 → 개인정보 및 보안 → 진단 및 피드백에서 「선택적 진단 데이터 보내기」를 끌 수 있다. 기업 환경이라면 그룹 정책이나 MDM 으로 `AllowTelemetry` 수준을 관리하고 있을 가능성이 높지만, 개인 개발 기기와 BYOD 는 사각지대다. 특히 고객사 계약 때문에 어떤 AI 도구를 쓰는지조차 민감한 정보가 되는 조직 — 예컨대 특정 벤더의 모델 사용을 금지하거나 의무화하는 계약 — 이라면, 도구 사용 사실 자체가 OS 벤더로 나간다는 점을 보안 평가 항목에 넣어야 한다 [가정: 이를 명시적으로 다루는 조직 정책 사례는 확인하지 않았다].

두 번째 시사점은 방법론이다. 원문은 「AI 에게 바이너리를 훑게 해 단서를 찾고, 사람이 실제 기계에서 재현해 확인한다」는 작업 방식을 보여 준다. 하루 전 HN 에 올라온 uBlock Origin 취약점 공개도 비슷한 분업을 밝혔다. 문서화되지 않은 OS 동작은 그동안 소수 리버서의 영역이었지만, 탐색 비용이 내려가면서 이런 발견은 더 자주 나올 것이다. OS 벤더 입장에서는 「문서화되지 않은 계측」이 더 이상 조용히 남아 있기 어려운 환경이 되었다.

시나리오를 나눠 보자. **낙관적 시나리오**에서는 Microsoft 가 이 계측의 존재와 목적을 문서화하고, 진단 데이터 뷰어에서 사용자가 확인할 수 있게 하며, EU 등 규제 지역에서는 명시적 동의 대상으로 돌린다. **비관적 시나리오**에서는 아무 설명 없이 기능 플래그가 이름만 바뀐 채 유지되고, 비슷한 계측이 브라우저·IDE·터미널로 번진다. 도구 벤더들도 OS 텔레메트리에 맞서 실행 파일 이름을 바꾸는 식의 회피를 시도할 수 있지만, 그것은 군비 경쟁일 뿐이다. **현실적 시나리오**는 이번 폭로가 규제 당국의 관심 목록에 한 줄 추가되는 정도로 끝나고, 개발자 커뮤니티에서는 「개발 기계는 Linux 로」라는 오래된 권고가 조금 더 설득력을 얻는 것이다.

더 큰 맥락도 있다. 코딩 에이전트는 이제 개발자 기계에서 가장 많은 권한을 가진 프로세스 중 하나다. 파일을 읽고, 명령을 실행하고, 네트워크에 접속한다. 그 에이전트들을 둘러싼 경쟁은 모델 품질만이 아니라 **배포 채널**의 경쟁이기도 하다. OS, IDE, 코드 호스팅, 클라우드를 모두 가진 기업이 OS 레벨 텔레메트리로 경쟁 에이전트의 사용을 관찰할 수 있다는 것은, 플랫폼 독점 논쟁에서 늘 나오던 「플랫폼이 자기 마켓의 데이터를 본다」는 문제의 새 판본이다.

## 결론

리드 질문으로 돌아가자. 비트 하나짜리 텔레메트리는 평범한 제품 진단인가, 시장 정보 수집인가. 원문이 증명한 것은 수집과 업로드의 **사실**이지 의도가 아니다. 의도는 Microsoft 만 안다. 그러나 판단에 필요한 재료는 충분하다. 경쟁 제품을 이름으로 지목한 전용 기능 플래그가 있고, 사용자가 수동으로 켜지 않았는데 서비스 실험으로 활성화되어 있었으며, 「선택적」 데이터가 기본으로 켜져 있었다. 데이터의 크기는 작지만, 그 데이터가 답하는 질문 — 「개발자들은 어떤 에이전트를 쓰고 있는가」 — 은 지금 업계에서 가장 비싼 질문 중 하나다.

개인 개발자에게 할 일은 명확하다. 진단 설정을 확인하고, 원하지 않으면 끈다. 조직에게 남는 질문은 더 넓다. 우리 개발 기계의 OS 는 우리 편인가, 아니면 우리가 쓰는 도구의 시장에서 경쟁하는 한 선수의 계측 장치인가. 그리고 그 질문에 답하기 위해 우리는 문서가 아니라 바이너리를 읽어야 하는 시대에 살고 있는가.
