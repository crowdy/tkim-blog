# Ladybird 알파 — 네 번째 브라우저 엔진은 AI 에이전트와 닫힌 기여로 만들어지는가

> 처음부터 새로 쓴 브라우저 엔진이 "일상에서 켜 볼 수 있는" 단계에 도달했다. 이것은 Chromium·WebKit·Gecko 3강 구도에 균열을 내는 사건인가, 아니면 AI 에이전트와 폐쇄적 개발 프로세스라는 새로운 비용 구조가 만든 일회성 질주인가?

## 도입

2026년 11월 23일(현지 시각), Ladybird Browser Initiative 의 Andreas Kling 은 짧은 공지를 올렸다. 제목은 "Ladybird is now in alpha". macOS 와 Linux 용 빌드를 내려받을 수 있고, 알파는 자동 업데이트가 돌아가는 롤링 채널이라는 내용이다. 공지는 스스로 몸을 낮춘다. 엔진은 "포크가 아니라 처음부터 직접 만든 것"이지만 그 위의 브라우저는 "수수하지만 기능은 한다(modest, but functional)" 수준이고, 일부 사이트는 동작하지 않으며 가끔 크래시가 난다. 보안에 대해서는 더 솔직하다. "새 브라우저는 몇 번이고 해킹당하며 그것이 과정의 일부"이므로 지금 시점에서는 보안에 대해 아무 약속도 하지 않는다고 적었다.

Hacker News 에서 이 공지(item 50614249)는 2,400점을 넘기며 그날의 1위가 됐다. 반응의 결은 크게 둘이었다. 하나는 "직접 써 보니 열어 둔 사이트가 전부 제대로 렌더링된다", "YouTube 와 Google Maps 도 조금 느리지만 잘 돈다"는 놀라움이다(여러 댓글의 정서를 요약한 것이며 직접 인용은 아니다). 다른 하나는 이 속도가 어디서 왔는지에 대한 질문, 그리고 6월에 외부 풀 리퀘스트를 전면 중단한 프로젝트를 여전히 "오픈소스 커뮤니티의 승리"로 불러도 되느냐는 질문이다. 이 글은 두 번째 질문을 축으로, 독립 엔진의 귀환이 무엇을 대가로 이루어졌는지를 살펴본다.

## 현상 분석 — 한 달에 7만 5천 개의 서브테스트

알파 직전의 Ladybird 가 얼마나 빨리 움직였는지는 프로젝트가 직접 낸 월간 뉴스레터에 수치로 남아 있다. 「This Month in Ladybird — October 2026」은 첫 문단부터 이렇게 요약한다. 10월 한 달 동안 스타일·레이아웃을 메인 스레드 밖으로 옮겼고, JavaScript JIT 를 만들었고, WebAssembly 엔진을 교체했고, 브라우저 UI 를 재설계했으며, Web Platform Tests(WPT)에서 Safari Technology Preview 를 넘어섰다.

WPT 수치가 특히 상징적이다. 뉴스레터에 따르면 10월 26일 Safari Technology Preview 를 통과했고, 월말 기준 통과 서브테스트는 2,184,722 개로 한 달 동안 75,650 개가 늘었다. 그런데 이 증가분의 대부분은 10월 22일 약 212만에서 27일 약 218만으로, 닷새 사이에 몰려 있다. 프로젝트는 그 이유를 숨기지 않는다. "AI 코딩 에이전트를 WPT 에 겨누고 빠진 기능을 채우라고 했다. 에이전트들은 작은 수정을 잔뜩 했고, 그것이 쌓였다." 가장 크게 늘어난 영역은 /css 약 3만, /editing 약 1만이었다.

언어 전환도 같은 패턴이다. 2026년 2월의 「Ladybird adopts Rust, with help from AI」에서 Kling 은 LibJS 의 렉서·파서·AST·바이트코드 생성기를 Claude Code 와 Codex 로 Rust 로 옮겼다고 밝혔다. 그는 이것이 "자율적 코드 생성이 아니라 사람이 지휘한 번역"이었으며, 수백 개의 작은 프롬프트로 방향을 잡고, 번역 후에는 서로 다른 모델에게 적대적 리뷰를 여러 차례 돌렸다고 설명한다. 결과는 약 2만 5천 줄의 Rust, 소요 기간은 약 2주였고, 손으로 했다면 수개월이 걸렸을 것이라고 적었다. 검증 기준은 "C++ 파이프라인과 바이트 단위로 동일한 출력"이었다. 10월 뉴스레터 시점에는 LibJS 런타임이 Rust 로 넘어가 JavaScript 엔진이 (flap 인터프리터와 GC 를 제외하고) 전부 Rust 가 됐고, 스타일 계산도 C++ 구현을 삭제하고 Rust 로만 돌린다.

기술적 내용도 단순한 따라잡기만은 아니다. 뉴스레터는 스타일·레이아웃을 별도 스레드로, 페인트 레코딩을 또 다른 스레드로 분리해 JavaScript 와 동시에 돌린다고 설명한다. 긴 스크립트가 메인 스레드를 막고 있어도 레이아웃을 바꾸는 CSS 애니메이션과 :hover 가 계속 동작하며, 프로젝트는 "우리가 아는 한 오늘 이것을 할 수 있는 다른 브라우저는 없다"고 주장한다(이 비교 주장은 프로젝트 측 주장이며 독립 검증은 확인하지 못했다). 성능 쪽 사례로는 x86 PC 에뮬레이터 JSLinux 가 Alpine Linux 를 셸까지 부팅하는 데 Ladybird 1.8초, Chrome 1.5초라는 수치를 들었다. 새 Wasm 엔진은 두 엔진이 모두 돌릴 수 있는 JetStream 3 Wasm 워크로드에서 이전 엔진보다 약 7배 높은 점수를 낸다고 한다.

보안 구조도 알파를 앞두고 다듬어졌다. 웹 페이지는 샌드박스된 렌더러 프로세스에서 돌고, 교차 사이트 iframe 과 팝업은 기본으로 별도 렌더러를 받으며, 최상위 사이트마다 네트워크 프로세스와 HTTP 캐시·서드파티 쿠키가 분리된다. 침해된 렌더러가 브라우저 프로세스에 임의 파일을 열어 달라고 요청할 수 있던 경로, 사용자 클릭을 위조해 팝업을 열거나 클립보드를 읽을 수 있던 경로도 막았다고 적었다. 알파 공지가 "보안 연구자들이 해킹해 주기를 원한다"고 말할 수 있는 배경이다.

## 심층 분석 — 속도와 신뢰를 맞바꾼 두 개의 결정

이 질주를 설명하는 결정은 두 개다. 하나는 AI 에이전트를 개발의 주력 도구로 쓰기로 한 것, 다른 하나는 외부 기여를 닫은 것이다. 둘은 별개의 결정처럼 보이지만 같은 경제학에서 나왔다.

2026년 6월 5일, Kling 은 「Changing How We Develop Ladybird」에서 공개 풀 리퀘스트를 더 이상 받지 않겠다고 선언했다. 앞으로 코드 변경은 프로젝트 메인테이너만 들여오고, 열려 있던 공개 PR 은 모두 닫으며, 이슈·이메일·포크를 통한 "그림자 기여 경로"도 만들지 않는다. 소스 코드는 계속 오픈소스 라이선스로 공개되고, 버그 리포트·사이트 테스트·표준 논의·보안 리포트 같은 외부 참여는 여전히 환영한다.

흥미로운 것은 이유다. 그는 수십 년 동안 코드 기여가 "누구를 신뢰할지 배우는 방법"이었다고 쓴다. 사람이 나타나 일을 하고, 변경에 책임을 지고, 곁에 남으면서 신뢰가 작업 자체에서 생겨났다. 그런데 AI 도구가 이 경제학을 빠르게 바꿨다는 것이다. "큰 패치는 큰 노력을 함의했고, 그 노력은 선의에 대한 합리적인 대리 지표였다. 그 가정은 더 이상 성립하지 않는다." 브라우저는 인터넷 전체의 신뢰할 수 없는 입력을 사용자 기기에서 실행하는 소프트웨어이고, 잘 위장된 취약점 하나면 공격자에게 충분하다. 끈기 있고 자원이 풍부한 캠페인이 메인테이너 신뢰를 얻어 악용한 사례가 이미 오픈소스에 있었다는 언급은 xz-utils 사건을 떠올리게 한다(본문은 특정 사건명을 명시하지 않는다).

즉 Ladybird 는 AI 가 생산 비용을 낮춘 것과 똑같은 이유로, 외부에서 들어오는 코드의 검증 비용이 올라갔다고 판단했다. 내부에서는 에이전트로 처리량을 늘리고, 외부에서 들어오는 경로는 좁혀 리뷰 부담과 공급망 위험을 줄인다. 이 조합은 내부적으로는 일관적이다. 에이전트가 만든 대량의 작은 수정을 받아들일지 판단하는 주체가, 그 결과에 책임을 지는 소수의 메인테이너로 한정되기 때문이다. "코드를 손으로 쳤는지는 중요하지 않다. 중요한 것은 브라우저에 들어간 뒤 누가 책임을 지는가"라는 문장이 이 구조를 요약한다.

HN 스레드에서는 이 트레이드오프에 대한 반응이 갈렸다. 한쪽은 "SQLite 나 Skia 같은 검증된 라이브러리를 받아들인 것이 품질을 크게 올렸지만, SerenityOS 시절의 해커 정신이 그립다"는 향수였고(댓글 정서의 요약), 다른 쪽은 "아직도 '소스는 공개하되 코드베이스에는 손대지 말라'인가, 그렇다면 관심 없다"는 냉담함이었다(역시 요약). 10월 뉴스레터의 WPT 성과를 인용하면서 "이 속도는 매우 닫힌 기여 정책 위에서 나온 것"이라고 짚은 댓글도 있었다. 창업자의 정치적 견해를 이유로 쓰지 않겠다는 댓글, 프로젝트가 GitHub 에서 비판자를 차단한다고 불만을 표하는 댓글도 상위권에 있었다. 기술 평가와 거버넌스 평가가 한 스레드 안에서 분리되지 않는다는 점 자체가, 브라우저가 단순한 소프트웨어가 아니라 웹의 규칙을 정하는 행위자라는 사실을 보여 준다.

여기서 기존 대안과 비교해 볼 필요가 있다. HN 의 한 댓글은 "Chromium 을 하드 포크하면 되지 않느냐"고 묻는다. 포크는 호환성을 즉시 얻지만, 엔진의 설계 결정과 거대한 코드베이스의 유지 비용을 그대로 물려받는다. Chromium 하드 포크를 장기간 독자적으로 유지하는 것은 사실상 또 하나의 대형 브라우저 벤더가 되는 일이다. Servo 는 Rust 로 쓴 독립 엔진이라는 점에서 Ladybird 와 가장 가까운 비교 대상이고, 실제로 HN 에서도 "브라우저 개발에 참여하고 싶은데 Servo 기반과 Ladybird 중 어디로 갈지 고민"이라는 질문이 나왔다. 개방형 거버넌스를 유지하는 Servo 와, 소수 메인테이너에게 책임을 집중한 Ladybird 는 같은 문제에 대해 정반대의 답을 고른 셈이다.

AI 에이전트의 기여 방식도 따져 봐야 한다. WPT 는 측정 가능한 목표이기 때문에 에이전트에게 맡기기 좋다. 실패하는 서브테스트를 고르고, 고치고, 통과 여부로 검증하면 된다. 그러나 WPT 통과 수는 "표준 준수의 하한"이지 "실제 웹 호환성"과 같지 않다. 실제 사이트는 표준 밖의 동작, 브라우저별 우회 코드, 봇 탐지에 의존한다. 10월 뉴스레터가 nytimes.com 과 reuters.com 의 봇 체크를 통과하게 됐다고 굳이 적은 것, HN 에서 "WSJ.com 이 이 브라우저를 수상하게 여긴다"는 보고가 나온 것은 이 간극을 보여 준다. 테스트 스위트가 있는 영역에서는 에이전트가 사람보다 훨씬 빨리 진도를 낼 수 있지만, 그 바깥은 여전히 사람의 판단과 현장 데이터가 필요한 영역이다.

## 전망과 시사점 — 네 번째 엔진은 누구를 위한 것인가

알파가 실무자에게 주는 가장 직접적인 시사점은 공지 자체에 적혀 있다. "웹사이트를 만든다면 Ladybird 에서 당신의 사이트를 열어 보고 무엇이 깨지는지 알려 달라." Ladybird 는 자동화 테스트용 WebDriver(10월에 WebDriver BiDi 추가)와 Firefox DevTools 프로토콜을 지원한다. 지금까지 크로스 브라우저 테스트 매트릭스는 사실상 Chromium·WebKit·Gecko 세 엔진이었다. 네 번째 엔진이 테스트 매트릭스에 들어온다는 것은, 특정 엔진의 버그나 비표준 동작에 기대어 온 코드가 드러날 기회가 하나 더 생긴다는 뜻이다. 특히 Chromium 전용 API 에 무심코 의존해 온 사내 도구라면, 표준 준수를 다시 점검할 저비용의 계기가 된다.

시나리오를 세 갈래로 나눠 보자. 낙관적 시나리오에서는 롤링 알파가 빠른 피드백 루프를 만들고, 에이전트 기반 개발이 테스트 가능한 영역의 격차를 계속 줄여 2027년 중 일반 사용자가 주 브라우저로 쓸 만한 수준에 도달한다. 이 경우 Ladybird 는 "광고 비즈니스와 연결되지 않은 엔진"이라는 지위로 프라이버시 지향 사용자와 공공 부문의 관심을 받을 수 있다. HN 에서 "Google 광고와 연결되지 않은 대안 브라우저가 생겨서 좋다"는 취지의 반응(댓글 정서 요약)이 나온 것도 이 지점이다.

비관적 시나리오에서는 보안이 발목을 잡는다. 공지 스스로 "보안에 대해 약속하지 않는다"고 했듯, 새 엔진은 공격자에게 새로운 사냥터다. JIT 와 새 Wasm 엔진은 역사적으로 브라우저 취약점이 가장 많이 나온 영역이고, 둘 다 10월에 막 들어왔다. 에이전트가 만든 대량의 작은 수정이 보안 경계 근처에서 미묘한 결함을 만들 가능성도 배제할 수 없다. 여기에 외부 기여 경로가 닫혀 있다는 점이 겹치면, 커뮤니티가 커질수록 "보고는 할 수 있지만 고칠 수는 없는" 사용자들의 피로가 쌓일 수 있다.

현실적 시나리오는 그 중간이다. Ladybird 는 당분간 웹 개발자와 브라우저 애호가의 테스트 대상, 그리고 엔진 다양성의 상징으로 기능하면서, 보안 연구자들의 표적이 되어 구조를 단단하게 다져 갈 것이다. 일반 사용자의 주 브라우저가 되기까지는 비밀번호 관리, 확장 기능(특히 광고 차단), Windows 정식 지원 같은 "엔진 바깥의 브라우저"가 더 큰 장벽이 될 가능성이 높다. HN 에서 비밀번호 관리 없는 브라우저는 쓰기 어렵다는 댓글, uBlock Origin 같은 확장을 원한다는 댓글이 반복된 것도 같은 맥락이다.

엔지니어링 조직에게는 또 다른 교훈이 있다. Ladybird 의 사례는 AI 에이전트를 "측정 가능한 목표가 있는 영역"에 투입했을 때의 위력과, 그 처리량을 감당하기 위해 거버넌스를 어떻게 바꿔야 하는지를 동시에 보여 준다. 2만 5천 줄 번역에 바이트 단위 동일성이라는 검증 기준을 먼저 세운 것, WPT 라는 외부 오라클에 에이전트를 붙인 것, 변경을 들여오는 사람을 책임질 수 있는 소수로 제한한 것은 모두 "생산은 싸졌지만 검증과 책임은 싸지지 않았다"는 같은 인식에서 나온다.

## 결론

리드 질문으로 돌아가자. Ladybird 알파는 3강 구도에 균열을 내는 사건인가, 일회성 질주인가. 현재 시점에서 정직한 답은 "균열을 낼 수 있는 조건이 처음으로 갖춰졌다"는 것이다. 처음부터 쓴 엔진이 실사용 사이트 대부분을 렌더링하고, 롤링 업데이트로 사용자 피드백을 받기 시작했다는 것은 수년 전까지만 해도 비현실적으로 여겨지던 일이다. 그러나 그 조건은 AI 에이전트의 처리량과, 외부 기여를 닫은 폐쇄적 프로세스라는 두 기둥 위에 서 있다.

이 두 기둥은 오픈소스의 오래된 약속, 즉 "누구나 코드를 보내 프로젝트를 바꿀 수 있다"는 약속과 긴장 관계에 있다. Ladybird 는 그 약속 대신 "누구나 코드를 볼 수 있고, 책임지는 사람이 코드를 들여온다"는 새로운 계약을 내놓았다. 이것이 AI 시대 오픈소스의 한 가지 표준 모델이 될지, 브라우저처럼 보안 위험이 극단적인 프로젝트에만 해당하는 예외가 될지는 아직 모른다.

독자에게 남기고 싶은 질문은 두 가지다. 당신이 운영하는 서비스는 네 번째 엔진에서 열리는가. 그리고 당신의 프로젝트가 AI 로 생산량을 늘렸을 때, 들어오는 코드를 누가 책임지는지에 대한 규칙도 함께 바꾸었는가. Ladybird 알파는 첫 번째 질문에 대한 시험대이자, 두 번째 질문에 대한 하나의 과감한 답안이다.
