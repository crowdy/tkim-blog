# uBlock Origin 의 유니버설 XSS — 확장이 웹페이지 안에 UI 를 그려야 하는 구조의 대가

> 가장 신뢰받는 보안 확장이 가장 넓은 공격면이 되었다. 이것은 uBlock Origin 한 프로젝트의 버그인가, 아니면 브라우저 확장이 자신의 UI 를 적대적인 웹페이지 안에 그려야만 하는 플랫폼 구조가 낳은 필연인가?

## 도입

2026년 11월 15일, 보안 연구자 Smitty van Bodegom 은 자신의 블로그 iter.ca 에 「Universal XSS in uBlock Origin from website-driven element picker」라는 글을 올렸다. 다음 날 이 글은 Hacker News 에서 619점, 댓글 183개를 모았다. 내용은 간단하면서도 불편하다. Firefox 용 uBlock Origin(MV2 판)에서, 악성 웹사이트가 사용자에게 클릭 한 번만 유도하면 확장에 임의의 「trusted filter」를 추가하게 만들 수 있었고, trusted filter 는 페이지에 JavaScript 를 주입할 수 있으므로 결과적으로 공격자는 **다른 아무 사이트**의 문맥에서 임의 코드를 실행할 수 있었다. 이른바 유니버설 XSS(UXSS)다.

GitHub 의 보안 권고 GHSA-cmqw-9r2w-6wv2 에 따르면 취약점은 11월 1일 이메일로 보고되었고, 영향 범위는 1.75.2 이하, 수정판은 1.75.4(11월 3일 공개)다. 유지관리자 gorhill 은 이틀 만에 패치를 냈고, 이후 1.76.0(11월 8일)에서 추가 방어를 넣었다. 대응 속도만 보면 모범적이다. 그런데도 이 사건이 많은 논쟁을 부른 이유는 공격 경로가 uBO 고유의 실수라기보다, 거의 모든 「페이지와 상호작용하는 확장」이 공유하는 설계 패턴을 찌르고 있었기 때문이다. 게다가 연구자는 취약점 발견의 상당 부분을 GPT 계열 모델이 했다고 밝혔고, 이것도 댓글의 한 축이 되었다.

## 공격의 해부 — 네 단계로 쌓아 올린 UXSS

원문이 설명하는 공격은 네 단계다. ① 요소 선택기(element picker)의 URL 을 알아낸다. ② 그 URL 을 투명한(opacity 0) iframe 으로 자기 페이지에 심는다. ③ 선택기를 메시지로 조종해 원하는 필터를 집어넣는다. ④ 보이지 않는 「Create」 버튼 위에 사용자의 클릭이 떨어지도록 iframe 을 배치한다.

**첫 단계: 확장 UUID 유출.** Firefox 에서 확장의 내부 리소스는 `moz-extension://<UUID>/...` 형태의 URL 을 갖는데, 이 UUID 는 설치마다 무작위다. 따라서 원래는 웹페이지가 선택기 URL 을 추측할 수 없다. 그런데 uBO 의 기본 필터 목록(uAssets)에는 `no-fetch-if` 스크립틀릿을 쓰는 규칙이 있었다. 광고 서버로 가는 `fetch` 요청을 가로채, 같은 API 를 가졌지만 아무것도 하지 않는 더미 스크립트(web accessible resource, WAR)를 대신 돌려주는 규칙이다. 문제는 이 더미 스크립트를 가져올 때 스크립틀릿 내부에서 `XMLHttpRequest` 로 `moz-extension://<UUID>/web_accessible_resources/...` 를 요청한다는 점이다. 스크립틀릿은 페이지 문맥에서 동작하므로, 페이지가 미리 `XMLHttpRequest.prototype.open` 을 덮어써 두면 그 URL — 즉 UUID — 을 그대로 엿볼 수 있었다. 공격자는 `fetch('/adsbygoogle.js')` 한 줄로 그 규칙을 발동시키기만 하면 됐다.

**둘째·셋째 단계: 선택기 원격 조종.** UUID 를 알면 선택기 UI 인 `epicker-ui.html` 을 iframe 으로 띄울 수 있다. 이 페이지는 확장의 백그라운드 스크립트와 통신해 필터를 추가하는 권한을 가진다. 공격자는 `MessageChannel` 을 만들어 `postMessage({ what: 'epickerStart' }, '*', [port])` 로 선택기를 시동하고, 대화 상자를 표시하라는 메시지와 함께 필터 내용을 보낸다. 정상적인 선택기는 스크립틀릿 필터 입력을 막지만, 네트워크 요청 유형(예: `image`)을 담는 `opt` 필드가 `$image` 처럼 필터 끝에 그대로 덧붙여진다는 점을 이용해, 거기에 줄바꿈과 함께 `google.com##+js(trusted-rpnt, script, ...)` 같은 **임의의 trusted 필터**를 끼워 넣을 수 있었다. 선택기로 추가한 필터는 (재컴파일 전까지) 항상 신뢰된 것으로 취급되므로, 스크립트 주입 권한까지 따라온다.

**넷째 단계: 클릭재킹.** 연구자는 이 부분을 실제로 구현하지 않았다고 밝힌다. 하지만 투명 iframe 을 버튼 위에 겹쳐 두는 것은 고전적인 클릭재킹 기법이고, 「페이지 아무 데나 한 번 클릭하게 만들기」는 어렵지 않다.

핵심 결함에 대한 원문의 진단은 명확하다. **선택기는 공격자의 메시지를 받아들여서는 안 됐다.** 수정은 그 지점을 정면으로 다뤘다. 권고에 기록된 커밋 순서는 이렇다. 1.75.2 에서 「스크립틀릿이 오염될 수 있는 XHR 메서드를 쓰지 않도록」 고쳤고, 1.75.4 에서 「검증된 비밀 토큰이 있어야만 선택기를 기동」하도록 했으며, 1.76.0 에서 「생성 직전의 필터를 검증」하고 「war: 관련 필터를 당분간 막는」 조치를 추가했다. 흥미로운 것은 1.75.2 패치 직후 연구자가 다시 메일을 보내, `XMLHttpRequest.prototype` 에 `responseText` getter 를 정의하는 방식으로 여전히 UUID 를 얻을 수 있다고 지적한 대목이다. 즉 첫 패치는 「UUID 를 숨기는」 방향이었고, 그것만으로는 막을 수 없다는 것이 드러나자 「선택기가 누구의 지시를 받는가」라는 신뢰 경계 쪽으로 방어선이 옮겨갔다.

원문에 따르면 MV3 판인 uBO Lite 에도 비슷하지만 덜 심각한 문제가 있었다. HN 에 올라온 한 댓글은 점검 기준으로 uBlock Origin 1.75.4, uBO Lite 2026.1110.1816 이상이어야 한다고 정리했다(직접 인용이 아니라 댓글 내용의 요약).

## 구조적 원인 — 확장 UI 는 왜 적의 영토에 그려지는가

이 사건을 「uBO 가 postMessage 출처 검증을 빠뜨렸다」로 요약하면 절반만 맞다. HN 토론의 가장 생산적인 줄기는 **왜 애초에 확장의 UI 가 웹페이지 안에 존재해야 하는가**라는 질문이었다.

한 댓글은 확장이 페이지의 요소와 함께 일해야 할 때 — 요소 선택기나 비밀번호 관리자의 자동완성 제안처럼 — 자기 인터페이스를 웹사이트 DOM 안에 넣을 수밖에 없는 현실이 늘 마음에 걸렸다고 썼다. 비밀번호 관리자의 경우, 페이지가 새로 생기는 DOM 요소를 감시하면 사용자가 어떤 계정을 가졌는지까지 새어 나갈 수 있다는 것이다(공감 댓글의 정서를 요약). 이에 대해 「괜찮은 비밀번호 관리자는 closed shadow DOM 이나 샌드박스 iframe 에 UI 를 넣으므로 그런 유출은 없다」는 반론도 붙었다. 양쪽 모두 일리가 있다. 격리 장치는 존재하지만, 그 장치를 올바르게 쓰는 것은 각 확장 개발자의 몫이고, 이번 uBO 의 경우처럼 iframe 으로 격리해 놓아도 **그 iframe 을 누가 띄우고 누가 말을 거느냐**를 검증하지 않으면 격리는 무력해진다.

가장 시사적인 댓글은 브라우저 개발에 관여했던 것으로 보이는 이용자의 회고였다. 확장 전용 오버레이 API 를 더 강하게 밀어붙이지 못한 것을 후회한다는 내용으로, 원래 Top Layer 를 기반으로 하려 했지만 확장이 하위 트리를 붙일 수 있는 원시 API 는 끝내 추가되지 않았다는 것이다. 그는 개발자 도구가 웹페이지 위에 그리기 위해 별도의 「오버레이 페이지」를 쓰고, 일부 플랫폼의 날짜 선택기도 같은 메커니즘을 쓰지만, 이 기계장치가 확장에는 노출된 적이 없다고 덧붙였다(요약이며 직접 인용 아님, 해당 이용자의 이력은 확인하지 않았다). 다른 댓글은 구형 uBO(Pale Moon 및 Quantum 이전 Firefox 용)가 `chrome://ublock0` 이라는 브라우저 크롬 영역에 선택기를 두었고, 페이지에 주입되는 iframe 은 `about:blank` 문서였다고 지적했다. 즉 XUL 시대에는 확장 UI 가 페이지 바깥, 브라우저 쪽 신뢰 영역에 살 수 있었는데, WebExtensions 로 이행하며 그 선택지가 좁아진 것이다.

여기서 트레이드오프가 선명해진다. WebExtensions 와 Chrome 의 Manifest V3 는 「확장이 너무 많은 힘을 가진다」는 문제의식에서 권한을 좁혀 왔다. 한 댓글이 정리했듯, 그 문제의식의 상당 부분은 취약점보다 **무료 확장을 사들여 브라우징 기록을 빼돌리거나 광고를 주입하는 수익화 패턴**에 대한 것이었다(요약). 그런데 권한을 좁히는 방향의 설계는 확장에 「페이지 밖에 그릴 수 있는 안전한 캔버스」를 주는 일에는 상대적으로 소홀했다. 결과적으로 확장은 여전히 페이지를 수정할 강력한 권한을 갖되, 그 수정의 UI 는 적대적일 수 있는 페이지와 같은 공간에 놓이게 되었다. 「문제는 페이지를 수정하는 것이 아니라, 페이지가 수정자와 상호작용할 수 있다는 것」이라는 댓글이 정곡을 찌른다(요약).

두 번째 구조적 원인은 **설치별 무작위 UUID 를 보안 경계로 쓰는 관행**이다. Firefox 가 확장 UUID 를 설치마다 무작위로 만드는 것은 지문 채취 방지와 리소스 보호를 위한 장치지만, 이번 사건은 그 값이 스크립틀릿 같은 「페이지 문맥에서 도는 확장 코드」를 통해 너무 쉽게 새어 나갈 수 있음을 보여 줬다. 한 댓글은 최근 다른 사례에서 Firefox 확장 UUID 가 추적 식별자로 쓰일 수 있다는 것을 알았는데, 이번엔 `fetch('/adsbygoogle.js')` 하나로 uBO 의 UUID 가 노출된다니 「아이러니한 재앙」이라고 썼다(요약). 추적을 막으려고 설치한 확장이 추적 식별자를 흘리는 구조다. 원문도 UUID 가 새는 경로가 이 필터 규칙 하나만이 아니라고 분명히 한다. 비밀 값의 은닉에 기대는 방어는, 그 비밀이 페이지 문맥과 닿는 순간 이미 반쯤 무너진 것이다.

세 번째 쟁점은 발견 방식이다. 연구자는 「UXSS 가 필터 주입에서 나올 것 같다」는 감을 갖고 모델에게 살펴보게 했으며, 모델이 문제를 찾았고 자신은 그것을 검증했다고 적었다. 글의 산문은 직접 썼고 PoC 코드는 Claude 가 대부분 작성했다고도 밝혔다. HN 에서는 이 공개 방식 자체를 반기는 반응(사람이 쓴 글이라는 신호가 더 많아지길 바란다)과, 이 정도로 단순한 취약점에 AI 도움이 필요했다는 데 실망한다는 반응이 엇갈렸다(모두 요약). 어느 쪽이든 사실은 하나다. 「감」과 「검증」은 사람이, 지루한 코드 경로 추적은 모델이 맡는 분업이 이미 실전 취약점 연구에서 돌아가고 있다는 것이다.

## 전망과 시사점 — 무엇을 고치고, 무엇을 버티는가

실무자에게 주는 첫 번째 시사점은 단순하다. **확장의 UI 가 페이지와 메시지를 주고받는다면, 그 채널은 외부 API 와 똑같이 취급해야 한다.** `postMessage` 수신 측은 발신자를 검증해야 하고, 「iframe 안에 있으니 안전하다」는 가정은 iframe 을 누가 띄웠는지 모르는 한 성립하지 않는다. uBO 가 채택한 비밀 토큰 방식 — 정상 경로의 콘텐츠 스크립트만 아는 값을 선택기 시동 메시지에 요구하는 것 — 은 웹 애플리케이션의 CSRF 토큰과 같은 발상이다. 새로울 것 없는 해법이 늦게 적용된 셈이며, 그래서 오히려 다른 확장에서도 같은 구멍이 있을 개연성이 높다고 봐야 한다 [가정].

두 번째는 **입력 정규화의 함정**이다. `opt` 필드에 줄바꿈을 넣어 필터 한 줄을 두 줄로 만드는 기법은, 「사용자가 고를 수 있는 값은 몇 개뿐」이라는 UI 수준의 가정이 메시지 수준에서는 아무 의미가 없음을 보여 준다. 1.76.0 의 「생성 직전 필터 검증」은 그 가정을 데이터 쪽에서 다시 세우는 조치다. 화면이 제한하는 것과 서버(여기서는 백그라운드 스크립트)가 강제하는 것은 다르다는, 웹 보안의 가장 오래된 교훈이 확장에서도 그대로 반복되었다.

시나리오를 나눠 보자. **낙관적 시나리오**에서는 이번 사건이 브라우저 벤더들로 하여금 확장 전용 오버레이·UI 표면을 다시 논의하게 만든다. 요소 선택기나 비밀번호 제안이 페이지 DOM 이 아니라 브라우저가 소유한 레이어에 그려진다면, 클릭재킹과 메시지 위조라는 두 축이 한꺼번에 사라진다. **비관적 시나리오**에서는 이번 사건이 「확장은 위험하다」는 서사를 강화해, 권한을 더 줄이는 방향으로만 정책이 움직인다. 그렇게 되면 광고 차단 같은 기능은 더 약해지고, 사용자는 효과가 떨어지는 DNS 차단이나 브라우저 내장 기능에 의존하게 된다. HN 에서도 「DNS 기반 차단이면 충분하다」는 주장에, 주요 동영상·SNS 사이트의 광고는 브라우저 수준 차단 없이는 막을 수 없다는 반박이 이어졌다(요약). **현실적 시나리오**는 그 중간이다. 개별 확장들이 토큰 검증, shadow DOM, 입력 검증을 하나씩 채택하며 구멍을 메우고, 플랫폼 차원의 해법은 느리게 온다.

사용자 관점에서는 자동 업데이트가 사실상 유일한 방어선이었다는 점도 짚어야 한다. 취약 버전이 공개된 지 이틀 만에 수정판이 AMO 에 올라왔지만, HN 에는 Android 용 Firefox 에서는 확장을 수동으로 업데이트할 방법이 마땅치 않다는 불만도 보였다(요약). 권고와 블로그 공개가 수정 후 약 2주 뒤에 이루어진 것은, 자동 업데이트가 퍼질 시간을 벌어 주는 책임 있는 공개의 전형이다.

## 결론

리드 질문으로 돌아가자. 이것은 uBO 의 버그인가, 구조의 필연인가. 답은 「둘 다이며, 비중은 구조 쪽이 더 크다」다. 직접적인 결함 — 선택기가 출처를 확인하지 않고 메시지를 받은 것, `opt` 필드를 검증하지 않은 것 — 은 분명 uBO 의 몫이고, 이미 고쳐졌다. 그러나 그 결함이 치명적일 수 있었던 이유는, 가장 강력한 권한을 가진 확장의 UI 가 가장 신뢰할 수 없는 공간인 웹페이지 안에 그려져야 했고, 그 UI 를 보호하는 수단이 설치별 무작위 문자열이라는 얇은 비밀이었기 때문이다.

브라우저 확장은 웹에서 사용자 편에 서는 거의 유일한 계층이다. 광고 차단기, 비밀번호 관리자, 접근성 도구가 모두 여기에 산다. 그 계층을 더 안전하게 만드는 방법이 「권한을 더 빼앗는 것」뿐이라면, 우리는 보안을 얻는 대신 사용자 주권을 잃는다. 반대로 확장에게 페이지 밖의 안전한 그릴 자리를 주는 방향은, 같은 권한을 유지하면서 공격면을 줄일 수 있다.

독자에게 남기는 질문은 이것이다. 당신이 쓰거나 만드는 확장 중, 페이지 안에 UI 를 그리고 그 UI 가 페이지와 말을 주고받는 것은 몇 개인가. 그리고 그 대화의 상대가 정말 당신이 생각하는 상대인지, 누가 보증하고 있는가.
