# Nginx HTTP/2 원격 코드 실행 — 다섯 팀이 동시에 찾은 11년 묵은 버그

> "복잡해서 아무도 못 찾는다"는 사실상의 방어선이 무너졌을 때, 웹의 정문을 지키는 C 코드는 여전히 지금의 패치 주기로 버틸 수 있는가.

## 도입

2026년 11월 18일(미국 시간), F5 는 Nginx 보안 릴리스를 내고 HTTP/2 처리부의 치명적 취약점 두 건을 공개했다. CVE-2026-123633 과 CVE-2026-123007 이다. 둘 다 CVSS 4.0 기준 9.2점, 인증 없이 원격에서 Nginx 서버의 코드를 실행할 수 있다. Wiz 의 공개 글 「Unauthenticated remote code execution in Nginx」는 한국 시간 11월 19일 Hacker News 에서 1,521점, 648개 댓글을 모으며 그날 최상위에 올랐다.

이 사건이 단순한 "또 하나의 CVE"가 아닌 이유는 세 가지다. 첫째, 대상이 Nginx 다. Wiz 는 Nginx 가 2억 2,500만 개 이상의 웹사이트를 구동한다고 쓴다. 리버스 프록시로서 여러 애플리케이션의 공통 입구에 서 있으므로, 뒤의 애플리케이션 코드가 아무리 안전해도 앞단에서 뚫린다. 둘째, 그중 하나(CVE-2026-123007)는 2015년의 Nginx 1.9.5 부터 존재했다. 11년간 아무도 찾지 못했던 버그다. 셋째, Wiz, Ikotas Labs, Metnir, Rapid7, Xint 다섯 팀이 **독립적으로** 같은 취약점을 보고했다. HN 에서는 "이게 버그 충돌(bug collision) 기록 아니냐"는 반응이 나왔다(댓글 요지).

그리고 같은 주에 비슷한 성격의 발표가 연달아 나왔다. Wiz 가 "어제 공개됐다"고 언급한 Calif 의 OpenJDK Base64 디코더 메모리 손상 취약점 Java4Shell 이 한국 시간 11월 18일 HN 상위에 올랐고, 11월 19일에는 Veria Labs 의 Ruby 문자열 대문자 변환 힙 오버플로 Ruby2Shell 이 뒤를 이었다. 세 건 모두 "메모리 안전한 고수준 언어 생태계"의 밑바닥에 깔린 C·어셈블리 코드에서 나왔고, 세 건 모두 발견 과정에 AI 가 깊게 관여했다.

## 현상 분석 — 두 개의 HTTP/2 버그와 한 주의 연쇄 공개

### CVE-2026-123633: 재사용 가능으로 잘못 표시된 연결

Wiz 의 기술 설명을 개념 수준으로 정리하면 이렇다. Nginx 는 새 연결을 받을 자리가 부족할 때 닫아도 되는 "재사용 가능" 연결 목록을 유지한다. 활성 요청이 없는 HTTP/2 연결은 이 목록에 들어갈 수 있지만, 요청이 시작되면 빠져야 한다. 그런데 헤더 프레임이 나뉘어 도착하는 특정 상황에서 요청 스트림이 생성된 뒤에도 연결이 목록에서 빠지지 않는 경로가 있었다. 이후 리버스 프록시로서 업스트림 연결을 새로 열 때 빈 슬롯이 부족하면, Nginx 는 바로 그 처리 중인 연결을 닫을 대상으로 고를 수 있다. 연결 메모리가 해제된 뒤에도 원래 요청 처리 코드는 그 메모리를 계속 쓴다. 전형적인 use-after-free 다.

영향 범위는 HTTP/2 를 켜고 **프록시로 동작하는** 구성이며, 영향 버전은 1.19.7 부터 1.31.8 까지다. Wiz 는 2026년 10월 21일 이 버그를 ASLR 우회를 포함한 RCE 확인과 수정안까지 붙여 보고했고, F5 는 다른 팀이 이미 같은 버그를 보고했다고 답했다.

### CVE-2026-123007: 흐름 제어 창의 정수 언더플로

두 번째 버그는 HTTP/2 흐름 제어 계산에서 나온다. Nginx 는 연결 단위로 "아직 보낼 수 있는 데이터 양"을 `send_window` 라는 카운터로 추적한다. 전송 대기 중이던 스트림이 취소되면 쓰지 않은 몫을 되돌려 주는데, 이 환불 연산이 HTTP/2 의 최대 창 크기를 검사하지 않았다. 카운터가 최댓값을 넘어서면, 이후 "더 늘려도 되는가"를 묻는 경계 검사가 부호 없는 정수 뺄셈에서 언더플로해 거대한 양수가 된다. 검사는 무력화되고, 잘못된 값은 결국 부호 있는 길이로 변환되며 음수가 되어 TLS 전송 경로에서 범위를 벗어난 메모리 복사로 이어진다. Wiz 는 이를 통해 메모리 노출과 힙 손상, 최종적으로 원격 코드 실행에 도달했다고 쓴다.

이 버그가 더 위험한 이유는 조건이 넓다는 데 있다. Wiz 표에 따르면 HTTP/2 를 켠 **기본 구성**에서 악용 가능하며, 영향 버전은 1.9.5 부터 1.31.8 까지다. Wiz 는 백엔드 애플리케이션이나 서드파티 모듈 없이 정적 파일만 서빙하는 64비트 서버에서 HTTPS 로 코드 실행을 시연했다고 밝혔다.

### 같은 릴리스의 다른 CVE 들

F5 의 같은 릴리스에는 이 두 건 외에도 HTTP/3 프록시의 use-after-free, DNS 리졸버 응답 처리의 use-after-free, auth_http 를 쓰는 메일 프록시 모듈의 use-after-free 등 9.2점 취약점이 세 건 더 포함됐다. 수정 버전은 Nginx OSS 기준 1.30.7(stable) 과 1.31.9(mainline) 이다.

### 공개와 패치의 간격

HN 초기 댓글 중 하나는 패치가 아직 나오지 않았는데 왜 이렇게 상세한 내용을 공개하느냐고 물었다가, 30분 안에 새 버전이 나왔다며 스스로 정정했다(요지 요약). 또 다른 참여 팀인 Xint 소속이라고 밝힌 사용자는 몇 가지 추가 버그와 루트 권한까지의 전체 체인을 다룬 별도 글이 있다고 소개했다. "공격이 실제로 나오기까지 몇 시간이나 걸리겠느냐"는 질문도 상위에 올랐다.

### 같은 주의 Java4Shell 과 Ruby2Shell

Calif 의 Java4Shell(CVE-2026-114938, CVSS 4.0 9.2)은 OpenJDK HotSpot 이 x86-64 의 AVX-512 VBMI 명령으로 Base64 디코딩을 가속하는 손으로 짠 어셈블리 코드의 꼬리 처리 버그다. 잘못된 입력에서 출력 길이를 음수로 계산해 배열 끝을 넘어 쓰게 된다. Calif 는 Keycloak, Jira, Confluence, Artifactory, Jenkins, PingFederate 에서 기본 설정 그대로 인증 전 RCE 를 시연했다고 밝혔다. HN 댓글에서는 AVX-512 를 끄거나 Base64 intrinsic 을 비활성화하는 JVM 플래그가 임시 완화책으로 공유됐다(댓글 정보이며 이 글에서 직접 검증하지 않았다).

Veria Labs 의 Ruby2Shell(CVE-2026-132825)은 Ruby 의 단일 바이트 인코딩(ISO-8859, Windows-125x 계열 일부)에서 독일어 ß 를 대문자로 바꿀 때 두 바이트 SS 를 쓰면서 경계 검사는 한 바이트분만 하는 버그로, 1바이트 힙 오버플로다. Ruby 2.4.0 부터 존재했고 3.3.14, 3.4.13, 4.0.10 에서 고쳐졌다. Rails 와 Sinatra(classic) 의 기본 구성에서 도달 가능하다고 한다. Ruby 를 번들하는 GitHub Enterprise Server 는 11월 21일 갱신 시점에 수정 릴리스가 없다고 표시돼 있었다.

## 심층 분석 — 왜 지금, 왜 한꺼번에

### 복잡성이라는 방어선의 붕괴

Wiz 는 두 취약점을 자사의 AI 코드 스캐닝 하니스 Wiz Atlas 로 발견했고, 영향 검증에 Gemini 4 Carbon 과 ChatGPT 5.6 Sol 을 썼다고 밝혔다. 그리고 이렇게 쓴다. 이런 메모리 안전성 결함은 여러 코드 경로와 메모리 연산 사이의 미묘한 상호작용을 추적해야 해서 역사적으로 찾기도, 악용하기도 매우 어려웠고, 그 복잡성 자체가 현실적인 장벽이었다. 그러나 AI 가 그 장벽을 근본적으로 허물고 있다는 것이다.

Calif 의 서술은 더 구체적이다. Java4Shell 을 찾은 연구자는 Codex 에게 JIT 컴파일러, intrinsic, 널리 노출된 API, 암호 영역을 살펴보게 했고, 초기 결과 대부분은 도달 불가능하거나 비현실적인 "슬롭"이었지만 약 20분간 계속 밀어붙여 Base64 버그를 얻었다고 쓴다. 발견에 한 시간, 첫 동작 익스플로잇에 두 시간이 더 걸렸고 총 토큰 비용은 200달러 미만이었다. Calif 는 이를 사람과 AI 가 결합한 "켄타우로스 해커"라 부른다.

Ruby2Shell 페이지는 Veria Labs 외에도 Ruby 보안 권고가 Ada Logics 의 Stephan Lipp 과 Anthropic 을, 추가 발견자로 OpenAI 와 협업한 Moritz Sanft 를 크레딧한다고 적는다. 한 버그에 여러 AI 기반 팀이 동시에 도달하는 현상이 Nginx 만의 일이 아니라는 뜻이다.

다섯 팀의 동시 발견은 중요한 신호다. 과거의 버그 충돌은 드물었고, 대개 같은 신규 기법이 퍼진 직후에 일어났다. 지금 일어나는 일도 구조적으로 같다. "새 기법"이 특정 퍼징 아이디어가 아니라 범용 모델이라는 점만 다르다. 그 기법은 방어자만 갖고 있는 것이 아니다. Wiz 도 연구자와 공격자 모두가 오래된 결함을 찾을 수 있게 된다고 명시한다.

### C 의 문제인가, 사람의 문제인가

HN 에서 가장 뜨거웠던 논쟁은 언어였다. 한 사용자는 처음에 "C 를 못 쓰는 프로그래머의 불운한 사례일 뿐, C 의 문제는 아니다"라고 비꼬았다가, 스스로 수정하며 사람이 상당한 분량의 C 를 올바르게 쓸 수 있다는 관념 자체가 틀렸다는 것이 점점 드러나고 있고, AI 보조 취약점 탐색 앞에서 이런 프로그램이 무너지고 있다고 정리했다(요지 요약).

세 사건을 겹치면 이 논점은 더 날카로워진다. Java 와 Ruby 는 메모리 안전성을 판매 포인트로 삼는 언어다. 그러나 런타임의 성능 핵심부는 여전히 C, C++, 어셈블리다. Calif 는 Java 의 강점이 메모리 안전성인데 Java 자체의 상당 부분이 저수준 언어로 쓰였고 그곳에서는 메모리 손상이 "여전히 삶의 일부"라고 쓴다. 즉 메모리 안전 언어로 애플리케이션을 짜는 것만으로는 충분하지 않다. 공격 표면은 런타임과 프록시, 즉 모두가 공유하는 하부 계층으로 이동했다.

### 성능 최적화의 비용

Calif 는 또 하나의 구조적 원인을 지적한다. Base64 가속 코드는 거대한 데이터를 디코딩하는 일부 애플리케이션에만 이득이지만, 코드는 몇백 바이트를 디코딩하는 모두에게 배포된다. 필요한 사람만 이득을 보고 모두가 위험을 진다. 그들은 이를 "공유지의 비극"이라 부르고, AI 로 죽은 코드와 불필요한 최적화를 찾아 걷어내는 "vibe-uncoding"을 제안한다. "무엇을 만들 수 있는가" 대신 "무엇을 지울 수 있는가"를 물어야 한다는 것이다. Nginx 의 경우에도 HTTP/2 를 쓰지 않는 사이트라면 꺼 두는 것이 가장 강력한 방어였다. HN 에서 "HTTP/1.1 만 쓰고 있어서 다행"이라는 반응이 나온 이유다.

### 공개 정책의 긴장

HN 의 "익스플로잇이 나오기까지 몇 시간이냐"는 질문은 공개 상세도에 대한 오래된 논쟁을 되살린다. Wiz 는 개념 수준의 원인 분석을 공개했고, Veria Labs 는 RCE 개념 증명을 11월 25일, 또는 주요 벤더가 수정을 내지 못하면 그 이후에 공개하겠다고 예고했다. AI 가 발견 비용을 낮춘다면 패치 diff 로부터 익스플로잇을 재구성하는 비용도 함께 낮아진다. "공개 후 패치까지의 창"은 줄어들고 "패치 공개 후 악용까지의 창"도 줄어든다.

## 전망과 시사점 — 방어 측의 시간표를 다시 짜기

### 즉시 할 일

Wiz 의 권고는 명확하다. HTTP/2 가 켜진 Nginx 배포를 식별하고 1.30.7 또는 1.31.9 이상(Nginx Plus 는 F5 가 안내한 수정 버전)으로 올린다. 즉시 업그레이드가 불가능하면 해당 server 블록에서 HTTP/2 를 끄고 listen 지시자의 http2 파라미터를 제거한 뒤 리로드하고, **기존 워커 프로세스가 실제로 종료됐는지 확인**한다. 리로드만 하고 구 워커가 살아 있으면 완화가 적용되지 않은 상태가 남는다. 예상치 못한 워커 크래시나 Nginx 가 띄운 명령은 조사 대상이지만, Wiz 는 이것이 확정 지표가 아니라 일반적 경고 신호라고 단서를 단다.

Java4Shell 과 Ruby2Shell 도 같은 주에 나왔으므로 점검 범위를 넓혀야 한다. JDK 와 Ruby 는 애플리케이션 의존성 목록이 아니라 베이스 이미지와 번들된 런타임에 숨어 있는 경우가 많다. GitHub Enterprise Server 처럼 런타임을 번들하는 제품은 벤더 패치를 기다려야 한다.

### 구조적 시사점

첫째, **노출 감소 속도**가 핵심 지표가 된다. Wiz 는 패치를 검증하고 서비스 소유자와 롤아웃을 조율하는 수작업이 여전히 크다고 인정하면서, 프로덕션에서 노출을 얼마나 빨리 줄일 수 있는지에 집중하라고 권한다. 버전 인벤토리, 설정 인벤토리(HTTP/2 가 어디서 켜져 있는가), 그리고 기능을 끄는 완화 스위치를 평소에 준비해 두는 조직이 유리하다.

둘째, **공격 표면 축소가 패치보다 싸다.** 쓰지 않는 프로토콜, 모듈, 최적화 경로를 꺼 두는 것은 미래의 취약점까지 미리 막는다. Calif 의 vibe-uncoding 제안은 슬로건처럼 들리지만, 기본값을 최소화하라는 오래된 보안 원칙의 재발견이다.

셋째, **메모리 안전 언어로의 이행 압력**이 커진다. 런타임과 프록시 같은 공유 인프라에서 Rust 등으로의 재작성 논의가 다시 힘을 얻을 것이다. 다만 재작성 자체가 새 버그를 만들 수 있고, 성능 핵심부는 여전히 unsafe 코드가 필요하다는 현실도 함께 고려해야 한다.

### 세 가지 시나리오

낙관적으로 보면, AI 가 수십 년 묵은 결함을 짧은 기간에 대량으로 털어내고, 몇 년 뒤의 기반 소프트웨어는 지금보다 훨씬 단단해진다. Wiz 도 장기적으로는 이 과정이 소프트웨어를 강화할 수 있다고 쓴다. 비관적으로 보면, 공격자가 같은 도구로 패치 적용 속도를 앞질러 레거시 시스템을 대량으로 장악한다. HN 의 한 사용자는 반년 안에 중요 인프라가 심각하게 뚫릴 것이라고 내다봤다(요지 요약). 현실적인 시나리오는 그 중간, 즉 한동안 "치명적 CVE 가 매주 나오는" 고강도 패치 시기를 거치며 조직 간 대응 속도 격차가 피해 격차로 이어지는 것이다.

## 결론

"복잡해서 아무도 못 찾는다"는 공식적인 방어선은 아니었지만, 사실상 많은 C 코드를 지켜 온 방어선이었다. 이번 주의 Nginx, Java4Shell, Ruby2Shell 은 그 방어선이 더 이상 유효하지 않다는 것을 세 번 연속으로 보여 주었다. 11년 묵은 버그를 다섯 팀이 동시에 찾았다는 사실은, 같은 버그를 여섯 번째로 찾는 쪽이 공격자일 가능성도 높아졌다는 뜻이다.

리드 질문에 답하자면, 지금의 패치 주기로는 버티기 어렵다. 필요한 것은 더 빠른 패치만이 아니라 덜 노출된 기본값, 즉 쓰지 않는 기능을 꺼 두고 무엇이 어디서 켜져 있는지 아는 상태다. 독자에게 묻는다. 당신의 인프라에서 HTTP/2 는 어디서 켜져 있고, 그것을 지금 당장 끌 수 있는가. JDK 와 Ruby 버전을 베이스 이미지까지 포함해 한 번의 질의로 뽑을 수 있는가. 이 두 질문에 바로 답할 수 없다면, 다음 주의 CVE 를 기다리기 전에 그 인벤토리부터 만드는 것이 우선이다.
