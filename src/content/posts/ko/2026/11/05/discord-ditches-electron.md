# Discord 는 왜 Electron 을 버리는가 — GPUI 로 옮긴 290MB 의 의미

> 크로스플랫폼 데스크톱 앱의 사실상 표준이던 Electron 을, 가장 유명한 Electron 앱 중 하나가 떠난다. 이것은 "웹 기술로 데스크톱 앱을 만든다"는 10년의 합의가 깨지는 신호인가, 아니면 자금과 인력이 넉넉한 회사만 누릴 수 있는 사치인가.

## 도입

2026년 11월 5일(KST), Hacker News 에 「Discord is ditching Electron and its new app uses less RAM」이라는 The Verge 기사가 올라와 496점, 댓글 439개를 모았다. 다음 날에는 Windows Latest 의 Abhijith M B 가 쓴 후속 기사 「Every Windows 11 app should kill Electron, and Discord just showed why」가 다시 483점, 댓글 512개를 모았다. 이틀 연속으로 같은 주제가 1면에 오른 셈이다.

Windows Latest 의 정리에 따르면, Discord 는 Electron 클라이언트를 Rust 로 작성한 새 클라이언트로 교체하고 있으며, 그 UI 는 Zed 에디터 제작진이 만든 GPU 가속 UI 프레임워크 GPUI 위에 올라가 있다. 많은 이들이 예상했던 Tauri 가 아니다. 이 기사의 저자가 확인한 작업 관리자 화면에서 새 클라이언트("Discord Phoenix")는 계정 두 개에 로그인한 상태로 290.2MB 를 쓰고 있었다. 저자의 PC 에서 Electron 앱은 유휴 상태에서도 보통 1~2GB 를 쓴다고 한다.

Discord 는 지난 10년 동안 "Electron 으로도 대규모 앱을 만들 수 있다"는 대표 사례였다. 그 회사가 떠난다는 사실이 이 뉴스의 무게다.

## 무엇이 바뀌는가 — Rust, GPUI, 그리고 시스템 웹뷰

Windows Latest 기사가 전하는 사실관계를 정리한다. (The Verge 원문은 이 글을 쓰는 시점에 직접 확인하지 못해, 후속 보도와 HN 토론을 기반으로 한다.)

**프레임워크.** 새 데스크톱 클라이언트는 Rust 로 작성되고 GPUI 로 UI 를 그린다. GPUI 는 HTML 없이 GPU 로 인터페이스를 직접 그리는 프레임워크다. Discord 는 2018년부터 Rust 를 써 왔고, GPUI 에 자체 패치를 얹어 쓰고 있으며 그중 일부를 업스트림에 올릴 수도 있다고 한다.

**웹 기술은 필요한 곳에만.** YouTube 임베드와 Activities 는 시스템 웹뷰를 쓴다. 브라우저용 앱은 HTML 렌더링을 유지하지만 로직은 WebAssembly 로 옮긴다. 모바일에서는 iOS 와 Android 모두 React Native 를 버리고, 네이티브 인터페이스를 유지하면서 Rust 를 통해 데스크톱과 앱 코드를 공유한다. 즉 "웹을 버린다"가 아니라 "앱의 핵심 로직을 Rust 한 벌로 모으고, 화면은 플랫폼마다 가장 가벼운 수단으로 그린다"는 설계다.

**성능 수치.** CTO Stanislav Vishnevskiy 가 공유한 15초짜리 영상에서 Rust 클라이언트는 Electron 클라이언트가 로딩을 끝내기 전에 친구 목록을 띄웠다. Discord 직원들은 둘 다 콜드 스타트였다고 확인했다. 기사 저자가 프레임 단위로 본 결과, Electron 앱은 약 3초간 빈 어두운 창을 보여준 뒤 팁을 띄웠고, Rust 창은 실행 1초 안에 나타났다. Vishnevskiy 는 클릭이 즉각적으로 느껴져 이제 돌아갈 수 없다고 말했다.

**RAM.** 앞서 말한 290.2MB 는 계정 두 개를 동시에 띄운 수치다. 2025년 12월에 한 Discord 직원은 일반적인 사용량이 1GB 미만이라고 말한 바 있고, 저자는 290.2MB 가 그 기준보다 약 70% 낮다고 계산한다. 다만 저자 스스로 이것이 초기 빌드의 스냅샷이며 Discord 가 동일 조건 벤치마크를 공개하지 않았다는 단서를 단다.

**기타.** 새 클라이언트는 로그인 토큰을 시스템 키링(Windows 에서는 자격 증명 관리자)에 저장하고, "Starting" 화면 없이 백그라운드에서 업데이트한다. 마케팅 디렉터는 Linux 에서도 동작한다고 했고, 비공개 테스트가 "곧" 시작된다고 했지만 공개 출시일은 없다. 엔지니어링 VP Mark Smith 는 접근성과 보안이 성능만큼 중요하다고 말했다.

**Electron 쪽의 마지막 노력.** 흥미로운 대목은, Discord 가 2026년 9월 Electron 42 로 업그레이드하면서 CPU 사용량 중앙값을 약 17% 줄였지만 p50 메모리는 약 4% 늘었다는 점이다. Electron 위에서 최적화를 계속해 봤자 메모리 쪽은 크게 개선되지 않는다는 판단이 이번 결정의 배경으로 읽힌다.

## 왜 지금인가 — Electron 의 계산서가 바뀐 세 가지 이유

Electron 은 Chromium 전체와 Node.js 를 앱마다 통째로 번들한다. HN 댓글들이 다시 정리했듯, 이 비용은 처음부터 알려져 있었다(직접 인용은 아니고, 댓글들의 설명을 요약). 그런데도 Electron 이 10년간 표준이었던 이유는, 그 비용을 상쇄하는 이득이 컸기 때문이다. HN 토론에서는 웹캠이나 미디어 접근이 필요한 크로스플랫폼 앱을 하나 내놓으려면 예전에는 플랫폼별 네이티브 라이브러리나 Qt 패키징 기술, 혹은 JVM 이 필요했고, Electron 이 그 패키징 문제를 해결했다는 설명이 나왔다(댓글 논지 요약). 한 팀이 여러 플랫폼을 감당하고, 더 구하기 쉬운 웹 개발자를 고용할 수 있다는 비즈니스 논리도 컸다.

그렇다면 무엇이 바뀌었나. 세 가지 변화가 겹친다.

**첫째, Rust 네이티브 UI 의 선택지가 실용 단계에 들어왔다.** GPUI 는 Zed 라는 실제 제품에서 검증된 프레임워크다. HN 에서는 Iced, Slint, Blitz/Dioxus, Sciter 같은 대안도 거론됐다. 다만 GPUI 의 성숙도에 대해서는 의견이 갈렸다. GPUI 가 기본적으로 Zed 의 필요에 맞춰 만들어졌고, crates.io 공식 릴리스가 없으며, 호환성을 깨는 변경이 있다는 우려가 나왔고, Discord 팀이 GPUI 메인테이너들과 접촉했다는 이야기도 언급됐다(댓글 논지 요약). Discord 가 자체 패치를 얹은 포크를 쓴다는 사실은 이 미성숙함을 회사의 엔지니어링 자원으로 메우고 있다는 뜻이기도 하다.

**둘째, 메모리가 다시 비싸졌다.** Windows Latest 저자는 RAM 에 대한 관심이 되살아난 이유 중 하나로 AI 수요가 끌어올린 DRAM 가격을 들고, Microsoft 도 Windows 11 의 RAM 사용량을 줄이고 있다고 짚는다. 사용자가 16GB 노트북에서 브라우저, IDE, 로컬 LLM 을 동시에 돌리는 시대에, 채팅 앱 하나가 1GB 를 차지하는 것은 더 이상 무시할 수 있는 비용이 아니다.

**셋째, AI 가 재작성 비용을 낮췄다는 주장.** HN 에서는 AI 덕분에 플랫폼별 네이티브 앱을 따로 유지하는 비용이 충분히 싸져서 Electron 의 트레이드오프가 더 이상 성립하지 않는다는 의견과, 다섯 개 플랫폼을 테스트하는 오버헤드는 여전히 크다는 반론이 맞섰다(댓글 논지 요약). 같은 맥락에서, 사람이 쓴 코드베이스를 AI 가 다시 쓰면 조직의 이해가 사라지는 것 아니냐는 질문도 큰 스레드를 이뤘다. 반론은 새 코드베이스에 합류하는 것과 다를 바 없고, 엔지니어는 이미 추상화에 의존해 일한다는 것이었다(댓글 논지 요약).

반대편의 논점도 무시할 수 없다. 가장 뜨거웠던 것은 **접근성**이었다. 스크린 리더 지원은 타협할 수 없는 조건이고 Rust UI 툴킷은 역사적으로 이 부분이 약했다는 지적에, GPUI 에 AccessKit 기반 접근성 경로가 생겼지만 UIA 같은 네이티브 API 보다는 덜 성숙하다는 답이 이어졌다(댓글 논지 요약). 저시력 사용자 중에는 웹 스택 덕분에 앱별 확대와 커스터마이즈가 쉬웠다는 사람도 있었고, 반대로 Discord 는 Electron 시절에도 접근성이 나빴고 개선에 수년이 걸렸다는 지적도 있었다(댓글 논지 요약). Electron 이 접근성을 공짜로 주지 않았듯, GPUI 도 공짜로 주지 않는다. 결국 실제 스크린 리더로 계속 테스트하는 조직의 의지가 결정한다.

또 하나, 메모리 수치를 둘러싼 냉정한 시각도 있었다. 290MB 라는 숫자가 인상적이지만, 빈 Chromium 탭 하나도 비슷한 양을 쓴다는 지적이 나왔다(댓글 논지 요약). 비교 대상이 "최적화되지 않은 Electron 앱"이라는 점, 그리고 기능이 다 들어간 정식판이 아니라는 점을 감안하면, 최종 수치는 지금보다 올라갈 가능성이 높다.

## 다른 앱들은 따라갈 수 있는가 — 실무자에게 주는 시사점

Windows Latest 저자는 Meta(WhatsApp)와 Microsoft(Teams)가 "변명거리가 바닥나고 있다"고 쓴다. 그의 테스트에서 WebView2 래퍼인 WhatsApp 은 최대 1.2GB, Teams 는 유휴 상태에서 963MB 를 썼다. 그는 WinUI 는 Windows 에서만 돌기 때문에 Discord 의 선택지가 되기 어려웠고, GPUI 는 이미 Windows, macOS, Linux 에서 돈다고 지적한다.

하지만 이것을 "모두 Electron 을 버려라"로 읽는 것은 성급하다. 실무자가 가져갈 교훈은 더 구체적이다.

첫째, **Discord 의 전략은 "공유 코어 + 얇은 UI"다.** 이번 재작성의 핵심은 GPUI 라는 특정 프레임워크가 아니라, 데스크톱, 모바일, 웹의 앱 로직을 Rust 한 벌로 모은 구조다. 웹은 WebAssembly 로, 모바일은 네이티브 UI 로, 데스크톱은 GPUI 로 같은 코어를 감싼다. 이 구조는 Discord 가 2018년부터 Rust 에 투자해 왔기 때문에 가능했다. Rust 코어가 없는 조직이 "Electron 을 GPUI 로" 바꾸는 것은 Discord 가 한 일과 전혀 다른 크기의 일이다.

둘째, **웹뷰를 완전히 버리지 않는다.** YouTube 임베드와 Activities 처럼 웹 콘텐츠가 본질인 부분은 시스템 웹뷰를 쓴다. 전부 네이티브냐 전부 웹이냐의 양자택일이 아니라, 화면 단위로 가장 싼 수단을 고르는 하이브리드가 현실적인 해답이다.

셋째, **측정이 먼저다.** Discord 가 Electron 42 로 CPU 를 17% 줄이고 메모리가 4% 늘었다는 데이터를 갖고 있었다는 사실이 중요하다. 재작성을 결정하기 전에 기존 스택에서 무엇이 개선 가능하고 무엇이 구조적 한계인지를 수치로 알고 있었다는 뜻이다.

시나리오로 보면 이렇다. **낙관적으로는** Discord 의 성공이 GPUI 생태계에 자원과 관심을 끌어오고, 접근성과 문서가 성숙해 중견 기업도 쓸 수 있는 선택지가 된다. **비관적으로는** 접근성 문제나 기능 동등성 문제로 출시가 길어지고, "대기업만 가능한 재작성"이라는 인식이 굳어진다. **현실적으로는** 대규모 사용자 기반을 가진 소수의 앱이 비슷한 길을 가고, 대다수의 사내 도구와 중소 SaaS 데스크톱 앱은 Electron 혹은 Tauri 같은 웹뷰 기반에 남는다. 비공개 테스트 결과가 그 갈림길을 보여줄 것이다.

## 결론

리드 질문에 답하자면, 이것은 Electron 시대의 끝이라기보다 "Electron 이 기본값인 시대"의 끝에 가깝다. Electron 이 해결한 패키징과 크로스플랫폼 문제는 여전히 실재하고, 대부분의 팀에게 그 계산은 여전히 Electron 쪽으로 기운다. 달라진 것은 계산식의 변수들이다. 메모리 가격이 올랐고, Rust 네이티브 UI 가 실전에 쓰일 만큼 자랐고, 재작성 비용에 대한 기대가 AI 로 바뀌었다.

Discord 의 이번 결정이 증명하는 것은 "Electron 은 나쁘다"가 아니라 "규모가 충분히 크고 공유 코어에 투자해 온 조직에게는 Electron 의 비용이 이득을 넘어섰다"는 것이다. 수억 명이 매일 띄워 두는 앱에서 수백 MB 는 사용자들의 RAM 을 합산하면 막대한 자원이다.

독자에게 남기는 질문은 이것이다. 당신의 데스크톱 앱에서 Electron 이 사주는 것은 무엇이고, 그 대가로 사용자에게 청구하는 것은 무엇인가. 그 두 숫자를 실제로 측정해 본 적이 있는가.
