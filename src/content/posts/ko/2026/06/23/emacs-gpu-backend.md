# 이맥스에 GPU를: 레거시 에디터가 역설적으로 던진 질문

> 40년 된 에디터에 GPU 렌더링을 붙이는 것이 가능할까. 그리고 가능하다면, 그 코드를 받아들일 공동체는 존재하는가.

## 도입

2026년 6월, 개발자 andros는 Hacker News에 짧은 링크 하나를 올렸다. 제목은 "I built a GPU back end for Emacs." 점수 180점, 91개의 댓글이 달렸다. 기술 뉴스 사이트에서 흔히 볼 수 있는 규모지만, 이 게시물이 촉발한 논쟁은 단순한 성능 개선 이야기를 훌쩍 넘어서 있었다.

Emacs는 1976년에 탄생한 텍스트 에디터다. GNU 프로젝트의 핵심 소프트웨어 중 하나로, 오늘날에도 전 세계 수십만 명의 개발자와 연구자가 매일 사용한다. 그 화면 렌더링 엔진, 즉 리디스플레이(redisplay) 시스템은 수십 년에 걸쳐 축적된 C 코드로 이루어져 있으며, 근본적인 구조는 프로세서가 단일 코어로 텍스트를 처리하던 시대의 설계를 그대로 유지하고 있다.

andros가 한 일은 이 오래된 설계 위에 Metal(macOS)과 OpenGL ES(GNU/Linux) 드라이버를 올리는 것이었다. 내장 동영상 재생, 셰이더 기반 커서 애니메이션, 버퍼 전환 시 크로스페이드 효과 같은 기능이 새로 생겼다. 4K 디스플레이에서 라인 스크롤 속도는 기존 Cairo 렌더러의 2.05배, 전체 화면 재드로우는 1.84배, 이미지 스크롤은 11.5배에 달했다.

그런데 GNU Emacs 프로젝트는 이 패치를 거절했다. 이유는 성능이나 코드 품질이 아니었다. LLM(대형 언어 모델)으로 생성된 코드가 포함되어 있다는 것이었다. 자유 소프트웨어 재단(FSF)의 저작권 정책과 충돌한다는 판단이었다.

이 사건은 복수의 질문을 동시에 제기한다. GPU 렌더링이 실제로 Emacs 사용자 경험을 개선하는가. 40년 된 아키텍처 위에 현대적 드라이버를 얹는 것이 기술적으로 어떤 의미를 갖는가. 그리고 오픈소스 공동체는 LLM 생성 코드를 어떤 기준으로 대해야 하는가. 이 글은 세 질문을 차례로 살핀다.

## GPU 백엔드의 구조: 3레이어 추상화와 구현 과제

andros가 선택한 접근법의 핵심은 Emacs 리디스플레이 엔진을 건드리지 않는다는 원칙이었다. Emacs의 리디스플레이 시스템은 코드베이스에서 가장 복잡한 영역 중 하나로, 기존 Cocoa·X11 백엔드 개발자들도 수년간 씨름해 온 부분이다. 이를 직접 수정하는 대신 그는 세 층으로 구성된 추상화를 설계했다.

첫 번째 층은 기존 리디스플레이 엔진이다. 이 층은 전혀 수정하지 않았다. Emacs가 텍스트와 UI 요소를 어떻게 배치할지 결정하는 모든 로직은 그대로 유지된다. 두 번째 층은 '중립 드로잉 정책 레이어(neutral drawing policy layer)'로, 순수 C로 작성된 약 25개의 기본 연산(primitive operation)으로 구성된다. 이 층은 "여기에 이런 글리프를 그려라", "이 영역을 이 색으로 채워라" 같은 명령을 플랫폼에 독립적인 형태로 표현한다. 세 번째 층은 실제 드라이버로, macOS에서는 Metal, Linux에서는 OpenGL ES가 이 층을 담당한다.

Metal 드라이버의 동작 방식은 다음과 같다. CoreText가 글리프를 GPU 텍스처 아틀라스에 래스터라이징한다. 각 글리프는 텍스처드 쿼드로 변환되어 GPU에서 합성된다. 프레임 합성 전체가 GPU 파이프라인 안에서 처리되므로, CPU에서 픽셀을 계산하는 Cairo 방식과 근본적으로 다른 처리 경로를 갖는다. Linux OpenGL 드라이버는 FreeType과 EGL을 사용해 동일한 방식을 재현한다. 텍스처 아틀라스 기반 글리프 렌더링이라는 접근은 게임 엔진이 수십 년 전부터 채택해 온 기법이지만, Emacs에 적용하는 과정에는 예상치 못한 복잡성이 따랐다.

구현 과정에서 부딪힌 기술적 과제는 여러 겹이었다. 가장 까다로운 문제는 기존 Cocoa 백엔드와의 픽셀 완전 일치(pixel-perfect parity)였다. GPU와 CPU의 안티앨리어싱 방식은 미묘하게 다르다. 릴리프 색상(relief color)의 처리, 글리프 위치 계산의 소수점 이하 오차 등이 육안으로는 보이지 않는 차이를 만들었다. andros는 자동화된 테스트 하네스를 구축해 두 백엔드의 렌더 결과를 화면 캡처 수준에서 비교했다. 픽셀 단위 회귀 테스트는 이 종류의 렌더링 작업에서 흔히 쓰이는 기법이지만, 여기서는 두 렌더러가 동일한 입력에서 동일한 출력을 내놓도록 수렴시키는 과정 자체가 상당한 반복 작업을 요구했다.

CADisplayLink 관련 문제도 있었다. macOS에서 디스플레이 동기화를 위해 CADisplayLink를 사용했는데, Emacs가 유휴 상태일 때 이 메커니즘이 동결되는 현상이 발생했다. 해결책은 애니메이션 타이머를 Lisp 레이어로 이관하고, 60Hz 또는 30Hz로 통합된 펌프를 구현하는 것이었다. Linux에서는 X11 더블 버퍼 익스텐션이 유령 이미지(ghost image)를 만들어냈다. 원인을 추적한 결과, 해당 익스텐션이 초기화 이후 GPU에 의해 전혀 갱신되지 않은 백 버퍼를 화면에 출력하고 있었다. 이 두 버그의 공통점은 기존 Emacs 코드베이스가 단일 스레드 CPU 렌더링을 가정하고 설계된 데 따른 부작용이라는 점이다.

이 구현이 보여주는 것은 거대한 레거시 코드베이스에 새 하드웨어 추상화를 삽입하는 일이 단순히 드라이버를 작성하는 것보다 훨씬 넓은 범위의 작업임을 확인시켜 준다. 테스트 인프라 구축, 기존 동작과의 정합성 확보, 플랫폼별 엣지 케이스 처리가 드라이버 코드 자체보다 더 많은 공수를 차지할 수 있다.

## 성능 결과의 역설: 해상도가 뒤집는 법칙

벤치마크 결과는 직관적이지 않다. GPU가 항상 빠를 것이라는 예상은 절반만 맞다.

노트북 해상도(1616×912)에서 GPU 백엔드의 타이핑 성능은 Cairo의 0.71배였다. 즉, 일반적인 사용 환경에서 GPU 버전은 기존보다 느리다. 이 결과는 언뜻 실망스럽지만, 그 이유를 이해하면 오히려 합리적이다.

작은 화면에서 한 문자를 입력할 때 갱신해야 하는 픽셀 영역은 좁다. CPU 기반 Cairo 렌더러는 이 좁은 영역에 대해 빠르게 응답한다. 반면 GPU는 커맨드 버퍼를 구성하고, GPU에 전송하고, 합성 결과를 다시 화면으로 가져오는 오버헤드가 발생한다. 갱신 영역이 작을수록 이 고정 비용의 비중이 커진다. CPU 래스터라이징은 업데이트 영역에 비례해 비용이 증가하는 반면, GPU는 파이프라인 셋업 비용이 상수에 가깝다. 화면이 작으면 CPU가 유리하다.

4K 디스플레이(3760×2210)에서는 상황이 완전히 역전된다. 라인 스크롤 2.05배, 전체 화면 재드로우 1.84배, 이미지 스크롤 11.5배. 이미지 스크롤 11.5배라는 수치는 특히 인상적이다. Cairo가 4K 이미지를 스크롤할 때 픽셀 수에 비례하여 CPU 부하를 소모하는 동안, GPU는 텍스처 샘플링과 합성을 병렬로 처리하기 때문에 부하 증가폭이 훨씬 완만하다.

andros는 이것을 "Cairo의 비용은 픽셀 수에 선형으로 증가하지만, GPU의 비용은 거의 변하지 않는다"라는 문장으로 요약한다. 이 원리는 Hacker News 댓글에서 공명을 일으켰다. 여러 사용자가 4K Wayland 디스플레이에서 Emacs의 심각한 지연을 경험한다고 보고했다. 고해상도 디스플레이의 보급이 기존 CPU 렌더링 방식의 한계를 실용적인 문제로 만들고 있는 것이다.

이 결과가 시사하는 바는 분명하다. GPU 백엔드의 가치는 평균적인 노트북 사용자보다 4K 모니터를 사용하는 개발자에게 훨씬 크다. 그리고 4K 디스플레이는 더 이상 소수의 전문가 환경이 아니다. 개인용 고해상도 모니터의 가격이 하락하면서, 이 격차는 점점 더 많은 Emacs 사용자에게 실질적인 문제가 되어가고 있다.

또한 GPU 백엔드가 가능하게 한 기능들, 즉 셰이더 기반 커서 애니메이션이나 버퍼 전환 크로스페이드는 단순한 시각 효과가 아니다. Hacker News 댓글에서 여러 사용자가 지적했듯이, 커서 강조 효과는 시력 약자를 위한 접근성 기능으로 기능할 수 있다. GPU 기반 렌더링이 열어주는 공간은 성능뿐 아니라 사용자 다양성 측면에서도 의미를 갖는다.

## GNU의 거부와 LLM 코드 정책: 오픈소스의 자가당착

andros는 이 프로젝트에서 코드의 100%를 LLM으로 생성했다는 사실을 공개적으로 밝혔다. GNU Emacs 프로젝트는 이것을 이유로 패치 수용을 거부했다.

FSF의 입장은 이해할 수 있는 역사적 맥락을 갖는다. 자유 소프트웨어 재단은 저작권 양도(copyright assignment)를 통해 기여 코드의 법적 소유권을 일원화한다. 이는 나중에 라이선스 위반이 발생했을 때 FSF가 법적으로 대응할 수 있도록 하기 위한 장치다. LLM 생성 코드의 저작권 귀속은 현재 법적으로 불분명하다. 저작물의 창작자가 명확하지 않은 코드에 대해 저작권 양도가 성립하는지, FSF가 법적 행위 주체로 기능할 수 있는지는 아직 판례가 확립되지 않은 영역이다.

그러나 Hacker News 댓글 반응은 이 결정에 비판적이었다. 한 사용자는 "FSF의 GPU 이념적 입장은 기괴하다"라고 썼다. 또 다른 댓글은 "당신은 그것이 가능하다는 것을 보여주었다. 더 많은 사람들이 함께 Emacs 리디스플레이 코드를 처치할 수 있기를 바란다"라는 반응을 보였다.

이 논쟁이 보여주는 긴장은 여러 층위에 걸쳐 있다. 첫째, 코드의 출처와 코드의 기능적 품질을 분리하는 문제다. andros가 LLM을 사용해 생성한 코드는, 그 출처와 무관하게, 4K 디스플레이에서 11.5배의 이미지 스크롤 성능을 달성한다. 코드가 동작하고, 테스트를 통과하고, 기존 행동과 정합성을 유지한다면, 그것을 생성한 도구의 성격이 수용 여부를 결정해야 하는가.

둘째, 자유 소프트웨어 운동의 핵심 가치와 실용적 발전 사이의 충돌이다. GNU 프로젝트는 소프트웨어 자유를 위해 오래된 코드를 유지하고, 호환성을 지키며, 법적 순결성을 보호하는 데 헌신한다. 이 헌신은 프로젝트를 수십 년 동안 살아있게 한 원동력이기도 하지만, 동시에 변화 속도를 늦추는 무게이기도 하다.

셋째, LLM 코드의 법적 불확실성이 실제 장벽인지, 아니면 기술 변화에 대한 보수적 반응을 합리화하는 논리인지의 질문이다. FSF가 LLM 코드에 대한 정책을 표명한 것 자체는 시대 흐름에 반응하는 것으로 볼 수 있다. 그러나 그 반응이 기여를 차단하는 방향으로만 작동한다면, 결과적으로 프로젝트는 점점 더 많은 잠재적 기여자를 잃게 된다.

Emacs는 현재 Neovim과의 경쟁에서 시각적 기능 면에서 뒤처지고 있다는 인식이 커지고 있다. smear-cursor, 펄스 애니메이션, 부드러운 스크롤 같은 기능들은 Neovim 생태계에서 먼저 도입되었다. GPU 백엔드는 이 간극을 좁힐 수 있는 기술적 토대였다. 그 토대를 거부한 결정이 프로젝트의 장기적 활력에 어떤 영향을 미칠지는 지금 당장 판단하기 어렵지만, 질문 자체를 피할 수는 없다.

andros의 작업은 개인 포크(fork)로 유지된다. 코드는 공개되어 있고, 누구든 사용할 수 있다. 이 패치를 LLM 없이 재구현하는 기여자가 나타난다면 GNU 프로젝트에 합류할 수 있을 것이다. 그러나 그 일이 실제로 일어날지, 또는 이 시도 자체가 오픈소스 거버넌스에 대한 더 깊은 토론을 불러올지는 미지수다.

## 결론

이맥스에 GPU를 붙이는 일이 가능하다는 것이 증명되었다. 3레이어 추상화로 기존 코드를 최소한으로 건드리면서, 4K 환경에서 의미 있는 성능 개선을 달성했다. 기술적 검증으로서의 가치는 패치 수용 여부와 무관하게 성립한다.

그런데 이 사건이 오픈소스 생태계에 던지는 질문은 기술을 넘어선다. LLM 생성 코드를 어떻게 평가할 것인가. 코드의 출처와 기능적 품질 중 무엇이 더 중요한가. 40년 된 공동체의 법적·이념적 순결성 유지와 기술적 진보 사이에서 어디에 무게를 둘 것인가.

쉬운 답은 없다. FSF의 입장에는 수십 년에 걸쳐 형성된 법적·철학적 토대가 있다. 동시에 GPU 없이 4K 디스플레이의 지연을 감수해야 하는 사용자들의 불편은 지금 이 순간에도 실재한다. 그 불편이 이념적 결정보다 덜 중요하다고 말하기는 어렵다.

이 패치가 촉발한 가장 중요한 결과는 아이러니하게도 코드 자체가 아닐지 모른다. "Emacs 리디스플레이 코드를 누군가 처치해줬으면"이라는 Hacker News의 댓글 하나가 보여주듯, 이 시도는 수많은 Emacs 사용자가 오랫동안 품어온 욕구를 가시화했다. 그 욕구가 어떤 형태로든 다음 행동을 만들어낼지, 그것이 이 이야기의 진짜 속편이 될 것이다.
